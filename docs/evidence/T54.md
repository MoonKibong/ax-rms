### 구현 중 발견한 사실(기준 6 설계를 두 번 바꾼 이유)

최초 설계(계약서 예시 그대로: 1초/6초 잠금의 성공·실패를 직접 단언)는 실제로 테스트할 수 없는 가정에
기반했다. `busy_timeout` 기본값이 0이 아니라 3000이라는 것 외에도, 구현하며 다음을 직접 확인했다:

- `transaction_mode=immediate`에서 두 커넥션의 `BEGIN IMMEDIATE`가 부딪히면, xerial sqlite-jdbc
  3.53.4.0은 "먼저 쥐고 있다가 몇 초 뒤 풀어주는" 인위적인 지연에 대해 재시도 중 그 해제를 바로 감지하지
  못한다 — 잠금을 0초만(거의 즉시 풀어줘도) 쥐고 있어도 대기 쪽은 약 5000ms(=busy_timeout) 뒤에야 끝나고,
  그마저도 실패로 끝난다(직접 측정: 0·1·4초 보유 모두 대기 쪽이 5018~5023ms 뒤 `SQLITE_BUSY`로 끝남).
  WAL이나 자동 커밋 여부와는 무관했다(원인을 하나씩 떼어 확인함: `busy_timeout`만 켜면 1초 보유는
  1035ms에 정상 성공, `transaction_mode=immediate`를 더하면 그 즉시 깨짐).
- 반대로 실제 업무 트랜잭션처럼 경쟁이 짧게(수십 ms 이하) 끝나는 경우는 전혀 문제가 없다 — 기준
  5(`ConcurrentAssignmentTest`)가 5회 반복 모두 안정적으로 통과한다.

그래서 기준 6을 "인위적으로 오래 쥐고 있다가 푸는 잠금의 성공·실패"가 아니라 두 가지로 다시 설계했다:
(a) 실제처럼 거의 동시에 시작하는 두 쓰기가 둘 다 성공하는지(`nearSimultaneousWritersBothSucceed`),
(b) busy_timeout보다 뚜렷이 긴(8초) 잠금에서 대기 쪽이 실패까지 걸리는 시간이 설정값(5000ms) 근처인지
직접 재는 것(`lockLongerThanBusyTimeoutFailsAfterRoughlyTheConfiguredTimeout`, `[4500,6500]` 범위).
계약서가 요구한 "잠금이 실제로 재현되고 busy_timeout이 그 재현에 영향을 준다"는 그대로 지켰다 — 다만
그 증명 방법을 실제로 관찰한 드라이버 동작에 맞게 바꿨다(계약의 수용 기준 문장이나 범위는 바꾸지 않았다).

### 그대로 둠, PM 결정 필요 — 지적 1(P1): `LockObservationTest`

리뷰어는 계약서 기준 6 그대로(1초 보유 뒤 성공, 6초 보유 뒤 `SQLITE_BUSY` 각각 직접 단언)를 복구하라고
했다. 직접 다시 확인했지만, 이는 `transaction_mode=immediate`를 쓰는 한 이 드라이버에서 재현할 수 없는
동작이다 — Spring/HikariCP를 완전히 빼고 순수 `DriverManager` 커넥션 두 개로만 다시 확인했다:

```java
// jdbc:sqlite:probe.db?busy_timeout=5000&transaction_mode=immediate
holder: setAutoCommit(false); insert; (1초 뒤) commit()
waiter(다른 스레드, 같은 순간부터 대기): setAutoCommit(false); insert; commit()
```

```
holder lock acquired at +0ms
holder released at +1003ms
waiter FAILED: org.sqlite.SQLiteException: [SQLITE_BUSY] The database file is locked (database is locked)
waiter elapsed=5025ms
```

Spring·HikariCP·WAL·자동커밋 여부와 무관하게, `transaction_mode=immediate`에서 두 `BEGIN IMMEDIATE`가
부딪히면 xerial sqlite-jdbc 3.53.4.0은 잠금이 1초 만에 풀려도 대기 쪽이 그걸 감지하지 못하고 busy_timeout

## `origin/main` 병합(T#56) 뒤 새로 드러난 문제 — PM 결정 필요

계약서 "전제"가 예상한 영향(#56의 `DbBusyTest`가 즉시 409 대신 수 초 뒤 409를 받는 것, 타이밍만)보다 **더
심각한 문제**가 실제 병합(`origin/main`의 T#56, 커밋 `c1d518b`)에서 드러났다. `make test` 256개 중
`DbBusyTest.writeWhileAnotherConnectionHoldsTheLockIsConflict`(T#56, `DbBusyTest.java:57`) 단 하나가
실패한다 — 나머지 255개(기존 233 + T54 신규 9 + T56 신규 14, `DbBusyTest` 제외)는 전부 통과한다.

### 재현

`DbBusyTest`는 1번째 쓰기 요청을 잠금이 걸린 채로 보내 409 `DB_BUSY`를 받고(이건 통과한다), 잠금을 푼 뒤
**같은 커넥션 풀의 커넥션으로 같은 요청을 재시도**해 201을 기대한다(`DbBusyTest.java:57`). 그 재시도가
500으로 끝난다:

```
org.springframework.transaction.TransactionSystemException: JDBC commit failed
Caused by: org.sqlite.SQLiteException: [SQLITE_ERROR] SQL error or missing database
  (cannot commit - no transaction is active)
```

Spring·HikariCP를 완전히 빼고 순수 `HikariDataSource` + `DriverManager`만으로 재현해, HikariCP 자체의
문제가 아니라 **`org.xerial:sqlite-jdbc` 드라이버 자체의 버그**임을 확인했다(아래는 스크래치 테스트의
결과 요약 — 커밋하지 않음):

```
locker: BEGIN IMMEDIATE (잠금을 쥔 채 유지)
c1(풀의 커넥션 1): setAutoCommit(false) → SQLITE_BUSY로 실패
locker: ROLLBACK (잠금 해제)
c2(같은 물리 커넥션 — identityHashCode 동일!): getAutoCommit() == false (!!) → setAutoCommit(false) 호출
  → insert 성공(그러나 실제로는 트랜잭션이 시작되지 않음) → commit() → SQLITE_ERROR: cannot commit
```

`org.sqlite.SQLiteConnection.setAutoCommit(boolean)`을 디컴파일해 보면(바이트코드 확인):
`connectionConfig.setAutoCommit(autoCommit)`(필드 갱신)을 **먼저** 하고, 그 다음에야
`db.exec("begin immediate;" 등)`을 시도한다. 그 `exec`가 `SQLITE_BUSY`로 실패해도 필드는 이미 `false`로
바뀐 뒤다. 그래서:

1. 커넥션 c1의 `setAutoCommit(false)`가 BUSY로 실패해도, 드라이버 내부의 "지금 autoCommit=false(=트랜잭션
   시작됨)" 플래그는 그대로 `false`로 남는다(실제로는 BEGIN이 성공하지 못했다).
2. 그 물리 커넥션이 (잠금이 풀린 뒤) 풀에서 재사용될 때, 새 `setAutoCommit(false)` 호출은 "이미
   false니까" 그대로 반환해(no-op) 버린다 — 진짜 `BEGIN IMMEDIATE`가 다시 나가지 않는다.
3. 그 상태에서 실행한 INSERT는 (실제로 트랜잭션이 없으므로) 자동커밋으로 바로 끝나고, Spring이 명시적으로
   호출하는 `commit()`은 SQLite 입장에서 "커밋할 트랜잭션이 없다"며 실패한다.

HikariCP의 `SQLExceptionOverride`(문제가 된 커넥션을 풀에서 버리게 하는 공식 메커니즘)로 우회를
시도했으나, `ProxyConnection.setAutoCommit()`의 바이트코드에는 예외를 가로채는 `checkException` 호출이
없어(다른 메서드와 다름) 이 경로에서는 전혀 동작하지 않는다(직접 확인함).

### 영향

`busy_timeout`(5000ms) 안에서 BUSY가 나는 모든 요청마다, 그 요청이 쓰던 풀의 커넥션 하나가 **영구히
오염된다**(앱이 재시작되거나 그 커넥션이 다른 이유로 버려지기 전까지). 커넥션 풀 크기(기본 10)만큼 반복되면
무관한 이후 요청들까지 500으로 실패할 수 있다 — 계약서 "결정" 절이 승인받은 "영향은 작다"(응답이 몇 초
느려질 뿐)라는 전제보다 범위가 넓다.

### 결정이 필요한 지점

이 문제는 T54가 고른 `transaction_mode=immediate`(기준 1·5)와 T56의 실제 HTTP 경로 테스트가 겹쳐야만
드러난다(T54 자신의 테스트는 원시 JDBC 또는 한 번만 실패하는 경로만 써서 이 재사용 시나리오를 만들지
않았다). 계약서 "전제"는 "나중에 merge하는 쪽이 고친다"고 이미 써 뒀고 T54가 그 쪽이지만, 실제 고치는
방법(예: Spring의 `DataSourceTransactionManager`를 상속해 `doBegin()` 실패 시 커넥션의
`setAutoCommit(true)`를 호출해 내부 플래그를 강제로 재동기화하는 보정 로직 추가)은 애플리케이션 전체의
모든 트랜잭션 경로에 영향을 주는 새 인프라라, 계약서가 승인한 "결정"의 위험 평가(응답 지연만)를 넘어선다.
코드는 고치지 않고 멈췄다 — 이슈에 알리고 PM 결정을 기다린다.

## 기준 7 — BUSY 뒤 커넥션 재사용 안전성 (PM 결정 A: `evictConnection`)

PM이 해결 방법 A(시작 실패 시 `evictConnection`으로 커넥션 폐기, 커스텀 `PlatformTransactionManager`)로


레드는 두 번째 트랜잭션의 `commit()`에서 난다 — 계약서 기준 7의 레드 설명(`TransactionSystemException`
←`SQLiteException: cannot commit`)과 정확히 일치하고, `DbBusyTest.java:57`의 500과 같은 근본 원인이다.

### 구현 — 계약서가 적은 방식(`doBegin()` 오버라이드)이 실제로는 늦다

계약서는 "`DataSourceTransactionManager`를 상속해 `doBegin()`을 오버라이드"하는 방식을 적었다. 그대로
구현해 실행해 보니 **레드가 그대로 남았다** — 디버그 출력으로 원인을 확인: Spring의 `doBegin()`
자체가 실패하면 **그 안에서 이미** `DataSourceUtils.releaseConnection(...)`으로 커넥션을 반납하고
`transactionObject.setConnectionHolder(null, false)`로 홀더를 지운 뒤에야 `CannotCreateTransactionException`
을 던진다(바이트코드로 확인, `DataSourceTransactionManager.doBegin():275-299`). 그래서 내 오버라이드의
`catch` 블록이 받는 시점에는 이미 커넥션이 반납되고 홀더가 비어 있어
(`transactionObject.getConnectionHolder()`가 `IllegalStateException: No ConnectionHolder available`을
던짐), `evictConnection()`을 부를 커넥션 자체를 못 집는다.

그래서 더 이른 지점으로 옮겼다: `DataSource.getConnection()`이 돌려주는 `Connection`을 동적 프록시로
감싸, `setAutoCommit(false)`가 BUSY(`SQLException`)로 실패하는 그 순간 바로 `evictConnection()`을
부른다(`BusyEvictingDataSource`). `evictConnection()`이라는 해결 방법 A의 메커니즘과 기준 7의 수용
기준 문장은 그대로다 — 계약서 "결정" 절의 서술(어느 클래스를 상속하는가)만 실제로 동작하는 지점으로
바뀌었다. 이 커넥션을 어떻게 앱 전체에 적용할지도 한 번 더 바뀌었다: `@Primary @Bean DataSource`로
새로 정의하면 Spring Boot의 `@ConditionalOnMissingBean(DataSource.class)`가 작동해 원래
`HikariDataSource` 빈 자체가 만들어지지 않는다(직접 확인함) — 그래서 `BeanPostProcessor`로 이미 만들어진
`dataSource` 빈을 초기화 직후 바꿔 끼우는 방식(`DataSourceRecoveryConfig`)을 썼다.
