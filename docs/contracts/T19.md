## 전제

- 선행 작업 #13, #15, #16, #17, #18, #38, #39는 모두 `main`에 있다(이슈 #19 댓글 "선행 작업 … 수용"). 이 계약서는 `origin/main`
  `5645d02`를 읽고 썼다.
- **이 태스크는 테스트와 그 실행 단계만 더한다.** 흐름이 지나는 화면은 모두 수용되었다: 로그인(T#6), 직원 목록(T#13), 프로젝트
  목록(T#15), 프로젝트 상세(T#16), 배치 화면(T#17), 대시보드(T#18), 직원 상세(T#38). 그래서 흐름의 업무 단언은 처음부터 통과할
  것으로 본다. 레드는 이 태스크가 만드는 것(흐름을 새 DB로 돌리는 단계, 스크린샷의 실행별 DB)이 없을 때 나온다(기준 1, 7). 흐름이
  결함을 찾으면 이 태스크에서 앱을 고치지 않고 멈추고 보고한다.
- **새 DB.** 흐름은 `scripts/e2e-servers.sh --fresh-db`(T#39)가 실행마다 새로 만드는 `.nexi-tmp/e2e-write.db`로 띄운 앱에서만 돈다.
  기존 `e2e-write` 단계와 DB를 함께 쓰지 않는다: 그 단계의 `write/employee-write.spec.ts`가 최동훈을 `투입 가능`으로 바꾸고("makes
  최동훈 투입 가능") 박소영의 직무·기술을 고쳐, 같은 DB에서는 흐름이 파일 순서에 기대게 된다. 그래서 흐름은 자기 Playwright 프로젝트
  `e2e-flow`(`testMatch: 'flow/*.spec.ts'`)와 `test:e2e`의 세 번째 단계 `bash ../scripts/e2e-servers.sh --fresh-db -- npm run e2e:flow`로
  돈다 (제안). 공유 DB 단계의 `e2e` 프로젝트는 `testIgnore`에 `'**/flow/**'`를 더한다.
- **시드 값.** `SeedRunner`는 날짜를 DB를 만든 날 `T` 기준으로 만든다. 2026-10-14 작업 트리 밖 임시 폴더에서 `5645d02`로 빌드한
  백엔드를 빈 DB로 띄워(시드가 들어감) `project.manager`로 API를 불러 확인했다(그 폴더는 지웠다):
  - 직원 20명, 프로젝트 5개, 부서 3개. 박소영: `투입 가능`, 알파 60%(`T−20 ~ T+40`), 현재 가용률 40%. 최동훈: `투입 불가`, 베타
    40%(`T−10 ~ T+30`), 확인 필요.
  - 베타 프로젝트: `진행 중`, `T−20 ~ T+60`, 배치 인력 3명(안유진, 임도윤, 최동훈), "필요 2명 / 배치 3명", 목록의 배치 인원 3.
  - 대시보드: 직원별 가용률 박소영 40%, 부서별 평균 가용률 개발팀 70.6%.
  - 박소영을 베타에 `T ~ T+30` 30%로 배치(201): 현재 가용률 10%, 같은 기간 후보 API 가용률 10%, 베타 배치 인원 4, 대시보드 박소영
    10%·개발팀 66.9%. 원문 §7 "정상 배치"(60% + 30% → 총투입률 90%, 가용률 10%)와 같다.
  - 이어서 박소영 베타 `T+31 ~ T+40` 50% → 400 `ASSIGNMENT_OVER_ALLOCATED` "대상 기간에 투입률 합계가 100%를 초과합니다."(알파 60% +
    50% = 110%, §7 "투입률 초과". 베타 30% 배치와 기간이 겹치지 않아 D27과 섞이지 않는다). 최동훈 베타 20% → 400
    `ASSIGNMENT_EMPLOYEE_UNAVAILABLE` "투입 불가 직원은 새 배치를 받을 수 없습니다.". 둘 다 저장되지 않았다.
  - 그 배치를 해제(204)하면 위 값이 모두 배치 전으로 돌아왔다(40%, 3명, 40%, 70.6%).
- 날짜는 하드코딩하지 않는다. `T`는 `GET /api/employees/<박소영 id>`의 `today`이고, 기간은 `frontend/e2e/support/assign.ts`의 `addDays`로
  만든다. 직원·프로젝트는 이름으로 찾는다(T#17과 같다).
- 근거: REQ-CONTEXT D2, D3, D7, D8, D9, D10, D18, D19, D29, D31, D33, D34, D36, D38, 원문 §7과 §10.
- **권한(D9, D25).** 흐름은 `project.manager`로 한다: 직원·프로젝트·대시보드 조회는 관리자 모두, 배치·해제는 프로젝트 관리자다. 이
  태스크는 권한 규칙과 화면의 역할 처리를 바꾸지 않는다. 서버가 범위 밖 요청(인력 관리자의 `POST`·`DELETE /api/assignments`, 직원
  역할의 조회)을 막는 것은 T#6 `AuthorizationPolicyTest`(`backend/src/test/java/com/ax/rms/security/AuthorizationPolicyTest.java:66-68`의
  배치 줄 포함)가 `make test`에서 회귀로 검사한다.
- `make`가 없는 환경에서는 Makefile의 각 줄을 같은 명령으로 실행해 증거에 적는다.

## 흐름

너비(`W` = 1280, 360)마다 테스트 하나다. 처음 `page.goto('/login')` 한 번 뒤로는 메뉴와 링크로만 이동한다(다시 불러온 값은 화면이
요청해 받은 값이다, D36). 단언의 값은 그 순간 같은 세션의 API 값과 같고, 아래 숫자(시드 값)와도 같다. 화면마다
`expectNoHorizontalOverflow(page, [W])`(D34).
