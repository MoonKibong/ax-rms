# T#17 프로젝트 인력 배치 화면

## 산출물

프로젝트 관리자가 `/projects/<id>/assign`에서 배치 기간을 정해 후보 직원의 기간 가용률을 보고, 한 명을 골라 일정 간트를 확인한 뒤 5% 단위 투입률로 배치하고, 현재 배치를 수정하거나 확인 대화상자를 거쳐 해제할 수 있으며, 서버가 돌려준 위반 원인이 관련 입력 아래에 보이고 저장 뒤 화면이 다시 불러온 값을 보이는 화면.

## 작업량

이슈 #17 그대로 하나로 한다. 예상 약 11.5시간이라 하루를 넘는다(PM 확인: 이 크기를 그대로 둔다, 이슈 #17 댓글). 더 나눈다면 "후보 조회·선택·배치 폼"(기준 1–3, 6의 앞부분, 7–9의 배치 부분)과 "현재 배치 수정·해제"(기준 4–5)로 나누는 것이 자연스럽다. 나누려면 PM이 `nexi-backlog split 17`로 나눈다.

## 화면 동작

### 라우트와 역할

| 경로 | 비로그인 | 직원만 | 인력 관리자만 | 프로젝트 관리자·겸임 |
|---|---|---|---|---|
| `/projects/:id/assign` (`:id` 양의 정수) | `/login` | `/me` | `/projects/:id`로 (제안) | 배치 화면 |

- `:id`가 양의 정수가 아니면 `/`로 돌아간다(`/projects/abc/assign`, `/projects/0/assign`). 없는 프로젝트(404)는 상세와 같은
  "프로젝트를 찾을 수 없습니다"와 "프로젝트 목록" 링크다. 돌려보낼 때는 어떤 `/api/*` 요청도 보내지 않는다.
- 인력 관리자만의 계정이 이 경로를 열면 읽기만 하는 상세로 돌려보낸다(T#16 상세가 "인력 배치"를 이 역할에 보이지 않는 것과 같은 규칙).

### 순서 (BRIEF 6.7, 넓은 구간과 좁은 구간 모두 한 열)

① 프로젝트 요약: 프로젝트명(h1), 기간 `YYYY-MM-DD ~ YYYY-MM-DD`(T#15의 `Period`), "프로젝트 상세" 링크(`/projects/<id>`). ② 배치 기간:
시작일·종료일 날짜 입력 둘(`type="date"`, 처음 값은 프로젝트 기간 `(제안)`). ③ 후보 직원 표: 이름 · 부서 · 기술 · 상태 · 기간 가용률.
④ 선택한 직원의 일정 간트. ⑤ 투입률 입력과 primary "배치". ⑥ 현재 배치 목록: 직원 · 기간 · 투입률 · "수정" · danger "해제".

- **후보 표.** 후보 API와 직원 목록 API를 `employeeId`로 합친다. 이름은 선택 버튼(`aria-pressed`, 접근 이름은 직원 이름)이고, 부서는
  `departmentName`, 기술은 "Java 중급, React 초급"처럼 `skills`를 쓴 그대로, 상태는 `Badge` 같은 글자 "투입 가능"/"투입 불가", 기간
  가용률은 `60%`(끝 정렬, 공백 없음, BRIEF 5절). 같은 직원이 이 프로젝트에 이미 배치돼 있어도 보인다(중복은 서버 규칙 D27이 막는다).
  기간 가용률이 0%이거나 투입 불가인 직원도 보인다: 그 직원을 골라 배치할 때 서버 원인(D8)을 화면이 보여 주는 것이 D33의 확인이다.
  표는 `DataTable`(좁은 구간에서 카드).
- **후보 필터(`no-results`).** 표 위에 이름 검색 입력 하나(`(제안)`, 클라이언트에서 이름에 포함 여부로 거른다). 결과가 없으면
  `StateMessage` `no-results`와 "필터 초기화".
- **간트.** 후보 표에서 직원을 고르면 `GET /api/employees/<id>`를 불러 그 직원의 배치 전부를 T#12 `Gantt`로 그린다(`today`는 응답의
  `today`). 선택하기 전에는 "직원을 선택하면 일정이 보입니다" 안내(제안)를 보인다.
- **투입률 입력.** 숫자 입력(`step=5`, `min=5`, `max=100`, BRIEF 3.2), 라벨 "투입률(%)", 처음 값은 비어 있다. "배치"는 직원을 고르기
  전에는 `disabled`다.
- **입력 단계 검사(D14).** 보내기 전에 투입률이 비었거나, 5~100의 정수가 아니거나, 5의 배수가 아니면 요청을 보내지 않고 투입률 아래에
  "투입률은 5~100의 5 단위로 입력하세요."(서버와 같은 문장)를 보인다. 시작일·종료일이 비었거나 시작일이 늦으면 요청을 보내지 않고 기간 아래에
  "시작일은 종료일보다 늦을 수 없습니다."/"시작일과 종료일을 입력하세요."(서버와 같은 문장)를 보인다.
- **위반 메시지(D33, BRIEF 6.7).** 서버 `message` 그대로, 원인과 관련된 입력 아래.
  - 투입률 아래: `ASSIGNMENT_INVALID_PERCENT`, `ASSIGNMENT_OVER_ALLOCATED`.
  - 기간 아래: `ASSIGNMENT_REQUEST_INVALID`, `ASSIGNMENT_OUT_OF_PROJECT_PERIOD`.
  - "배치" 버튼 위(오류 메시지 블록, `role="alert"`): `ASSIGNMENT_EMPLOYEE_UNAVAILABLE`, `ASSIGNMENT_NO_AVAILABILITY`, `ASSIGNMENT_OVERLAP`,
    `ASSIGNMENT_MODIFY_FORBIDDEN_UNAVAILABLE`, 그리고 `ASSIGNMENT_NOT_FOUND`·그 밖의 `{code,message}`.
  - 메시지는 입력 바로 아래(간격 4px 이내)에 위험 색과 경고 아이콘으로 보이고, 입력은 `aria-invalid`와 `aria-describedby`를 가진다(T#4
    `TextField`의 `error` 규칙). 값을 바꾸면 그 입력의 메시지가 사라진다.
  - 응답이 `{code,message}`가 아니거나 네트워크 오류면 버튼 위에 "저장하지 못했습니다. 잠시 후 다시 시도하세요."(제안)를 보이고 입력은
    그대로 둔다.
- **저장(D36).** "배치"는 `POST /api/assignments`를 한 번 보낸다(처리 중에는 loading, 같은 클릭을 다시 눌러도 요청은 하나다). 201이면 폼의
  투입률을 비우고, 프로젝트(현재 배치 목록)·후보 표·선택한 직원의 간트를 **다시 불러온다**(화면이 값을 계산해 바꾸지 않는다).
- **현재 배치 목록.** 프로젝트 API의 `assignments`를 `DataTable`로: 직원(링크 `/employees/<employeeId>`) · 기간 · 투입률(`60%`, 끝 정렬)
  · "수정" · danger "해제". 없으면 `StateMessage` `empty` "배치된 직원이 없습니다"(T#16과 같은 글자).
- **수정.** 행의 "수정"은 그 직원을 선택하고 배치 기간·투입률 입력에 그 배치의 값을 채우며, 폼 안내를 "<직원> 배치 수정"으로, 주 버튼을
  "수정 저장"으로 바꾸고 secondary "취소"를 둔다. "수정 저장"은 `PATCH /api/assignments/<assignmentId>`로 바뀐 값만(`allocationPercent`,
  `startDate`, `endDate` 중) 보낸다. 성공(200)이면 위 저장과 같이 다시 불러오고 수정 모드를 끝낸다. 위반 메시지의 자리는 배치와 같다.
  수정 모드에서는 후보 표의 다른 직원을 골라도 수정 대상이 바뀌지 않는다(수정 대상은 행이 정한다). "취소"를 누르면 폼을 비우고 배치
  모드로 돌아간다.
- **해제(D28·D29).** 행의 danger "해제"는 `Dialog`를 연다(BRIEF 3.6 "확인 대화상자"): 제목 "배치 해제", 대상 줄 "<직원> · <프로젝트> ·
  <기간> · <투입률>", secondary "취소", danger "해제" 순서. "해제"는 `DELETE /api/assignments/<assignmentId>`를 한 번 보낸다(처리 중에는
  loading이고 Esc는 닫지 않는다). 204면 대화상자를 닫고 위처럼 다시 불러온다. 실패하면 대화상자 안에 서버 메시지를 보이고 열어 둔다.
  브라우저 `confirm`은 쓰지 않는다.
- **불러오는 중·오류.** 처음 프로젝트를 불러오는 동안 "불러오는 중…"과 그 영역 `aria-busy="true"`, 실패하면 `StateMessage` `error`와
  "다시 시도". 후보 표는 자기 영역만 불러오는 중·오류(`StateMessage` `error`, "다시 시도")를 따로 가진다. 후보 표가 비면(후보 API가 빈
  배열) `StateMessage` `empty` 제목 "이 기간에 투입 가능한 직원이 없습니다"(BRIEF 6.7).
- **겹친 요청.** 기간을 바꾸면 이전 후보 요청을 취소하고 늦게 온 이전 응답은 버린다. 후보 표를 다시 불러오는 동안은 이전 표에 `aria-busy`를
  둔다. 선택을 바꾸면 이전 직원의 간트 요청을 취소한다.
- **너비(BRIEF 6.7, 7절).** 두 구간 모두 한 열이다. 후보 표와 현재 배치 목록은 1024px 이상에서 표, 미만에서 카드다. 간트는 화면 너비다.
  1280, 1024, 1023, 360px에서 가로 넘침이 없다. 공백 없는 48자 이름·부서·기술이 칸·카드·간트 안에서 줄바꿈된다.

## 수용 기준

1. **API 모듈과 라우트.** `api/assignments.ts`에 후보·배치 타입이 있고, `/projects/:id/assign`이 `ManagerOnly` 아래에 있다. `:id`가 양의
   정수가 아니면 `/`로, 인력 관리자만의 계정은 `/projects/:id`로, 비로그인은 `/login`, 직원만은 `/me`로 간다. 이 돌려보냄에는
   `/api/*` 요청이 없다. 기존 `/projects/:id`, `/projects/new` 같은 경로의 동작(T#16)은 그대로다.
   - 확인: Vitest `AppRoutes.assign.test.tsx`(`MemoryRouter`, 가짜 `fetch`로 요청 기록).
   - 준비: `null`을 그리는 `ProjectAssignPage` 스텁과 라우트 없음. 레드: `/projects/1/assign`이 배치 화면이 아니라 `/`로 돌아가 실패한다.
2. **보기: 요약·후보 표·간트·현재 배치.** 가짜 응답으로 순서 ①–⑥이 DOM 순서대로 그려지고, 후보 표의 열·값(부서, 기술, 상태, `60%`), 선택
   버튼의 `aria-pressed`, 선택 뒤 간트와 `GET /api/employees/<id>` 한 번, 현재 배치 목록의 값·링크·`수정`·`해제`가 보인다. 기간을 바꾸면
   후보 요청이 그 기간으로 한 번 더 나간다.
   - 확인: Vitest `ProjectAssignPage.test.tsx`(가짜 `fetch`, `MemoryRouter`, `AuthContext`). 준비·레드: 기준 1과 같다.
3. **배치와 위반 메시지(D8, D14, D33).** 투입률을 5의 배수가 아니게 입력하면 요청 없이 투입률 아래에 문장이 보인다. 서버가 돌려준 코드마다
   메시지가 정해진 자리에 보인다(투입률 아래 2종, 기간 아래 2종, 버튼 위 4종과 그 밖). 성공하면 요청 본문이
   `{employeeId, projectId, startDate, endDate, allocationPercent}`이고, 폼이 비워지며 프로젝트·후보·간트 요청이 다시 나간다. 응답을 붙잡은
   동안 같은 클릭을 다시 눌러도 `POST`는 하나다.
   - 확인: Vitest `ProjectAssignPage.test.tsx`(요청을 붙잡았다가 풂, 코드별 응답).
4. **수정(D28).** "수정"이 값을 채우고 "수정 저장"과 "취소"를 보이며, `PATCH`가 바뀐 값만 보낸다. 성공 시 다시 불러오고 배치 모드로 돌아간다.
   `ASSIGNMENT_MODIFY_FORBIDDEN_UNAVAILABLE`은 버튼 위에 보인다.
   - 확인: Vitest `ProjectAssignPage.test.tsx`.
5. **해제 확인 대화상자.** "해제"가 `role="dialog"`(제목 "배치 해제", 대상 줄)를 열고, "취소"는 요청 없이 닫고, "해제"는 `DELETE` 한 번을 보내
   204면 닫고 다시 불러오며, 실패하면 대화상자 안에 메시지를 보이고 열어 둔다. 처리 중에는 loading이고 Esc가 닫지 않는다.
   - 확인: Vitest `ProjectAssignPage.test.tsx`.
6. **상태와 겹친 요청.** 불러오는 중, 프로젝트 오류·404와 다시 시도, 후보 표의 오류·`empty`·`no-results`(필터 초기화), 기간을 바꿀 때 늦게 온
   이전 후보 응답이 무시됨, 선택을 바꿀 때 이전 간트 요청 취소.
   - 확인: Vitest `ProjectAssignPage.test.tsx`(응답 지연).
7. **모양과 값 (e2e, 실제 시드, 읽기만).** `frontend/e2e/projects-assign.spec.ts`. 1280px와 360px: `project.manager`로 상세에서 "인력 배치"를
   눌러 `/projects/<id>/assign`에 간다. h1 "알파 프로젝트", 후보 표(데스크톱은 표, 360px는 카드), 박소영과 최동훈이 후보에 있고 최동훈의 상태가
   "투입 불가", 박소영을 고르면 간트가 보인다. 현재 배치 목록 세 줄(권지안, 강민재, 박소영). 인력 관리자만의 계정(`hr.manager`)으로 열면
   상세로 돌아간다. 이 검사는 실제 서버에 쓰기 요청을 보내지 않는다.
   - 확인: Playwright `frontend/e2e/projects-assign.spec.ts`. 준비: 라우트·화면 스텁. 레드: h1 "알파 프로젝트"가 없어 `toHaveCount(1)` 단언이 실패한다.
8. **위반 메시지의 자리와 모양 (e2e, 고정 응답).** 가로챈(`page.route`) 응답으로 투입률 아래(100% 초과)·기간 아래(프로젝트 기간 밖)·버튼
   위(투입 불가) 메시지를 각각 만들고, 메시지가 해당 입력 바로 아래(간격 ≤ 4px)와 버튼 위에 있으며 글자가 위험 색(`rgb(191, 43, 27)`)임을 잰다.
   1280px와 360px. 48자 이름·부서·기술이 넘치지 않고 1280/1024/1023/360px에서 가로 넘침이 없다.
   - 확인: Playwright `projects-assign.spec.ts`(`expectNoHorizontalOverflow`). 준비·레드: 기준 7과 같다.
9. **실행별 임시 DB의 실제 저장·재조회 (e2e 저장, D8, D14, D27, D28, D33, D36).** `frontend/e2e/write/assignment-write.spec.ts`(`beforeAll`에서
   `E2E_DB === 'fresh'` 확인, `serial`)를 `scripts/e2e-servers.sh --fresh-db -- npm --prefix frontend run e2e:write`로 돌린다(공유 DB `backend/data/e2e.db`에는 쓰지
   않는다). 베타 프로젝트의 배치 화면에서 `project.manager`로, 기간은 API가 준 `today`(`GET /api/employees/<id>`)와 프로젝트 기간에서 정한다(박소영의 알파 배치와
   베타 프로젝트 기간이 겹치는 날). 후보 표의 가용률은 고른 기간의 `periodAvailability`(D18)이므로, 단언은 **같은 기간으로 부른
   `GET /api/assignments/candidates?projectId=&startDate=&endDate=`의 그 직원 `periodAvailability`와 같은 수**인지로 한다(`currentAvailability`(오늘 가용률)와 비교하지 않는다):
   (a) 박소영(알파 60%)을 50%로 배치 → 투입률 아래에 서버 메시지 "대상 기간에 투입률 합계가 100%를 초과합니다."; 저장되지 않음(그 직원의 `GET /api/employees/<id>`
   `assignments`에 베타 배치가 없음); (b) 투입률을 30%로 고쳐 다시 "배치" → 현재 배치 목록에 박소영의 베타 30%, 후보 표의 박소영 기간 가용률이 그 기간의 후보 API 값과
   같음(배치 전보다 낮아짐), `page.reload()` 뒤에도 같음; (c) 그 배치를 "수정"해 40%로 → 목록 40%, 후보 표의 값이 다시 후보 API 값과 같음; (d) 최동훈(투입 불가)을 골라 배치
   → 버튼 위 "투입 불가 직원은 새 배치를 받을 수 없습니다.", 저장되지 않음; (e) 박소영의 베타 배치를 "해제" → `Dialog`("배치 해제")를 거쳐 목록에서 사라지고, 후보 표의
   박소영 기간 가용률이 같은 기간의 후보 API 값과 같으며 그 값이 (a) 시작 전의 값과 같음.
   - 확인: Playwright `e2e-write` 프로젝트. 준비: 스펙만 둔다. 레드: 배치 화면이 없어 (a)의 첫 단언(`getByRole('heading', …)`)이 실패한다.
10. **스크린샷 (D33, D34, D35, D36).** `make screenshots T=17`이 `docs/screens/T17/`에 전체 페이지로 저장한다: `assign-1280.png`,

    - 확인: `frontend/e2e/screens/T17.spec.ts`, `make screenshots T=17; echo $?`가 0이고 PNG 6장이 있다.
    - 준비·레드: 스펙을 만든 뒤 배치 화면 제목이 없어 단언이 실패하고 PNG가 생기지 않는 것이 레드다.

## 격리

- 읽기 e2e와 스크린샷은 T#4의 `scripts/e2e-servers.sh`와 README "검사 격리" 표를 그대로 쓴다(백엔드 18080, 공유 DB `backend/data/e2e.db`,
  프런트엔드 14173, 서버 기록 `.nexi-tmp/e2e-servers.pids`). **공유 DB에는 읽기 요청만 보낸다.** 위반 메시지와 해제 대화상자의 모양은
  브라우저 안의 `page.route`로 가로챈 응답으로 만든다.
- 저장 e2e(기준 9)는 `--fresh-db`의 `<저장소>/.nexi-tmp/e2e-write.db`(실행마다 새로 만들고 끝나면 지운다)로만 쓴다. 이 태스크는 그 스크립트, `e2e-write` 설정, README "검사 격리" 표를 고치지 않는다. 모든 e2e 실행이 같은 잠금을 쓰므로 읽기·저장·스크린샷 실행을 차례로 돌린다.
- 외부 네트워크를 쓰지 않는다(D40). 기계별 설치 경로나 PATH 설정을 쓰지 않는다.

## 하지 않을 일

- 백엔드 변경, 새 API. 후보 API(T#10)와 직원 목록 API(T#13)를 합쳐 후보 표를 만든다. 서버에 부서·기술을 후보 응답에 넣는 변경은 하지 않는다.
- 권한 규칙 변경. 서버가 배치 쓰기를 프로젝트 관리자에게만 허용하는 것은 #6이 이미 한다.
- `Dialog`와 `SelectField`를 이 태스크에서 만들거나 고치는 일(→ #39). 이 화면은 `main`의 `Dialog`를 쓰기만 한다. `--fresh-db` 스크립트와 `e2e-write` 설정도 고치지 않는다.
- 프로젝트 등록·수정 폼(→ #34), 직원 상세·등록·수정(→ #38·#39), 대시보드(→ #18), "인력 부족"·"부족한 역량" 표시(→ #32, D20·D36).
- 배치 추천·자동 배치, 여러 직원 한 번에 배치, 배치 이력, 프로젝트 필요 역량에 맞춘 후보 정렬·적합도 점수. 후보는 서버 응답 순서를 그대로 쓴다.
- 가로챈 응답으로 만든 스크린샷을 실제 저장의 증거로 쓰는 일(저장은 기준 9가 증명한다).
- 스크린샷 픽셀 비교 자동화. 스크린샷은 리뷰어가 BRIEF와 대조한다.
