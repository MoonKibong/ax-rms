## 오류 처리 기준

### 예외

1. 업무 규칙 위반과 없는 리소스는 `com.ax.rms.web.ApiException(HttpStatus status, String code, String message)` 하나로 던진다. 패키지별 예외 클래스를 새로 만들지 않는다.
2. `EmployeeApiException`, `ProjectException`, `AssignmentRuleException`, `AssignmentNotFoundException`을 지우고 `ApiException`으로 바꾼다. 상태·코드·메시지는 지금 값 그대로다(`AssignmentRuleException`은 400, `AssignmentNotFoundException`은 404).
3. `@RestControllerAdvice`는 `com.ax.rms.web`에 하나만 둔다. `EmployeeApiExceptionHandler`, `ProjectApiErrorHandler`, `AssignmentApiErrorHandler`를 지운다. 컨트롤러 안의 `@ExceptionHandler`는 두지 않는다. 단 하나의 예외를 둔다: `AuthController`의 읽을 수 없는 로그인 본문 → 400 `AUTH_INVALID_REQUEST`(T#6 계약, 빈 값과 같은 응답).

### 오류 응답

4. 모든 `/api/**` 오류 응답의 본문은 키가 `code`, `message` 둘뿐이다. `message`는 한국어이고 예외 클래스 이름·스택·SQL·내부 경로를 담지 않는다.
5. 전역 처리기(`ResponseEntityExceptionHandler`를 확장)는 아래 표대로 답한다. 같은 잘못된 요청은 API가 달라도 같은 응답이다.

   | 원인 | 상태 | code | message |
   |---|---|---|---|
   | `ApiException` | 예외의 값 | 예외의 값 | 예외의 값 |
   | 읽을 수 없는 본문(깨진 JSON, 틀린 타입), 형식이 틀린 경로·질의 값(숫자 자리에 글자, 없는 enum 값, 틀린 날짜), 빠진 필수 질의 값 | 400 | `REQUEST_INVALID` | 요청 형식이 올바르지 않습니다. |
   | 지원하지 않는 `Content-Type` | 415 | `UNSUPPORTED_MEDIA_TYPE` | 요청 본문은 JSON으로 보내야 합니다. (지금과 같음) |
   | 없는 경로(`NoResourceFoundException`) | 404 | `NOT_FOUND` | 요청한 주소를 찾을 수 없습니다. |
   | 지원하지 않는 메서드 | 405 | `METHOD_NOT_ALLOWED` | 지원하지 않는 요청 방식입니다. (`Allow` 헤더 유지) |
   | `SQLITE_BUSY`(원인 사슬에 `org.sqlite.SQLiteException`의 결과 코드가 BUSY 계열) | 409 | `DB_BUSY` | 다른 작업이 처리 중입니다. 잠시 후 다시 시도하세요. |
   | 그 밖의 처리 안 된 예외 | 500 | `INTERNAL_ERROR` | 서버 오류가 발생했습니다. 잠시 후 다시 시도하세요. |

6. 위 표에 없는 Spring MVC 표준 예외도 `ResponseEntityExceptionHandler`가 정한 상태를 지키고 본문만 `{code,message}`로 바꾼다(코드는 상태에서 정한다: 406 `NOT_ACCEPTABLE`, 그 밖의 4xx는 `REQUEST_INVALID`).
7. `AccessDeniedException`·`AuthenticationException`은 전역 처리기가 삼키지 않고 보안 설정(`ApiSecurityFilterChain`)이 답하게 다시 던진다. 401 `AUTH_REQUIRED`, 403 `AUTH_FORBIDDEN`은 지금과 같다.
8. 요청 record는 필수 값에 원시 타입(`long`, `int`)을 쓰지 않고 래퍼 타입을 쓴다. 빠진 값은 서비스가 그 API의 요청 오류 코드로 400을 답한다(0으로 읽어 엉뚱한 오류가 나지 않게).
9. 목록 안의 `null` 요소는 그 목록의 항목 오류 코드로 400이다(`skills`의 `null` → `EMPLOYEE_SKILL_INVALID`).
10. 인증 중 저장소 오류는 401로 가리지 않는다. 틀린 계정·비밀번호만 401 `AUTH_INVALID_CREDENTIALS`다. 내부 오류는 위 표의 500(또는 `SQLITE_BUSY`면 409)이다.
11. 로그: 500은 `ERROR`로 예외와 스택을 남기고, 409 `DB_BUSY`는 `WARN`으로 한 줄 남긴다. 4xx 업무 오류는 로그를 남기지 않는다(쓰기 감사·규칙 위반 로그는 이 태스크 범위 밖이다).

### 트랜잭션

12. 한 요청에서 쓰기를 둘 이상 하는 서비스 메서드는 `@Transactional`이다. 읽기 전용 서비스는 필요할 때 `readOnly`를 쓴다.
13. 이 태스크는 이 규칙만 적고 코드는 바꾸지 않는다. 직원 등록·수정·상태 변경과 시드에 규칙을 적용하는 일은 #54가 한다.
14. 트랜잭션 안에서 던진 `ApiException`은 롤백된다(런타임 예외 기본 동작).

### API 클라이언트 (프런트엔드)

15. 서버 오류 본문 `{code,message}`를 읽는 일은 `frontend/src/api`의 한 곳에서 한다(새 코드는 호출부마다 복제하지 않는다). 401은 그 한 곳에서 처리한다. 구현은 #55가 한다.
16. 화면은 `message`를 그대로 보이고, `code`는 입력 근처에 붙이는 분기에만 쓴다. 모르는 `code`와 `code`가 없는 응답은 "저장하지 못했습니다. 잠시 후 다시 시도하세요."(T#34와 같은 글자)로 보인다.
17. 이 태스크는 이 규칙만 적고 프런트엔드 코드는 바꾸지 않는다.

## 수용 기준

1. `docs/ENGINEERING.md`가 있고 첫 줄이 `상태: 승인`이며, 절 `## 예외`, `## 오류 응답`, `## 트랜잭션`, `## API 클라이언트`가 있고 위 규칙 1–17이 들어 있다. 패키지 공개 경계·주석·로깅 전반 절은 없다 — 확인: N9
2. `main/java`에 `@RestControllerAdvice` 클래스가 정확히 하나(`com.ax.rms.web`)이고, 예외 4종과 처리기 3개가 없으며, `ApiException`이 있다 — 확인: N8
3. 깨진 JSON을 직원·프로젝트·배치 쓰기 API에 보내면 모두 400 `REQUEST_INVALID`와 같은 `message`다. 직원 목록 `?status=FOO`, `?departmentId=abc`, `GET /api/employees/abc`, `GET /api/projects/abc`, 배치 후보 조회의 빠진 `projectId`와 틀린 날짜도 같다 — 확인: N1
4. 처리 안 된 예외(대시보드 서비스가 던진 `RuntimeException`)는 500 `INTERNAL_ERROR`이고 본문에 예외 클래스 이름·스택이 없으며, `ERROR` 로그에 그 예외가 남는다 — 확인: N2
5. 없는 `/api/**` 경로는 로그인한 상태에서 404 `NOT_FOUND`, `DELETE /api/projects/1`은 405 `METHOD_NOT_ALLOWED`이고 `Allow` 헤더가 있으며, 본문은 둘 다 `{code,message}` 둘뿐이다. 로그인하지 않은 같은 요청은 지금처럼 401 `AUTH_REQUIRED`다 — 확인: N3
6. 다른 연결이 쓰기 잠금을 잡고 있을 때 직원 등록은 409 `DB_BUSY`이고 `WARN` 로그가 남으며, 직원은 만들어지지 않는다. 잠금이 풀린 뒤 같은 요청은 201이다 — 확인: N4
7. `skills`에 `null` 요소가 있는 직원 등록은 500이 아니라 400 `EMPLOYEE_SKILL_INVALID`다 — 확인: N5
8. 배치 생성 본문에서 `employeeId`, `projectId`, `allocationPercent` 중 하나가 빠지면 400 `ASSIGNMENT_REQUEST_INVALID`다(404·`ASSIGNMENT_OVER_ALLOCATED` 등 엉뚱한 오류가 아니다) — 확인: N6
9. 로그인 중 `AccountRepository`가 `DataAccessException`을 던지면 500 `INTERNAL_ERROR`와 `ERROR` 로그이고, 틀린 비밀번호는 그대로 401 `AUTH_INVALID_CREDENTIALS`다 — 확인: N7
10. 지금 동작하는 것은 그대로다(regression): 읽을 수 없는 로그인 본문 400 `AUTH_INVALID_REQUEST`, 415 `UNSUPPORTED_MEDIA_TYPE`, 401·403 본문, 업무 규칙 코드(`EMPLOYEE_*`, `PROJECT_*`, `ASSIGNMENT_*`)와 상태, 모든 기존 백엔드 테스트 — 확인: 회귀 검사
11. 정리 결과를 README의 오류 응답 설명이 반영한다(README 70행의 "Spring 기본 오류 본문" 문장이 없고 표의 코드가 있다) — 확인: N9

## 하지 않을 일

- 패키지 공개 경계(`package-private`), 주석 규칙, 로깅 전반 절은 ENGINEERING.md에 넣지 않는다(회고 3.3절 보류).
- WAL·`busy_timeout`·`transaction_mode`, `@Transactional` 추가, 시드 트랜잭션은 #54가 한다. 이 태스크는 `SQLITE_BUSY`를 409로 바꾸는 변환만 한다.
- 프런트엔드 코드(401 처리, `apiFetch`, 오류 코드 문자열 표시)는 바꾸지 않는다(#55). 프런트 테스트 안의 `PROJECT_REQUEST_INVALID` 모의 응답도 그대로 둔다.
- 쓰기 감사 로그, 규칙 위반 로그, 로그인 실패 로그를 만들지 않는다. CSRF·로그인 시도 제한(B#16), 빈 부서 평균(B#19)은 건드리지 않는다.
- 업무 규칙 오류 코드(`EMPLOYEE_*`, `PROJECT_*`, `ASSIGNMENT_*`)의 값, 상태, 메시지를 바꾸지 않는다. 바뀌는 것은 형식 오류의 코드(`PROJECT_REQUEST_INVALID`, 배치의 형식 오류 `ASSIGNMENT_REQUEST_INVALID` → `REQUEST_INVALID`)뿐이다.
- 입력 길이 제한, Bean Validation 도입, 읽기 전용 트랜잭션 적용은 하지 않는다.

## 화면

해당 없음. 화면을 바꾸지 않으므로 `make screenshots`는 쓰지 않는다. 응답 코드가 바뀌는 요청(깨진 본문)은 화면이 `message`를 그대로 보이므로 사용자에게 보이는 글자가 바뀔 수 있다: 프로젝트 쓰기의 깨진 본문은 "요청 본문을 읽을 수 없습니다." → "요청 형식이 올바르지 않습니다."가 된다. 화면 폼은 정상 입력만 보내므로 시연 흐름(§10)에는 닿지 않는다.
