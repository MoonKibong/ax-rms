# T#8 직원 API

## 산출물

`backend/`에 직원 목록(검색·필터)·상세·등록·수정·상태 변경 REST API가 있고, 상세는 배치 현황·현재 가용률·확인 필요

## 직원 API

### 목록 — `GET /api/employees`

쿼리 매개변수(모두 선택, 조합하면 AND로 적용):

- `name`: 이름에 포함된 문자열(부분 일치).
- `departmentId`: 그 부서 id인 직원만.
- `skill`: 그 기술 이름(숙련도 무관)을 가진 직원만.
- `status`: `AVAILABLE` 또는 `UNAVAILABLE`.
- `minAvailability`: 오늘 기준 현재 가용률(D7, D18, D19)이 그 값 이상인 직원만(경계값 포함, 이상).

응답 200, 배열, 각 항목은 `id` 오름차순으로:

```json
{
  "id": 1, "name": "박소영", "departmentId": 10, "departmentName": "개발팀",
  "jobTitle": "백엔드 개발자", "careerYears": 5,
  "availabilityStatus": "AVAILABLE", "currentAvailability": 40, "needsReview": false
}
```

### 상세 — `GET /api/employees/{id}`

응답 200:

```json
{
  "id": 1, "name": "박소영", "departmentId": 10, "departmentName": "개발팀",
  "jobTitle": "백엔드 개발자", "careerYears": 5,
  "availabilityStatus": "AVAILABLE", "unavailableReason": null, "unavailableUntil": null,
  "currentAvailability": 40, "needsReview": false,
  "skills": [{"skillName": "Java", "proficiencyLevel": "ADVANCED"}],
  "assignments": [
    {"projectId": 2, "projectName": "감마 프로젝트", "projectStatus": "DONE",
     "startDate": "2025-11-27", "endDate": "2026-01-16", "allocationPercent": 30},
    {"projectId": 1, "projectName": "알파 프로젝트", "projectStatus": "IN_PROGRESS",
     "startDate": "2026-05-26", "endDate": "2026-07-25", "allocationPercent": 60}
  ]
}
```

`assignments`는 그 직원의 전체 배치(종료된 프로젝트 포함, D15 간트용)를 `startDate` 오름차순으로 담는다. 없는 id는
404 `{"code": "EMPLOYEE_NOT_FOUND", "message": "직원을 찾을 수 없습니다."}`.

### 등록 — `POST /api/employees`

요청 본문: `{"name", "departmentId", "jobTitle", "careerYears", "skills": [{"skillName", "proficiencyLevel"}]}`.
`skills`는 없으면 빈 배열로 둔다. 새 직원은 항상 `AVAILABLE`로 시작한다(요청에 상태 필드가 있어도 무시).

성공: 201, `Location: /api/employees/{새 id}`, 본문은 상세와 같은 모양(`assignments`는 빈 배열).

검증 실패(모두 400, D33):

| 조건 | code |
|---|---|
| `name`이 비었다 | `EMPLOYEE_NAME_REQUIRED` |
| `jobTitle`이 비었다 | `EMPLOYEE_JOB_TITLE_REQUIRED` |
| `departmentId`가 없거나 그 부서가 없다 | `EMPLOYEE_DEPARTMENT_NOT_FOUND` |
| `careerYears`가 없거나 음수다 | `EMPLOYEE_CAREER_YEARS_INVALID` |
| `skills`에 같은 `skillName`이 두 번 나온다 | `EMPLOYEE_SKILL_DUPLICATE` |
| `skills`의 `skillName`이 비었거나 `proficiencyLevel`이 `BEGINNER`·`INTERMEDIATE`·`ADVANCED`가 아니다 | `EMPLOYEE_SKILL_INVALID` |

### 수정 — `PUT /api/employees/{id}`

요청 본문은 등록과 같다(`name`, `departmentId`, `jobTitle`, `careerYears`, `skills`). `skills`는 요청 배열로 완전히
바꾼다(없던 줄은 더하고, 요청에 없는 줄은 지운다). 투입 상태 관련 필드(`availabilityStatus`,
`unavailableReason`, `unavailableUntil`)는 요청에 있어도 무시한다(D6 — 상태는 전용 API로만 바꾼다).

성공: 200, 본문은 상세와 같은 모양(배치는 바뀌지 않는다). 검증 실패는 등록과 같은 표. 없는 id는 404
`EMPLOYEE_NOT_FOUND`.

### 상태 변경 — `PATCH /api/employees/{id}/status`

요청 본문: `{"availabilityStatus", "unavailableReason", "unavailableUntil"}`.

- `availabilityStatus`가 `UNAVAILABLE`이면 `unavailableReason`이 비어 있지 않아야 한다(D6). 비었으면 400
  `EMPLOYEE_REASON_REQUIRED` "투입 불가 사유를 입력하세요.". `unavailableUntil`은 선택이다(없으면 `null`).
- `availabilityStatus`가 `AVAILABLE`이면 `unavailableReason`과 `unavailableUntil`을 요청에 값이 있어도 항상
  `null`로 바꾼다.
- `availabilityStatus`가 그 둘이 아니면 400 `EMPLOYEE_STATUS_INVALID`.
- 성공: 200, 본문은 상세와 같은 모양. 기존 배치는 하나도 지우거나 바꾸지 않는다(D6).
- 없는 id는 404 `EMPLOYEE_NOT_FOUND`.

### `needsReview` (D21)

`AvailabilityCalculator`에 메서드를 더한다: `needsReview(AvailabilityStatus status, List<Assignment> assignments,
LocalDate today)`. 상태가 `UNAVAILABLE`이고, 그 직원의 배치 중 종료일이 오늘이거나 오늘보다 뒤인 것이 하나라도
있으면 `true`다(D19의 "종료일이 오늘 이전"의 반대로 "오늘 이후"를 정의해 일관성을 맞춘다). 상태가 `AVAILABLE`이면
배치와 무관하게 항상 `false`다.

## 수용 기준

1. **목록 — 기본과 이름 검색 (D2).** 필터 없이 부르면 200, 20건, `id` 오름차순. `name=소영`이면 정확히 `박소영`
   1건.
   - 확인: `EmployeeApiTest`(실제 포트, HTTP 클라이언트, `AbstractSeedTest` 시드).
   - 준비: 테스트 클래스와 HTTP 클라이언트만 둔다.
   - 레드: 처리기가 없어 `GET /api/employees`가 404라 "200이어야 한다" 단언이 실패한다.
2. **목록 — 부서·기술·투입 상태 필터 (D2).**
   - `departmentId`에 "개발팀"의 id(`DepartmentRepository`에서 이름으로 찾음)를 주면 8건이고, `박소영`·`최동훈`·
     `한지우`를 포함하며 `이수민`(기획팀)은 없다.
   - `skill=Java`면 정확히 `박소영`, `한지우` 2건이다(다른 직원은 Java 기술이 없다).
   - `status=UNAVAILABLE`이면 정확히 `최동훈` 1건이다.
   - 확인·준비: 기준 1과 같음. 레드: 404라서 세 가지 모두 "200이어야 한다"나 건수 단언이 실패한다.
3. **목록 — 가용률 필터와 필터 조합 (D2, D7, D18, D19).**
   - `minAvailability=60`이면 15건이고, 경계값인 `최동훈`(현재 가용률 정확히 60)을 포함하며, `박소영`(40)과
     `권지안`(55)은 없다 — 이상(≥) 조건임을 경계로 증명한다.
   - `departmentId=개발팀`과 `status=UNAVAILABLE`을 함께 주면 정확히 `최동훈` 1건이다(두 필터가 AND로 겹친다;
     개발팀은 8명이고 `UNAVAILABLE`인 직원은 `최동훈` 하나뿐이므로, 둘을 AND가 아니라 OR로 처리하면 결과가
     개발팀 전체인 8건이 돼 1건과 구분된다).
   - 확인·준비: 기준 1과 같음. 레드: 404라서 건수 단언이 실패한다.
4. **상세 — 배치 현황과 현재 가용률 (D2, D7, D15).** `박소영`의 id로 상세를 부르면 200, `currentAvailability`
   40, `skills`는 `[{"skillName":"Java","proficiencyLevel":"ADVANCED"}]`, `assignments`는 2건이고 `startDate`
   오름차순으로 "감마 프로젝트"(종료된 프로젝트, 30%)가 "알파 프로젝트"(60%)보다 먼저 온다(종료된 프로젝트도
   배치 현황에는 그대로 나온다 — D15 간트용).
   - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: 404라서 "200이어야 한다" 단언이 실패한다.
5. **상세 — 확인 필요 (D21).** `최동훈`의 상세는 `availabilityStatus` `UNAVAILABLE`, `unavailableReason`
   `"육아휴직"`, `needsReview` `true`다(배치가 "베타 프로젝트"에 남아 있고 그 종료일이 오늘보다 뒤다).
   - 확인: `EmployeeApiTest`. 준비·레드: 기준 4와 같음.
6. **`needsReview` 계산 (D21, 순수 함수).** `AvailabilityCalculatorTest`에 5가지를 더한다.
   - 상태 `UNAVAILABLE`, 배치 종료일이 오늘보다 뒤 → `true`.
   - 상태 `UNAVAILABLE`, 배치 종료일이 오늘과 같음(경계) → `true`.
   - 상태 `UNAVAILABLE`, 배치 종료일이 오늘보다 전 → `false`.
   - 상태 `UNAVAILABLE`, 배치 없음 → `false`.
   - 상태 `AVAILABLE`, 배치 종료일이 오늘보다 훨씬 뒤 → `false`.
   - 확인: `AvailabilityCalculatorTest`.
   - 준비: `needsReview`가 `UnsupportedOperationException`을 던지는 스텁. (참·거짓이 섞인 기댓값이라 상수
     스텁 하나로는 다섯 경우를 모두 틀리게 만들 수 없다 — T#7에서 걸렸던 "스텁이 기댓값과 우연히 같아 레드가
     약해지는" 문제를 피하려고 예외 스텁을 쓴다.)
   - 레드: 다섯 테스트 모두 그 예외로 실패한다(아직 어떤 기댓값과도 일치하는 반환값이 없다).
7. **상세 — 404.** 존재하지 않는 id(예: `999999`)로 상세·수정·상태 변경을 부르면 모두 404
   `EMPLOYEE_NOT_FOUND`.
   - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: 지금은 모든 요청이 404이지만 본문이 없거나
     `{"code","message"}` 형식이 아니라서 "`code`가 `EMPLOYEE_NOT_FOUND`여야 한다" 단언이 실패한다.
8. **등록 (D2).** 유효한 본문으로 등록하면 201, `Location` 헤더가 새 경로를 가리키고, 본문의
   `availabilityStatus`는 `AVAILABLE`이다. 그 뒤 목록을 부르면 21건이고 새 이름이 들어 있다.
   - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: `POST /api/employees`가 404라 "201이어야 한다" 단언이
     실패한다.
9. **등록 — 검증 오류 (D33).** 위 표의 6가지를 각각 보내고 각 `code`를 확인한다(`name` 빈 문자열, `jobTitle` 빈
   문자열, 존재하지 않는 `departmentId`, `careerYears` -1, 같은 `skillName` 두 번, 잘못된 `proficiencyLevel`).
   - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: 404라서 여섯 단언 모두 실패한다.
10. **수정과 상태 필드 무시 (D2, D6).** `박소영`을 수정(예: `careerYears`를 6으로, `skills`를 `[{"skillName":
    "Java","proficiencyLevel":"ADVANCED"}, {"skillName":"Kubernetes","proficiencyLevel":"BEGINNER"}]`로)하면
    200이고 상세를 다시 부르면 그 값이 반영된다. 같은 요청에 `"availabilityStatus":"UNAVAILABLE"`을 더 넣어도
    응답의 `availabilityStatus`는 그대로 `AVAILABLE`이다.
    - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: `PUT`이 404라 "200이어야 한다"와 반영 단언이 실패한다.
11. **상태 변경 — 성공과 배치 유지 (D6).** `박소영`을 상태 변경 전 배치 2건의 내용을 적어 두고, `{"availabilityStatus":
    "UNAVAILABLE", "unavailableReason":"병가", "unavailableUntil":"2026-07-01"}`로 바꾸면 200이고
    `availabilityStatus`·`unavailableReason`·`unavailableUntil`이 그대로 반영된다. 그 뒤 같은 직원의 배치 2건을
    다시 읽으면 건수와 내용(프로젝트·기간·투입률)이 바꾸기 전과 완전히 같다(지우거나 바꾸지 않았다는 증거).
    - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: `PATCH`가 404라 "200이어야 한다" 단언이 실패한다.
12. **상태 변경 — 검증과 복귀 시 초기화 (D6, D33).**
    - 사유 없이 `{"availabilityStatus":"UNAVAILABLE"}`을 보내면 400 `EMPLOYEE_REASON_REQUIRED`.
    - 알 수 없는 상태값(예: `"RETIRED"`)을 보내면 400 `EMPLOYEE_STATUS_INVALID`.
    - 기준 11로 `UNAVAILABLE`이 된 직원에게 `{"availabilityStatus":"AVAILABLE"}`을 보내면 200이고
      `unavailableReason`과 `unavailableUntil`이 둘 다 `null`로 돌아온다.
    - 확인: `EmployeeApiTest`. 준비: 기준 1과 같음. 레드: 404라서 세 단언 모두 실패한다.
13. **오류 형식 공통 (D33).** 기준 7, 9, 12에서 받은 4xx 응답 본문은 모두 키가 정확히 `code`, `message` 둘뿐이고
    `message`는 한국어다(`password`·`passwordHash`처럼 엉뚱한 키가 없다는 것과 같은 종류의 확인).
    - 확인: `EmployeeApiTest`(같은 응답을 재사용해 키 집합을 단언).
14. **회귀.** `make build`, `make test`, `make lint`가 작업 전후 모두 통과한다. 다음은 고치지 않고 통과한다:
    `HealthControllerTest`, `ApplicationStartupTest`(T#3), T#5 백엔드 검사 전부,
    `AvailabilityCalculatorTest`의 기존 9개 테스트(T#7, 기준 6에서 새 테스트만 더한다).
    - 확인: 작업 전 베이스라인 실행과 작업 후 실행을 각각 기록한다.

- 프로젝트·배치 REST API (→ T#9, T#10). 이 태스크는 `assignments`를 상세의 읽기 전용 배치 현황으로만 보여 준다.
- 배치 저장 규칙(D8)과 투입 불가 직원의 배치 수정 제한(D28) — 배치를 만들거나 바꾸는 쪽(T#10)의 몫이다. 이
  태스크의 상태 변경 API는 배치를 전혀 건드리지 않는다(기준 11).
- 역할별 403 검사, 로그인·세션 (→ T#6). 이 API 자체는 요청자의 역할을 확인하지 않는다.
- 대시보드 집계(D5, D20, D23) (→ T#11).
- 직원 삭제, 계정(로그인) 생성·연결 — 요구사항에 없다.
- 목록 페이지네이션 — 직원 20~수백 명 규모라 필요 없다(D2는 그런 요구가 없다).
- 확인 필요(`needsReview`)로 목록을 필터링 — D2의 목록 필터 목록에 없다. 화면에는 보이지만 필터 대상은 아니다.
- 프런트엔드 변경 — 이 태스크는 `backend/`만 건드린다.
- 부서 등록·수정 — D26에 따라 영구히 없음(시드 전용, `DepartmentRepository`는 조회만 쓴다).
