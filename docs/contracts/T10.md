# T#10 배치 API: 배치·투입률 수정·해제와 검증 규칙

## 산출물

`backend/`에 배치 생성·투입률·기간 수정·해제 REST API(`/api/assignments`)와 기간별 후보 직원 가용률 조회 API가 있고, D8·D14·D27·D28 검증 규칙을 적용해 위반마다 원인 코드와 한국어 메시지(`{"code","message"}`, D33)를 돌려주며, §7의 여섯 시나리오가 자동 테스트로 통과한다.

## 설계 (계약서 수준)

T#5의 `AssignmentRepository`·`EmployeeRepository`·`ProjectRepository`와 T#7의 `AvailabilityCalculator`(순수 계산)를 그대로 재사용한다. 새 테이블·새 저장소 메서드는 만들지 않는다. 테스트는 T#5의 임시 DB + 고정 `Clock` 인프라(`AbstractSeedTest`, "오늘" = 2026-06-15)를 쓴다.

인증·권한 검사는 이 태스크에서 구현하지 않는다 — T#6의 서버 보안 설정(한 곳, 경로·메서드)이 적용한다(PM 결정, 이슈 #10 댓글 2026-10-13). 경로는 T#6 권한 표의 `/api/assignments/**` 아래에 둔다(새 경로 없음, 표 변경 없음). 테스트는 T#6의 로그인 도우미(`AbstractApiTest` + `ApiClient.login`)로 데모 계정 `project.manager`로 로그인해 부른다(PM 결정, 이슈 #10 댓글 2026-10-13). 역할별 403 검사는 T#6의 `AuthorizationPolicyTest`가 맡는다.

### 엔드포인트

- `POST /api/assignments` — 본문 `{"employeeId", "projectId", "startDate", "endDate", "allocationPercent"}`. 성공: 201, 본문은 생성된 배치(`id` 포함).
- `PATCH /api/assignments/{id}` — 본문 `{"allocationPercent", "startDate", "endDate"}`의 부분 집합(준 것만 수정). 성공: 200, 본문은 수정된 배치.
- `DELETE /api/assignments/{id}` — 해제. 성공: 204.
- `GET /api/assignments/candidates?projectId=&startDate=&endDate=` — 기간의 후보 직원 목록. 성공: 200, `[{"employeeId","name","availabilityStatus","periodAvailability"}]`. `periodAvailability`는 T#7 `periodAvailability`의 그 기간 값(100 − 최저일 총투입률, D18).

### 검증 규칙 (순서대로 검사)

| 규칙 | 조건 | 상태 | 원인 코드 |
|---|---|---|---|
| D14 | 투입률이 5~100이 아니거나 5단위가 아님 | 400 | `ASSIGNMENT_INVALID_PERCENT` |
| 존재 | POST: 직원이 없음 | 404 | `ASSIGNMENT_EMPLOYEE_NOT_FOUND` |
| 존재 | POST: 프로젝트가 없음 | 404 | `ASSIGNMENT_PROJECT_NOT_FOUND` |
| 존재 | PATCH·DELETE: 배치가 없음 | 404 | `ASSIGNMENT_NOT_FOUND` |
| D8 | 신규 배치인데 직원 상태가 투입 불가 | 400 | `ASSIGNMENT_EMPLOYEE_UNAVAILABLE` |
| D8 | 대상 기간의 가용률(D18)이 0% | 400 | `ASSIGNMENT_NO_AVAILABILITY` |
| D8 | 저장·수정 후 대상 기간의 어느 날도 100% 초과(수정은 자기 자신 제외) | 400 | `ASSIGNMENT_OVER_ALLOCATED` |
| D8 | 배치 기간이 프로젝트 기간 안에 아님 | 400 | `ASSIGNMENT_OUT_OF_PROJECT_PERIOD` |
| D27 | 같은 직원·같은 프로젝트에 기간이 겹치는 배정이 있음(수정은 자기 자신 제외) | 400 | `ASSIGNMENT_OVERLAP` |
| D28 | 투입 불가 직원의 수정이 투입률을 높이거나 기간을 늘림 | 400 | `ASSIGNMENT_MODIFY_FORBIDDEN_UNAVAILABLE` |

- 규칙 위반은 400, 없는 리소스는 404. 본문은 항상 `com.ax.rms.web.ApiError`(`{"code","message"}`, D33)이고 메시지는 한국어.
- 이 태스크가 예외 처리기를 두면 범위를 `basePackages`로 한정하고, `ApiErrorHandler`가 이미 다루는 예외(`HttpMediaTypeNotSupportedException` → 415 `UNSUPPORTED_MEDIA_TYPE`)는 다루지 않는다. 둘 다 다뤄야 하는 예외가 생기면 `@Order`로 우선순위를 명시한다.
- D28: 투입 불가 직원은 투입률 하향·기간 축소·해제만 허용한다.
- 수정은 직원 투입 가능 여부와 무관하게 "수정 후" 상태에 D14, D8(자기 자신 제외: 어느 날도 100% 초과 금지, 프로젝트 기간 안), D27(자기 자신 제외)를 적용한다.

## 수용 기준

모든 API 테스트는 시드 데이터(`AbstractSeedTest`)를 쓰고, 직원·프로젝트 ID는 저장소에서 이름·조건으로 찾아 숫자를 하드코딩하지 않는다.

1. **정상 배치**: E1(박소영, P1 알파에 60% 보유)를 P3(베타)에 30%로 `[2026-06-15..2026-06-25]` 배치 → 201, 본문 `allocationPercent`=30, `id`가 null이 아님 — 확인: `AllocationCreateTest.normalAllocation`.
2. **D14**: 투입률 0, 3, 7, 105 각각 POST → 400 `ASSIGNMENT_INVALID_PERCENT` — 확인: `AllocationCreateTest.invalidPercent`.
3. **존재(404)**: 없는 직원 ID로 POST → 404 `ASSIGNMENT_EMPLOYEE_NOT_FOUND`. 없는 프로젝트 ID로 POST → 404 `ASSIGNMENT_PROJECT_NOT_FOUND`. 없는 배치 ID에 PATCH → 404 `ASSIGNMENT_NOT_FOUND`. 없는 배치 ID에 DELETE → 404 `ASSIGNMENT_NOT_FOUND` — 확인: `AllocationNotFoundTest`.
4. **D8 투입 불가**: E2(최동훈, 시드에 투입 불가)를 P4(델타)에 20%로 신규 배치 → 400 `ASSIGNMENT_EMPLOYEE_UNAVAILABLE` — 확인: `AllocationCreateTest.unavailableEmployee`.
5. **D8 가용률 0**: 기존 배치 없는 직원(E3 이수민)을 `[오늘..오늘+5]`에 100% 배치(201)한 뒤 같은 기간에 5%를 더 배치 → 400 `ASSIGNMENT_NO_AVAILABILITY` — 확인: `AllocationCreateTest.noAvailability`.
6. **D8 초과**: E1의 P1 기간과 겹치는 `[2026-06-15..2026-06-25]`에 P3 50% 추가 → 400 `ASSIGNMENT_OVER_ALLOCATED`(60+50=110) — 확인: `AllocationCreateTest.overAllocated`.
7. **D8 프로젝트 기간**: E3을 P4(델타 `[2026-07-15..2026-10-13]`)에 기간 `[2026-10-14..2026-10-20]`으로 배치 → 400 `ASSIGNMENT_OUT_OF_PROJECT_PERIOD` — 확인: `AllocationCreateTest.outOfProjectPeriod`.
8. **D27 중복**: E1을 P3에 `[2026-06-01..2026-06-10]` 20% 배치(201)한 뒤 E1을 P3에 `[2026-06-05..2026-06-20]` 20%로 다시 배치 → 400 `ASSIGNMENT_OVERLAP` — 확인: `AllocationCreateTest.overlap`.
9. **투입률 수정**: E1의 P1 배치(60%)를 40으로 PATCH → 200, 본문 `allocationPercent`=40. 7로 PATCH → 400 `ASSIGNMENT_INVALID_PERCENT` — 확인: `AllocationModifyTest.lowerPercent`, `invalidPercent`.
10. **D28**: E2(시드에 투입 불가, P3 40% 보유)의 배치를 45로 PATCH → 400 `ASSIGNMENT_MODIFY_FORBIDDEN_UNAVAILABLE`. 20으로 PATCH → 200 — 확인: `AllocationModifyTest.unavailableRules`.
11. **PATCH 업무 규칙(투입 가능 직원)**: E1(AVAILABLE)에 대해서도 수정 후 상태를 검사한다 — 확인: `AllocationModifyTest.businessRules`.
    - 수정 후 100% 초과: E1을 P3에 `[2026-06-15..2026-06-25]` 30%로 배치(201)한 뒤 그 배치를 50%로 PATCH → 400 `ASSIGNMENT_OVER_ALLOCATED`(60+50=110).
    - 기간 수정 후 프로젝트 기간 밖: E3을 P4(델타)에 `[2026-07-15..2026-08-15]` 30%로 배치(201)한 뒤 기간을 `[2026-10-14..2026-10-20]`으로 PATCH → 400 `ASSIGNMENT_OUT_OF_PROJECT_PERIOD`.
    - 기간 수정 후 겹침: E1을 P3에 `[2026-06-01..2026-06-10]` 20%(201)과 `[2026-06-15..2026-06-25]` 20%(201)에 배치한 뒤 후자의 기간을 `[2026-06-05..2026-06-20]`으로 PATCH → 400 `ASSIGNMENT_OVERLAP`.
12. **해제**: E2의 P3 배치를 DELETE → 204, `AssignmentRepository.findByEmployeeId(E2)`가 비어 있고 E2의 `[2026-06-15..2026-06-25]` 가용률이 100으로 돌아옴 — 확인: `AllocationDeleteTest.release`.
13. **후보 조회**: `GET /api/assignments/candidates?projectId=P3&startDate=2026-06-15&endDate=2026-06-25` → 200, E1의 `periodAvailability`=40(100−60), E2의 `availabilityStatus`="UNAVAILABLE" — 확인: `AllocationCandidatesTest.candidateList`.
14. **§7 여섯 시나리오(D10)**: 각각 독립 테스트 클래스(독립 임시 DB)로 — 확인: `AllocationScenario*Test` 6개.
    - 정상 배치: 기준 1과 같고, 배치 후 E1의 그 기간 가용률이 10(100−90) — `AllocationScenarioNormalTest`.
    - 투입률 초과: 기준 6과 같음 — `AllocationScenarioOverAllocatedTest`.
    - 투입 불가 직원: 기준 4와 같음 — `AllocationScenarioUnavailableTest`.
    - 기간이 겹치지 않는 배치: E1을 P4에 `[2026-07-26..2026-08-15]` 30%로 배치 → 201(P1의 60%는 그 기간을 덮지 않아 합산 안 함), 그 기간 가용률 70 — `AllocationScenarioNonOverlapTest`.
    - 배치 해제: 기준 12와 같음 — `AllocationScenarioReleaseTest`.
    - 상태 변경: 기준 10과 같음(시드의 E2가 이미 투입 불가 상태; 상태 변경 API는 T#8, 대시보드 "확인 필요" 표시는 T#11) — `AllocationScenarioStatusChangeTest`.
15. **오류 본문**: `POST /api/assignments`에 `Content-Type: text/plain`으로 보내면 415, `code`=`UNSUPPORTED_MEDIA_TYPE`. 이 태스크의 모든 4xx 응답 본문은 키가 정확히 `code`, `message` 둘뿐이다 — 확인: `AllocationErrorShapeTest`.
16. **회귀**: `make build`, `make test`, `make lint`가 그대로 통과한다 — 확인: 같은 명령(baseline: `origin/main` 62b74bc, 현재 통과 상태 유지).

## 하지 않을 일

- 인증·권한 구현과 역할별 403 검사 — → T#6(서버 보안 설정 한 곳; PM 결정, 이슈 #10 댓글).
- 직원 상태 변경 API — → T#8. 기준 10·14의 "상태 변경"은 시드의 E2(이미 투입 불가)를 그대로 쓴다.
- 대시보드 집계와 "확인 필요" 표시 — → T#11.
- 프로젝트 기간 변경 시 기존 배치 밖으로 나가는 것 막기(D30) — → T#9(프로젝트 수정 API).
- 배치 화면(프런트엔드) — → T#17.
- 프런트엔드 변경 — 이 태스크는 `backend/`만 건드린다.
