# T#15 프로젝트 목록 화면

## 산출물

로그인한 관리자가 `/projects`에서 프로젝트 목록을 상태 필터로 보고, 프로젝트명·상태·기간·필요 인원·배치 인원을 확인하는 화면(빈 목록·검색 결과 없음·오류 상태 포함)이 있고, 이 화면이 쓰는 공용 `Badge`와 `SegmentedControl`이 있다.

## 작업량

이슈 #15 그대로 하나로 한다(나누지 않는다). 예상 약 7시간(하루, 빠듯함).

| 일 | 예상 |
|---|---|
| `DataTable` 셀 렌더, `Badge`, `SegmentedControl`과 Vitest | 1.5시간 |
| 목록 화면과 데이터 불러오기(필터, 지연 응답, 상태) | 2시간 |
| 화면 Vitest | 1.5시간 |
| e2e(실제 시드, 응답 가로채기, 네 너비), 스크린샷 | 1.5시간 |
| 레드·그린 기록, 증거 | 0.5시간 |

## 전제

- 근거: REQ-CONTEXT D3, D13, D29, D34, D35, D36. 화면은 `docs/design/BRIEF.md` 6.5절(프로젝트 목록), 3.3절(DataTable), 3.4절(StateMessage), 3.6절(Badge), 4절(Layout), 5절(Formats)을 따른다. BRIEF가 정하지 않은 값은 `(제안)`이다.
- 데이터는 #9의 `GET /api/projects`와 `GET /api/projects?status=<PLANNED|IN_PROGRESS|DONE|ON_HOLD>`(`main`에 있음)다. 항목은 `{id, name, startDate, endDate, status, requiredHeadcount, assignedHeadcount}`이고 `id` 오름차순으로 오며, 화면은 그 순서 그대로 보여 준다. 필요 인원과 배치 인원은 API 값을 그대로 쓴다(D36). 화면이 합계나 상태를 다시 계산하지 않는다.
- 권한: 이 화면은 #6의 라우트 보호 아래(`ManagerOnly`)에 있다. 인력 관리자·프로젝트 관리자·겸임이 본다. 직원 역할만 가진 계정은 `/projects`에서 `/me`로 가고(`AppRoutes.test.tsx`가 확인), 서버는 직원 역할의 `GET /api/projects`를 403으로 막는다(`AuthorizationPolicyTest`). 이 태스크는 그 규칙을 바꾸지 않는다.
- 이 태스크가 `PlaceholderPage`를 대신해 `/projects`에 `ProjectListPage`를 둔다. 다른 라우트는 바꾸지 않는다.
- `DataTable`(T#4)에 셀을 직접 그리는 선택 속성 `render`를 더한다. 이 속성이 없는 열은 지금과 똑같이 값을 글자로 보인다(하위 호환).
- `Badge`는 BRIEF 3.6절 "이후 태스크가 같은 기준으로 만드는 것"의 첫 사용이다. 이 태스크는 프로젝트 상태 배지(D13)만 만든다. 직원 상태 배지 등은 그 화면 태스크가 같은 컴포넌트에 더한다.
- `SegmentedControl`은 BRIEF 6.5절의 "한 줄 분할 버튼"이다. BRIEF 3절에 따로 값이 없어 아래 값을 이 계약서가 정한다(제안).
- `make`가 설치되어 있지 않은 환경에서는 Makefile의 각 줄을 같은 명령으로 실행해 증거에 적는다.

## 화면 동작

### 구성 (BRIEF 6.5, 넓은 구간 ≥1024px)

1. 제목 "프로젝트"(h1, xl/700).
2. 상태 필터: `SegmentedControl`, 항목 "전체", "계획", "진행 중", "완료", "보류" 순서.
3. 표(`DataTable`): 열 "프로젝트명", "상태", "기간", "필요 인원", "배치 인원". 인원 두 열은 끝 정렬(`tabular-nums`)이고 숫자만 쓴다(BRIEF 5절).

좁은 구간(<1024px)에서는 같은 구성이 한 열이고, 표는 카드가 되며(`DataTable`), 필터는 같은 분할 버튼이다.

- 프로젝트명 셀은 `/projects/<id>`로 가는 링크다(`Link`). 그 상세 화면은 #16이 만든다. 그 전에는 알 수 없는 경로라 `/`로 돌아간다.
- 상태 셀은 `Badge`다. 글자를 항상 쓴다: 계획, 진행 중, 완료, 보류(D13).
- 기간 셀은 `YYYY-MM-DD ~ YYYY-MM-DD`(`~` 앞뒤 공백 한 칸, BRIEF 5절)다. 줄바꿈은 `~` 뒤에서만 일어난다(`~` 앞 공백은 줄바꿈하지 않는 공백).
- 이 태스크는 "프로젝트 등록" 버튼과 "인력 부족" 배지를 그리지 않는다(아래 "하지 않을 일").

### 필터와 주소

- 필터 상태는 주소의 `status` 쿼리에 있다: `/projects`(전체), `/projects?status=PLANNED|IN_PROGRESS|DONE|ON_HOLD`(제안). 알 수 없는 값은 전체로 본다. 필터 버튼을 누르면 쿼리가 바뀌고 새로 불러온다.
- 선택된 항목은 `aria-pressed="true"`이고 나머지는 `false`다. 이미 선택된 항목을 다시 눌러도 요청을 더 보내지 않는다.
- 전체는 `GET /api/projects`(쿼리 없음), 그 밖은 `GET /api/projects?status=<값>`이다.

### 불러오는 동안과 상태 (D35)

- **불러오는 중**: 표 자리에 "불러오는 중…"(sm, text-muted)을 두고 그 영역에 `aria-busy="true"`를 둔다. 필터 버튼은 그대로 눌린다.
- **오류**: 네트워크 오류나 2xx가 아닌 응답이면 표 자리에 `StateMessage` `error`와 "다시 시도"를 둔다. "다시 시도"는 현재 필터로 다시 부른다. 세션 만료(401)도 같은 오류 상태다(제안: 세션 만료 처리는 이 태스크가 하지 않는다).
- **빈 목록**: 필터가 "전체"이고 결과가 비면 `StateMessage` `empty`, 제목 "등록된 프로젝트가 없습니다".
- **검색 결과 없음**: 필터가 "전체"가 아닌데 결과가 비면 `StateMessage` `no-results`, 제목 "이 상태의 프로젝트가 없습니다", 버튼 "필터 초기화"(전체로 되돌린다).
- **지연 응답과 겹친 요청**: 필터를 바꾸면 앞의 요청은 버리고, 그 응답이 나중에 도착해도 화면을 바꾸지 않는다. 항상 마지막으로 고른 필터의 응답만 보인다. 오류 뒤 "다시 시도"도 같다.

### `SegmentedControl` 값 (제안)

- `role="group"`에 접근 이름(`aria-label` "상태 필터")을 두고, 항목은 `<button type="button">`이다. 항목 너비는 같다(`flex: 1`). 컨테이너는 한 줄이고 가로로 넘치지 않는다.
- 높이는 `--control-height`(40px), 컨테이너 테두리 1px `--color-border-strong`, 반경 `--radius-sm`, 항목 글자 sm/600.
- 선택된 항목: 배경 `--color-primary`, 글자 `--color-on-primary`(대비 6.62). 선택 안 된 항목: 배경 `--color-surface`, 글자 `--color-text`. hover는 선택 안 된 항목 배경 `--color-surface-subtle`.
- 포커스는 BRIEF 3절 공통 규칙(2px `--color-focus` outline, offset 2px)이다.
- 넓은 구간에서는 컨트롤 너비가 최대 480px이고 왼쪽에 붙는다(항목 약 96px). 좁은 구간(328px)에서는 항목 5개의 너비가 각각 약 65px(328 ÷ 5)이고, 한 줄에 모두 보인다.

### `Badge` 값 (BRIEF 3.6절)

xs/600, 패딩 `2px 8px`, 반경 `--radius-full`. 프로젝트 상태(D13): `계획` text-muted/surface-subtle, `진행 중` primary/surface-subtle, `완료` success/success-bg, `보류` warning/warning-bg. 대비는 BRIEF 2.1절 표의 쌍(5.64, 5.84, 5.19, 5.52)이다.

## 수용 기준

1. **`DataTable`의 셀 렌더 (하위 호환).** `Column`에 선택 속성 `render?: (row) => ReactNode`를 더한다. 있으면 그 반환 값이 표의 셀과 카드의 값 자리에 들어가고, 없으면 지금과 같이 `String(row[key])`이다. T#4의 `DataTable` 테스트는 고치지 않고 통과한다.
   - 확인: Vitest `DataTable.test.tsx`에 테스트를 더한다(표 셀과 카드 줄 모두에 사용자 지정 내용, `render` 없는 열은 글자 그대로).
   - 준비: `Column` 타입에 `render?`만 더한다(구현에서 쓰지 않는 스텁). 레드: 사용자 지정 내용이 보이지 않아 `getByRole('link')`/`getByText` 단언이 실패한다.
2. **`Badge`.** 상태 `PLANNED`, `IN_PROGRESS`, `DONE`, `ON_HOLD`를 각각 글자 "계획", "진행 중", "완료", "보류"로 그리고, 요소에 `data-status`로 상태를 둔다.
   - 확인: Vitest `Badge.test.tsx`. 준비: `null`을 그리는 스텁. 레드: `getByText('진행 중')`이 없어 실패한다. 색과 모양은 기준 7(e2e).
3. **`SegmentedControl`.** 항목 목록과 선택 값을 받아 `role="group"` 안에 버튼을 그리고, 선택된 버튼만 `aria-pressed="true"`이며, 다른 버튼을 누르면 `onChange(값)`을 부른다. 선택된 버튼을 다시 눌러도 `onChange`를 부르지 않는다.
   - 확인: Vitest `SegmentedControl.test.tsx`. 준비: `null`을 그리는 스텁. 레드: `getByRole('group')`이 없어 실패한다.
4. **목록과 필터 (D3, D13).** 로그인한 관리자로 `/projects`를 열면 `GET /api/projects`를 한 번 부르고, 항목마다 한 줄(카드)로 이름(링크 `/projects/<id>`), 상태 배지, 기간(위 형식), 필요 인원, 배치 인원을 API 값 그대로 보인다. "진행 중"을 누르면 `/api/projects?status=IN_PROGRESS`를 부르고 쿼리가 `?status=IN_PROGRESS`가 되며 그 버튼이 선택된다. "전체"는 쿼리 없이 부른다. 주소가 `?status=DONE`으로 열리면 처음부터 `DONE`으로 불러오고 "완료"가 선택되어 있다. `?status=bogus`는 전체다. 이 태스크는 "인력 부족"을 그리지 않는다(필요 2·배치 1인 진행 중 항목에도 없다).
   - 확인: Vitest `ProjectListPage.test.tsx`(가짜 `fetch`, `MemoryRouter`). 준비: `null`을 그리는 `ProjectListPage` 스텁. 레드: 이름 링크가 없어 실패한다.
5. **상태 (D35).** 불러오는 중에는 "불러오는 중…"과 `aria-busy`가 보인다. 오류(네트워크 거부, 500, 401)는 `StateMessage` error와 "다시 시도"이고, 누르면 같은 주소로 다시 부르고 성공하면 목록이 보인다. 전체에서 빈 응답은 "등록된 프로젝트가 없습니다"(empty), 필터 상태에서 빈 응답은 "이 상태의 프로젝트가 없습니다"(no-results)와 "필터 초기화"이고, 누르면 `GET /api/projects`를 부르고 "전체"가 선택된다.
   - 확인: `ProjectListPage.test.tsx`. 준비·레드: 기준 4와 같다(제목 텍스트가 없어 실패).
6. **지연 응답과 겹친 요청.** 필터 "진행 중"의 응답을 붙잡아 둔 채 "완료"를 눌러 그 응답을 먼저 돌려준 뒤, 붙잡은 응답을 풀어도 화면은 "완료" 결과 그대로다. 테스트는 첫 요청이 실제로 붙잡혔고(아직 응답 전) 나중에 풀렸음을 기록한다. 오류 뒤 "다시 시도"를 누른 직후 필터를 바꾸는 경우도 마지막 선택만 보인다. 이미 선택된 항목을 다시 눌러도 요청이 늘지 않는다.
   - 확인: `ProjectListPage.test.tsx`. 준비·레드: 기준 4와 같다.
7. **모양과 값 (e2e, 실제 시드, 1280px·360px).** `project.manager`로 로그인해 `/projects`를 연다. 시드 프로젝트 5건(알파, 감마, 베타, 델타, 엡실론 프로젝트)이 `id` 순으로 보이고, 필요 인원은 모두 `2`다. 상태 배지는 글자 "진행 중"(알파, 베타), "완료"(감마), "계획"(델타), "보류"(엡실론)이고 계산된 색이 BRIEF 값이다: 진행 중 글자 `rgb(41, 82, 204)`·배경 `rgb(238, 241, 245)`, 완료 `rgb(27, 115, 64)`·`rgb(231, 244, 236)`, 계획 `rgb(85, 96, 110)`·`rgb(238, 241, 245)`, 보류 `rgb(143, 83, 0)`·`rgb(253, 241, 220)`. 필터를 "진행 중"으로 바꾸면 알파·베타 2건이고 주소가 `?status=IN_PROGRESS`이며, 새로고침해도 같다. "전체"로 돌아오면 5건이다. "인력 부족"과 "프로젝트 등록"은 없다.
   - 필터 컨트롤: 항목 5개가 한 줄에 있고(윗변이 같다) 컨트롤이 넘치지 않는다(`scrollWidth <= clientWidth`). 선택된 항목의 배경 `rgb(41, 82, 204)`·글자 `rgb(255, 255, 255)`, 선택 안 된 항목의 배경 `rgb(255, 255, 255)`·글자 `rgb(26, 31, 39)`. 컨트롤 높이 40px. 360px에서 각 항목 너비는 64px 이상이다.
   - 표: 1280px에서 열 머리글 5개와 `th scope="col"`, 인원 열 숫자가 끝에 맞는다(셀의 글자 오른쪽 끝이 같다). 360px에서는 카드(`display: block` 행)이고 머리글이 시각적으로 숨겨져 있으며 각 카드의 첫 값(프로젝트명)이 제목(글자 두께 600)이다.
   - 확인: Playwright `frontend/e2e/projects.spec.ts`. 준비: `/projects`가 `PlaceholderPage`(제목만)인 상태(스텁은 필요 없다). 레드: `locator('table')`이나 필터 `getByRole('group', { name: '상태 필터' })` 개수가 0이라 `toBe(1)` 단언이 실패한다. 개수로 즉시 판정한다.
   - 실제 시드의 배치 인원은 e2e DB(`backend/data/e2e.db`)가 만들어진 날짜에 따라 달라지므로 이 기준은 배치 인원 숫자를 단언하지 않는다(숫자는 기준 8이 고정 응답으로 확인한다).
8. **고정 응답으로 확인하는 값과 상태 (e2e, 응답 가로채기).** `page.route`로 `/api/projects*`를 고정 응답으로 바꿔서 확인한다(로그인은 실제 서버).
   - 값: 항목 `{id: 7, name: '아주 긴 프로젝트 이름 …(48자 공백 없음)', startDate: '2026-05-16', endDate: '2026-09-13', status: 'IN_PROGRESS', requiredHeadcount: 5, assignedHeadcount: 3}`이 기간 `2026-05-16 ~ 2026-09-13`, 필요 `5`, 배치 `3`으로 보이고, 이름 링크의 `href`가 `/projects/7`이다. 48자 이름은 칸 안에서 줄바꿈된다(그 요소의 `scrollWidth <= clientWidth`). 360px에서 기간 값은 `~` 뒤에서만 줄이 바뀐다(첫 줄의 끝이 `~`).
   - 상태: 빈 응답(전체)은 "등록된 프로젝트가 없습니다". 필터 "계획"의 빈 응답은 "이 상태의 프로젝트가 없습니다"와 "필터 초기화"이고, 누르면 전체 요청이 나간다. 500 응답은 오류 상태이고 "다시 시도"가 같은 필터로 다시 요청한다.
   - 지연: "진행 중" 응답을 붙잡고(요청이 실제로 와서 붙잡혔음을 기록) "완료"를 누르면 "완료" 결과가 보이고, 붙잡은 응답을 풀어도 바뀌지 않는다.
   - 확인: Playwright `frontend/e2e/projects.spec.ts`. 준비·레드: 기준 7과 같다(`table`·필터 개수 0).

## 격리

새로 건드리는 DB·폴더·서비스·포트는 없다. e2e와 스크린샷은 T#4가 만든 `scripts/e2e-servers.sh`와 README "검사 격리" 표를 그대로 쓴다(백엔드 18080, DB 파일 `backend/data/e2e.db`, 프런트엔드 14173, 서버 기록 `.nexi-tmp/e2e-servers.pids`). e2e는 목록을 읽기만 하고 데이터를 바꾸지 않는다(`POST`·`PUT`을 보내지 않는다). 응답 가로채기는 브라우저 안(`page.route`)에서만 일어난다. 외부 네트워크를 쓰지 않는다(D40). 기계별 설치 경로나 PATH 설정을 쓰지 않는다.

## 하지 않을 일

- **"프로젝트 등록" 버튼과 프로젝트 상세·등록·수정 화면(→ #16).** BRIEF 6.5절은 목록 제목 줄에 이 버튼을 두라고 하지만, 눌러서 갈 곳(`/projects/new`)이 #16에 있다. 목록의 이름 링크가 가리키는 `/projects/<id>`도 #16이 만든다.
- **"인력 부족" 배지.** BRIEF 6.5절은 표 마지막 열로 두지만, 판정은 D20(오늘 배치 인원이 필요 인원보다 적거나 필요 역량 줄의 기술 보유자가 배치되지 않음)이라 기술 보유 여부를 아는 백엔드에서만 계산한다(D36). 목록 API에는 그 값이 없고 대시보드 API(#11)가 만든다. 화면이 필요 인원과 배치 인원으로 직접 판정하지 않는다.
- 이름 검색, 기간·인원 정렬, 페이지 나누기, 프로젝트 삭제.
- 세션 만료(401) 처리(로그인 화면으로 보내기)와 `AuthContext`의 변경.
- `Badge`의 직원 상태·배치·대시보드 변형(→ 각 화면 태스크)과 `Gantt` 변경.
- 백엔드 변경, 새 API, BRIEF 변경.
- 스크린샷 픽셀 비교 자동화. 스크린샷은 리뷰어가 BRIEF와 대조한다.
