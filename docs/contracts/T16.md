# T#16 프로젝트 상세 화면과 목록의 "프로젝트 등록" 버튼

## 산출물

로그인한 관리자가 프로젝트 상세(`/projects/<id>`)에서 정보·인력 현황·필요 역량·배치 인력을 볼 수 있는 화면이 있고, 프로젝트 관리자에게는 상세의 "인력 배치"·"수정"과 목록 제목 줄의 "프로젝트 등록" 링크 버튼이 있다.

## 작업량

PM 결정(이슈 #16 댓글, 2026-10-13 계약 승인 뒤 수정 요청)에 따라 이 태스크는 **상세 화면과 목록의 "프로젝트 등록" 버튼만** 한다. 등록·수정 폼(`/projects/new`, `/projects/<id>/edit`), `SelectField`, 폼의 오류 표시(D30·D33), 쓰기 라우트 돌려보내기, 폼 스크린샷은 **#34**로 옮겼다(선행 작업 #13, #16). 예상 약 4.5시간.

| 일 | 예상 |
|---|---|
| 공용 부품(`ButtonLink`, `Period` 분리)과 Vitest | 1시간 |
| 상세 화면과 Vitest | 1.5시간 |
| 라우트·권한 버튼, 목록의 "프로젝트 등록" 버튼과 Vitest | 0.5시간 |
| e2e(실제 시드, 너비), 스크린샷 | 1시간 |
| 레드·그린 기록, 증거 | 0.5시간 |

## 전제

- 근거: REQ-CONTEXT D3, D9, D11, D13, D22, D29, D34, D36. 화면은 `docs/design/BRIEF.md` 6.6절(프로젝트 상세), 3.1절(Button), 3.3절(DataTable), 3.4절(StateMessage), 3.6절(Badge), 4절, 5절을 따른다. BRIEF가 정하지 않은 값은 `(제안)`이다.
- 선행 작업은 #4, #6, #9, #15다(PM 댓글). #15는 `main`에 있다.
- 데이터는 #9의 `GET /api/projects/{id}`다. 응답: `{id, name, description|null, startDate, endDate, status, requiredSkills:[{jobTitle, skillName, proficiencyLevel, headcount}], requiredHeadcount, assignedHeadcount, assignments:[{assignmentId, employeeId, employeeName, startDate, endDate, allocationPercent, currentAvailability}]}`. 없는 id는 404 `{"code": "PROJECT_NOT_FOUND", …}`다. 화면은 값을 API 그대로 보이고 계산하지 않는다(D36).
- 권한(D9, D25): 라우트는 #6의 `ManagerOnly`(관리자 역할만) 아래다. **쓰기로 가는 버튼("인력 배치", "수정", "프로젝트 등록")은 `PROJECT_MANAGER` 역할이 있는 계정에만** 보인다(`dual.manager` 포함, `hr.manager`는 읽기만). 서버는 인력 관리자만의 `POST`·`PUT`을 403으로 막는다(#6 `AuthorizationPolicyTest`). 이 태스크는 그 규칙을 바꾸지 않고 쓰기 요청도 보내지 않는다.
- 모바일(D29): 등록·수정으로 가는 버튼은 1024px 미만에서 숨긴다(CSS `display: none`). "인력 배치"는 두 구간 모두에서 보인다(BRIEF 6.6). 쓰기 라우트 자체의 모바일 처리는 #34다.
- 버튼이 가는 곳은 이 태스크가 만들지 않는다. "수정"(`/projects/<id>/edit`)과 "프로젝트 등록"(`/projects/new`)은 #34가 만들고, "인력 배치"(`/projects/<id>/assign`, 제안: 경로 이름)는 #17이 만들며, 배치 인력 표의 직원 이름 링크 `/employees/<employeeId>`는 #14가 만든다. 그 전에는 알 수 없는 경로라 `/`로 돌아간다(T#6의 `*` 라우트, T#15의 이름 링크와 같다). #17·#34가 다른 경로를 정하면 그때 이 링크를 바꾼다.
- `make`가 설치되어 있지 않은 환경에서는 Makefile의 각 줄을 같은 명령으로 실행해 증거에 적는다.

## 화면 동작

### 라우트

`ManagerOnly` 안에 `/projects/:id`(상세) 하나를 더한다. `:id`가 양의 정수가 아니면(`/projects/new`, `/projects/abc` 포함) 알 수 없는 경로와 같이 `/`로 돌아간다(T#6의 `*` 라우트 동작). 쓰기 라우트는 만들지 않는다. 로그아웃 상태는 `/login`, 직원 전용 계정은 `/me`로 가는 T#6 동작은 그대로다.

### 상세 (BRIEF 6.6, 넓은 구간 ≥1024px과 좁은 구간 <1024px 모두 한 열)

순서: ① 제목 줄: 프로젝트명(h1, xl/700), 상태 `Badge`, 기간(`YYYY-MM-DD ~ YYYY-MM-DD`) ② 설명(없으면 `—`, text-muted) ③ 인력 현황: "필요 5명 / 배치 3명"(`requiredHeadcount`, `assignedHeadcount`, 문장에는 `명`을 붙인다, BRIEF 5절) ④ "필요 역량" 표: 직무 · 기술 · 숙련도(초급·중급·고급, D11) · 인원 ⑤ "배치 인력" 표: 직원(링크 `/employees/<employeeId>`) · 기간 · 투입률(`60%`, 끝 정렬) ⑥ 버튼 줄: primary "인력 배치"(링크 `/projects/<id>/assign`), secondary "수정"(링크 `/projects/<id>/edit`).

- 표는 `DataTable`(좁은 구간에서 카드). 기간 셀은 T#15의 `Period`(분리한 공용 부품)로 그린다. 필요 역량이 없으면 표 자리에 `StateMessage` `empty` 제목 "등록된 필요 역량이 없습니다", 배치가 없으면 "배치된 직원이 없습니다"(제안).
- 버튼: "인력 배치"는 `PROJECT_MANAGER` 역할이 있으면 두 구간 모두에서 보인다. "수정"은 `PROJECT_MANAGER`가 있을 때 DOM에 있고 <1024px에서는 `display: none`이다. `hr.manager`(인력 관리자만)에게는 셋 다 없다.
- **불러오는 중**: "불러오는 중…"(sm, text-muted)과 그 영역의 `aria-busy="true"`. **오류**(네트워크, 404가 아닌 2xx 아님): `StateMessage` `error`와 "다시 시도". **없는 프로젝트**(양의 정수이지만 404 `PROJECT_NOT_FOUND`): `StateMessage` `empty` 제목 "프로젝트를 찾을 수 없습니다"와 "프로젝트 목록" 링크(제안).
- "인력 부족"이나 부족한 역량은 그리지 않는다(아래 "하지 않을 일").

### 목록 화면의 버튼 (#15 PM 메모)

`ProjectListPage` 제목 줄에서 h1 오른쪽에 primary "프로젝트 등록"(링크 `/projects/new`)을 둔다. `PROJECT_MANAGER`가 있을 때 DOM에 있고 <1024px에서는 `display: none`이다. `hr.manager`와 직원 전용 계정에는 없다. 목록의 나머지 동작은 T#15 그대로다.

## 수용 기준

1. **공용 부품.** (a) `ButtonLink`: `Link`를 `Button`과 같은 모양(`primary`, `secondary`)으로 그리고 역할은 링크다. (b) `Period`(T#15의 `ProjectListPage`에 있던 기간 표시)를 `components/Period.tsx`로 옮긴다. 목록의 기간 표시는 그대로여야 한다.
   - 확인: Vitest `ButtonLink.test.tsx`와, T#15의 `ProjectListPage.test.tsx`·`e2e/projects.spec.ts`가 고치지 않고 통과한다(기준 7).
   - 준비: `null`을 돌려주는 `ButtonLink` 스텁. 레드: `getByRole('link', { name })`이 없어 실패한다. `Period`는 옮기기만 하는 정리라 새 검사 없이 기준 7의 회귀 검사로 지킨다.
2. **상세 값과 상태.** 시드 형식의 응답으로 순서 ①–⑥이 그려지고(이름, 배지, 기간, 설명 또는 `—`, "필요 5명 / 배치 3명", 필요 역량 표의 열과 숙련도 한글, 배치 표의 직원 링크·기간·`60%`), 요청은 `GET /api/projects/<id>` 한 번이다. 필요 역량·배치가 없으면 각각 empty 상태다. 불러오는 중, 오류(다시 시도), 404가 위 동작대로다. `/projects/new`와 `/projects/abc`는 요청 없이 `/`로 돌아간다. `/projects/5/edit`처럼 정의되지 않은 경로도 `/`로 돌아간다.
   - 확인: Vitest `ProjectDetailPage.test.tsx`(가짜 `fetch`, `MemoryRouter`, 응답을 붙잡았다가 풂)와 `AppRoutes.projects.test.tsx`. 준비: `null`을 그리는 `ProjectDetailPage` 스텁과 상세 라우트 없음. 레드: `getByRole('heading', { name })`이 없어 실패하고, 라우트 테스트는 `/projects/1`이 목록 화면으로 가지 않고 `/`로 돌아가 실패한다.
3. **버튼과 역할.** `PROJECT_MANAGER`(`dual.manager`)에게는 상세에 "인력 배치"(`/projects/<id>/assign`)와 "수정"(`/projects/<id>/edit`), 목록에 "프로젝트 등록"(`/projects/new`)이 DOM에 있고, `hr.manager`(`HR_MANAGER`만)에게는 셋 다 없다. 1024px 미만에서 "수정"과 "프로젝트 등록"이 `display: none`이고 "인력 배치"는 보인다(e2e의 계산된 `display`).
   - 확인: Vitest `ProjectDetailPage.test.tsx`, `ProjectListPage.register.test.tsx`(역할별 DOM)와 기준 4의 e2e(너비별 `display`). 준비·레드: 기준 2와 같다.
4. **모양과 값 (e2e, 실제 시드 읽기만).** `frontend/e2e/projects-detail.spec.ts`. 1280px와 360px: `project.manager`로 목록에서 "알파 프로젝트" 링크를 눌러 상세에 간다. 주소가 `/projects/<id>`, h1 "알파 프로젝트", 배지 "진행 중"(글자 `rgb(41, 82, 204)`·배경 `rgb(238, 241, 245)`), 인력 현황이 `필요 2명 / 배치 N명` 형식(N은 숫자. 시드가 만들어진 날짜에 따라 달라 숫자는 단언하지 않는다), 필요 역량 표 한 줄(백엔드 개발자, Java, 중급, 2), 배치 표 세 줄(권지안, 강민재, 박소영 순). 1280px에서는 표 머리글이 있고 360px에서는 카드다. "인력 배치"는 두 너비 모두에서 보이고 `href`가 `/projects/<id>/assign`이다. "수정"과 목록의 "프로젝트 등록"은 1280px에서 보이고(`display`가 `none`이 아님) 360px에서는 `display: none`이다. `hr.manager`로 같은 화면을 열면 "인력 배치"·"수정"·"프로젝트 등록"이 없다. 없는 프로젝트(`/projects/99999`)는 "프로젝트를 찾을 수 없습니다"이고, `/projects/new`를 열면 주소가 `/`가 된다.
   - 실제 서버에는 `POST`·`PUT`을 보내지 않는다.
   - 확인: Playwright `frontend/e2e/projects-detail.spec.ts`. 준비: `/projects/<id>`가 정의되지 않은 상태(`/`로 돌아간다). 레드: 상세의 h1 "알파 프로젝트"나 `table` 개수가 0이라 `toBe(1)` 단언이 즉시 실패한다. 개수로 즉시 판정한다(앱이 `GET /api/auth/me`를 먼저 부른 뒤 그리므로 내비게이션이 보인 뒤에 판정한다).
5. **반응형 (D29, D34).** 상세가 1280px, 1024px, 1023px, 360px에서 가로 넘침이 없다. T#4의 `expectNoHorizontalOverflow`를 쓴다. 상세의 두 표는 1024px에서 표, 1023px에서 카드다. 공백 없는 48자 프로젝트명(가로챈 응답)이 제목 줄에서 줄바꿈되고 가로 넘침을 만들지 않는다.
   - 확인: Playwright `frontend/e2e/projects-detail.spec.ts`(48자 이름은 `page.route`로 가로챈 `GET` 응답). 준비·레드: 기준 4와 같다.
6. **스크린샷 (D34).** `make screenshots T=16`이 `docs/screens/T16/`에 전체 페이지로 저장한다: `list-1280.png`(제목 줄의 "프로젝트 등록"), `list-360.png`(버튼 없음), `detail-1280.png`, `detail-360.png`(실제 시드의 "알파 프로젝트"). 각 화면의 제목이 보임을 단언한 뒤 찍는다. 끝난 뒤 서버가 모두 내려가 있다(T#4 기준 11(a)와 같은 확인).
   - 확인: `frontend/e2e/screens/T16.spec.ts`, `make screenshots T=16; echo $?`가 0이고 PNG 4장이 있다. 이어서 `.nexi-tmp/e2e-servers.pids`의 프로세스 그룹이 모두 없고 18080·14173에 응답이 없다.
   - 준비·레드: 스펙 파일이 없을 때 `make screenshots T=16`이 `screenshots: frontend/e2e/screens/T16.spec.ts 없음`으로 실패하는 것은 레드가 아니다. 스펙을 만든 뒤 상세 제목이 없어 단언이 실패하고 PNG가 생기지 않는 것이 레드다.
7. **회귀.** `make build`, `make test`, `make lint`가 통과한다. T#15의 `ProjectListPage.test.tsx`·`Badge.test.tsx`·`SegmentedControl.test.tsx`·`DataTable.test.tsx`·`e2e/projects.spec.ts`, T#6의 `AppRoutes.test.tsx`·`e2e/auth.spec.ts`, T#4·T#12·T#25 검사는 고치지 않고 통과한다. ## 격리

새로 건드리는 DB·폴더·서비스·포트는 없다. e2e와 스크린샷은 T#4가 만든 `scripts/e2e-servers.sh`와 README "검사 격리" 표를 그대로 쓴다(백엔드 18080, DB 파일 `backend/data/e2e.db`, 프런트엔드 14173, 서버 기록 `.nexi-tmp/e2e-servers.pids`). **실제 서버에는 읽기 요청만 보낸다.** 48자 이름은 브라우저 안의 `page.route`로 가로챈 응답으로 확인한다. 외부 네트워크를 쓰지 않는다(D40). 기계별 설치 경로나 PATH 설정을 쓰지 않는다.

## 하지 않을 일

- **등록·수정 폼(`/projects/new`, `/projects/<id>/edit`), `SelectField`, 폼의 오류 표시(D30·D33), 쓰기 라우트의 권한·모바일 돌려보내기, 폼 스크린샷(→ #34).** 이 태스크는 "수정"·"프로젝트 등록" 버튼을 링크로 두기만 하고, 그 도착지는 #34가 만든다. #34가 #13의 `SelectField`에 `error`를 더한다.
- **`useMediaQuery`.** 이 태스크의 버튼은 CSS로 숨기므로 쓰이지 않는다. 쓰기 라우트를 너비로 돌려보내는 #34가 필요할 때 만든다.
- **"부족한 역량"과 "인력 부족" 표시.** BRIEF 6.6절 인력 현황은 부족한 역량을 함께 보이라고 하지만, 그 판정은 D20(필요 역량 줄의 기술 보유자가 배치되었는가)이라 백엔드 규칙이다(D36). 상세 API에는 그 값이 없고 화면이 직접 판정하지 않는다. 필요 인원과 배치 인원만 보인다.
- 인력 배치 화면과 배치 생성·수정·해제(→ #17). "인력 배치" 버튼은 링크일 뿐이다.
- 직원 상세 화면(→ #14), 프로젝트 삭제, 상태 전이 규칙, 이름 검색.
- 백엔드 변경, 새 API, BRIEF 변경, 세션 만료(401) 처리와 `AuthContext` 변경.
- 스크린샷 픽셀 비교 자동화. 스크린샷은 리뷰어가 BRIEF와 대조한다.
