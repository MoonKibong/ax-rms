# T#5 데이터 모델·저장소 계층·시드 데이터

## 산출물

`backend/`에 부서·직원·직원기술·계정·역할·프로젝트·필요역량줄·배치 8개 테이블(스키마)과 그 각각을 다루는 저장소(repository) 계층, 그리고 빈 DB로 처음 실행할 때 D31의 시드(부서3·직원20·프로젝트5·배치15, §7 시나리오용 데이터, 역할별 데모 계정 4개)를 넣는 시더(seeder)가 있다.

## 스키마 (SQLite, `schema.sql`로 `CREATE TABLE IF NOT EXISTS` — 멱등)

- `department(id, name)`
- `employee(id, name, department_id→department, job_title, career_years, availability_status CHECK IN ('AVAILABLE','UNAVAILABLE'), unavailable_reason NULL, unavailable_until NULL)`
- `employee_skill(id, employee_id→employee, skill_name, proficiency_level CHECK IN ('BEGINNER','INTERMEDIATE','ADVANCED'))`, `UNIQUE(employee_id, skill_name)`
- `account(id, employee_id→employee UNIQUE, username UNIQUE, password_hash)` — D17: 계정 1:employee 1(계정은 정확히 하나의 직원을 가리키고, 그 직원을 가리키는 계정은 최대 하나)
- `account_role(account_id→account, role CHECK IN ('HR_MANAGER','PROJECT_MANAGER','EMPLOYEE'))`, `PRIMARY KEY(account_id, role)`
- `project(id, name, description, start_date, end_date, status CHECK IN ('PLANNED','IN_PROGRESS','DONE','ON_HOLD'))`
- `project_required_skill_line(id, project_id→project, job_title, skill_name, proficiency_level CHECK IN ('BEGINNER','INTERMEDIATE','ADVANCED'), headcount)`
- `assignment(id, employee_id→employee, project_id→project, start_date, end_date, allocation_percent CHECK (allocation_percent BETWEEN 5 AND 100 AND allocation_percent % 5 = 0))`

역할(`HR_MANAGER`=인력 관리자, `PROJECT_MANAGER`=프로젝트 관리자, `EMPLOYEE`=직원)은 D25 해석에 따라 모든 계정이 최소 `EMPLOYEE`를 갖고(본인 상세는 누구나 봄), 추가로 `HR_MANAGER`/`PROJECT_MANAGER`를 가질 수 있다(D17 겸임).

## 저장소 계층

엔터티마다 저장소 인터페이스(JDBC 구현)가 있고, 최소 삽입(insert)과 조회(findAll, findById 또는 그에 준하는 조건 조회)를 제공한다: `DepartmentRepository`, `EmployeeRepository`, `EmployeeSkillRepository`, `AccountRepository`(역할 조회·배정 포함), `ProjectRepository`, `ProjectRequiredSkillLineRepository`, `AssignmentRepository`.

## 수용 기준

1. 스키마: 위 8개 테이블이 `schema.sql`로 생성된다 — 확인: 빈 DB로 컨텍스트를 올린 테스트가 `sqlite_master`에서 8개 테이블명을 모두 조회함(새 검사: 준비 — `schema.sql` 테스트 스텁과 조회 테스트 작성; 레드 — `schema.sql`이 없어 8개 중 0개 조회됨).
2. 저장소 계층: 7개 저장소 각각 삽입한 값을 조회로 그대로 돌려준다 — 확인: 저장소별 라운드트립 단위 테스트 7개(새 검사: 준비 — 저장소 인터페이스 선언과 테스트 스텁; 레드 — 구현체가 없어 컴파일되지 않으므로, 먼저 빈 구현체(미구현 예외 던짐)를 두어 테스트가 그 예외로 실패하게 한 뒤 구현한다).
3. 데이터 정합성 제약: `allocation_percent`(5~100, 5단위가 아니면 거부), `availability_status`/`proficiency_level`/`project.status`(허용값 밖이면 거부), `account.employee_id`(중복 삽입 거부)가 DB 제약으로 걸린다 — 확인: 각각 위반 값을 삽입해 SQL 예외가 나는 테스트 4개(새 검사: 준비 — 제약 없는 임시 테이블로 먼저 돌려 통과(위반 안 됨)함을 레드로 기록; 레드 — CHECK/UNIQUE 제약 전이라 위반 삽입이 성공해 "예외 발생" assertion이 실패).
4. 시드 트리거와 멱등성: 부서 테이블이 빈 DB로 처음 실행하면 시더가 D31 데이터를 넣고, 이미 데이터가 있으면(부서 수가 0이 아니면) 다시 넣지 않는다 — 확인: 테스트가 임시 빈 DB로 컨텍스트를 두 번 올려(또는 시더를 두 번 호출) 두 번째 실행 후 건수가 그대로임을 확인(새 검사: 준비 — 시더 스텁(아무 것도 안 넣음) 작성; 레드 — 시더가 없어 부서 수가 0으로 남아 "0이 아님" assertion 실패).
5. 시드 건수(D31): 부서 3, 직원 20, 프로젝트 5, 배치 15 — 확인: 각 테이블 `COUNT(*)` 테스트(새 검사: 레드 — 시더 없어 전부 0).
6. §7 시나리오 데이터: 다음 세 조건을 만족하는 행이 시드에 있다 — 확인: 각각을 쿼리로 확인하는 테스트 3개(새 검사: 레드 — 시더 없어 해당 행 자체가 없음).
   - (a) 어떤 직원이 오늘(`LocalDate.now()`, 서버 날짜)을 포함하는 기간(`start_date`=오늘-20일, `end_date`=오늘+40일)에 투입률 60%인 배치를 가진다.
   - (b) `availability_status`가 `UNAVAILABLE`이고 `unavailable_until`이 오늘 이후인 직원이 있고, 그 직원은 `end_date`가 오늘 이후인(오늘-10일~오늘+30일, 투입률 40%) 배치를 가진다(D21 "확인 필요" 조건을 만족하는 행).
   - (c) (a)의 직원이 같은 프로젝트가 아닌 다른 프로젝트에, (a)의 배치 기간과 겹치지 않는 배치(`start_date`=오늘-200일, `end_date`=오늘-150일, 투입률 30%)를 하나 더 가진다.
7. 데모 계정(D31): 다음 4개 계정이 있고 비밀번호는 BCrypt로 해시 저장되며 평문은 README에 적힌다 — 확인: 계정·역할 조회 + `BCryptPasswordEncoder.matches(README의 평문, 저장된 해시)`가 각 계정에서 true인 테스트(새 검사: 준비 — `spring-security-crypto` 의존성 추가, README에 평문 자리 채워두고 테스트 스텁 작성; 레드 — 계정이 없어 조회 결과가 비어 있어 실패).
   - 인력 관리자 전용(역할: `EMPLOYEE`, `HR_MANAGER`)
   - 프로젝트 관리자 전용(역할: `EMPLOYEE`, `PROJECT_MANAGER`)
   - 직원 전용(역할: `EMPLOYEE`만)
   - 겸임(역할: `EMPLOYEE`, `HR_MANAGER`, `PROJECT_MANAGER`)
8. README: 4개 데모 계정의 아이디·평문 비밀번호·역할이 표로 적혀 있다(로그인 화면은 T#6에서 만들어지므로, 이 태스크에서는 "데이터로 존재함"과 계정 정보만 기재) — 확인: 기준 7의 테스트가 이 README의 값을 그대로 읽어 사용하므로 같은 근거로 확인됨.
9. 회귀: `make build`, `make test`, `make lint`가 그대로 통과한다(T#3에서 만든 백엔드 상태 API·프런트엔드는 바뀌지 않음) — 확인: `make build`/`make test`/`make lint`(baseline: T#3 머지 커밋, 이미 통과 상태 유지).

## 검증 명령

- 새 검사: 기준 1~7에 해당하는 JUnit 테스트(패키지 `com.ax.rms.seed`, `com.ax.rms.repository` 등). 각 레드/준비는 위 수용 기준에 적었다.
- 회귀 검사: `make build`, `make test`, `make lint` — 작업 전후 모두 통과해야 한다(이 태스크가 `backend/` 기존 코드(상태 API)를 깨지 않는지 보는 것이 목적).

## 하지 않을 일

- 직원·프로젝트·배치의 REST API(목록·상세·등록·수정·배치) — → T#8, T#9, T#10.
- 가용률 계산 로직(겹침 판정, 날짜별 합계) — → T#7. 이 태스크는 계산 없이 원본 데이터만 저장한다.
- 로그인·인증·권한 검사 — → T#6. 데모 계정은 데이터로만 존재하고, 이 태스크에서 로그인 가능 여부를 검증하지 않는다.
- 부서 등록·수정 API나 화면 — D26에 따라 영구히 없음(시드 전용).
- 대시보드 집계 — → T#11.
- 프런트엔드 변경 — 이 태스크는 `backend/`만 건드린다.
