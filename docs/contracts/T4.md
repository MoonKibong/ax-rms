# T#4 Design system: BRIEF 기반 토큰·레이아웃·기본 컴포넌트와 make screenshots

## 산출물

승인된 `docs/design/BRIEF.md`를 옮긴 프런트엔드 디자인 시스템이 있다. 토큰, 반응형 레이아웃 셸, 기본 컴포넌트, 이것들을 모아 보여 주는 참조 화면 하나로 이루어지고, `make screenshots T=<N>`이 앱을 띄워 계약서가 정한 화면을 1280px·360px로 찍어 `docs/screens/T<N>/`에 저장한 뒤 이번 실행이 띄운 서버만 내린다.

## 작업량

하루를 넘을 것으로 예상한다. 이 계약서는 승인하지 않고, PM이 아래 "분할안"대로 `/nexi-backlog split 4`를 실행하기를 권한다.

| 일 | 예상 |
|---|---|
| Playwright 설치·설정, 격리, 빌드 뒤 preview, 이번 실행이 띄운 서버만 내리기, `make screenshots`, 포트 검사, README, 클린 카피 재실행 | 4–5시간 |
| 토큰과 대비 테스트, 레이아웃 셸(넓은·좁은 내비게이션) | 2–3시간 |
| 기본 컴포넌트 4개(버튼, 입력, 표, 세 상태)와 Vitest | 3–4시간 |
| 참조 화면, 반응형·측정 e2e, 글꼴 번들과 글꼴 검증 | 2–3시간 |

**분할안.** 각 부분은 `main`에서 새로 시작하고 새 계약서를 쓴다. 이 계약서는 참고용이다.

- **A 「스크린샷·e2e 기반」** (선행 작업: #3).
  - 아래 격리 표, 기준 11–12, 기준 10의 "모든 요청은 localhost" 부분을 맡는다.
  - 기준 8의 측정 도우미 `frontend/e2e/support/layout.ts`도 맡는다.
  - 화면은 T#3의 임시 첫 화면을 찍는다. BRIEF 전이라 BRIEF 대조는 없다.
- **B 「컴포넌트·참조 화면」** (선행 작업: A).
  - BRIEF(`/nexi-design`)와 기준 1–10을 맡는다.
  - A가 만든 `make screenshots`로 참조 화면을 찍는다.
- 지금 #4를 선행 작업으로 둔 이슈(#6, #12–#18)는 B를 선행 작업으로 바꾼다. B는 A에 기대므로 A도 함께 기다리게 된다.

## 전제

- BRIEF는 이 계약서 초안 다음에 `/nexi-design 4`로 쓰고, 이 계약서와 함께 PM이 승인한다. 분할하면 B에서 쓴다. 아래에서 "BRIEF Tokens", "BRIEF Layout"처럼 부르는 값은 승인된 BRIEF의 해당 절에 있는 값이다. 테스트는 그 값을 기대값으로 옮겨 적고, 리뷰어는 BRIEF와 대조한다.
- 참조 화면은 T#3의 임시 첫 화면(`/`, 백엔드 상태 표시)을 대신한다. 백엔드 상태 표시는 그대로 남긴다(T#3 기준 7, 회귀 검사). 업무 화면이 생기면 그 태스크들이 `/`를 가져간다.
- 라우터는 넣지 않는다. 내비게이션 링크는 BRIEF Layout이 정한 경로를 가리키기만 하고, 라우팅·라우트 보호는 T#6이 맡는다.
- **반응형 회귀의 범위.** 이 태스크의 e2e는 참조 화면만 잰다. 다른 화면의 레이아웃 회귀는 이 검사로 잡히지 않는다. 화면을 만들거나 바꾸는 이후 태스크(T#6 로그인, T#12–T#18)는 각자 계약서에 자기 화면의 반응형 검사를 e2e로 더한다: 1280px, 360px, BRIEF breakpoint 양쪽에서 가로 넘침이 없는지 잰다. 그때 이 태스크의 측정 도우미(기준 8)를 쓰고, `make test`가 그 검사를 실행한다.

## 격리

e2e 검사(`make test`, `npm --prefix frontend run test:e2e`)와 `make screenshots`가 건드리는 대상과 그것을 고르는 방법은 아래와 같다. README의 "검사 격리" 표에도 같은 내용을 runner 옵션으로 적는다.

| 대상 | 값 | 정하는 법 |
|---|---|---|
| 백엔드 포트 | `18080` | `scripts/nexi-isolated.sh --root <저장소> --file DB_PATH=backend/data/e2e.db --set SERVER_PORT=18080 -- ./backend/mvnw -f backend/pom.xml spring-boot:run` |
| 백엔드 DB 파일 | `<저장소>/backend/data/e2e.db` (`*.db`라 git 제외) | 위 명령의 `--file DB_PATH=...` |
| 프런트엔드 포트 | `14173`. 이번 실행에서 막 빌드한 `frontend/dist`를 `vite preview --port 14173 --strictPort`로 띄운다 | 아래 "빌드 순서" |
| `/api` 프록시 대상 | e2e·스크린샷은 `http://localhost:18080`. 개발 서버 기본값은 `http://localhost:8080`(T#3과 같음) | `frontend/vite.config.ts`가 환경변수 `API_TARGET`을 읽고, 없으면 `http://localhost:8080`을 쓴다 |
| Playwright 브라우저 | 기본 `~/.cache/ms-playwright`, 격리 실행에서는 `<root>/.nexi-home/ms-playwright` | `--set PLAYWRIGHT_BROWSERS_PATH=<root>/.nexi-home/ms-playwright` |
| 스크린샷 출력 | `docs/screens/T<N>/` | `make screenshots T=<N>` |
| 외부 네트워크 | 쓰지 않는다 (D40) | 기준 10이 확인한다 |

**빌드 순서.** `test:e2e` 스크립트와 `make screenshots`는 먼저 `npm --prefix frontend run build`(`tsc -b && vite build`)로 그 시점의 소스를 빌드한다. 그 빌드가 성공한 뒤에만 `vite preview`를 띄워 검사하거나 찍는다. 빌드가 실패하면 서버를 띄우지 않고 실패한다. `make test`는 `test:e2e`를 부르므로 같은 순서를 따른다.

**서버를 띄우고 내리기.** e2e와 `make screenshots` 모두 다음을 지킨다.

- 서버를 띄우기 전에 18080과 14173을 둘 다 확인한다. 하나라도 쓰이고 있으면 아무 서버도 띄우지 않고, 그 포트를 쓰는 프로세스를 건드리지 않은 채 0이 아닌 코드로 끝난다. 다른 앱을 재사용하지 않는다(`reuseExistingServer: false`).
- 이번 실행이 띄운 프로세스(그 자식 JVM 포함)만 기억해 두었다가, 성공·실패·중단(Ctrl-C, SIGTERM) 어느 경우든 그것만 내린다.
- 포트나 이름으로 프로세스를 찾아 죽이지 않는다(`fuser -k`, `kill $(lsof -t -i:…)`, `pkill -f` 같은 방식을 쓰지 않는다).

## 수용 기준

1. **토큰.** `frontend/src/styles/tokens.css`가 BRIEF Tokens의 모든 토큰(색 역할, 글자 크기 단계, 간격 단계, 모서리 반경, 그림자)을 CSS 사용자 정의 속성으로 정의하고, 값은 BRIEF와 같다. BRIEF가 짝지은 글자색/배경색 쌍마다 WCAG 대비가 4.5:1 이상이다. 토큰 값은 이 파일 한 곳에만 있고, 컴포넌트 CSS는 `var(--…)`로만 색을 쓴다.
   - 확인: Vitest `frontend/src/styles/tokens.test.ts`. tokens.css 텍스트를 읽어 BRIEF 값 표와 비교하고 대비를 계산한다. 준비: 빈 `tokens.css`와 테스트. 레드: 첫 토큰이 없어 기대값 비교가 실패한다.
   - 확인: `grep -rnE "#[0-9a-fA-F]{3,8}\b|rgb\(" frontend/src --include=*.css | grep -v tokens.css`가 빈 결과다.
2. **레이아웃 셸.** `AppShell`이 `header`(banner), `nav`(navigation), `main` 랜드마크를 그린다. BRIEF Layout의 내비게이션 항목을 링크로 보여 주고, 현재 항목에는 `aria-current="page"`가 있다. 본문 최대 너비와 여백은 BRIEF Layout을 따른다.
   - 확인: Vitest `AppShell.test.tsx`. 준비: children만 그리는 스텁. 레드: `queryByRole('navigation')`가 null이라 `toBeInTheDocument()`가 실패한다.
3. **버튼.** `Button`이 BRIEF Components의 변형(variant)과 `disabled`, `loading` 상태를 가진다. `loading` 중에는 `aria-busy="true"`이고 클릭해도 `onClick`이 불리지 않으며 라벨 글자를 유지한다.
   - 확인: Vitest `Button.test.tsx`. 준비: 평범한 `<button>`을 그리는 스텁. 레드: `aria-busy`가 없고 loading 중 클릭에서 `onClick`이 불려 실패한다.
4. **입력과 입력 오류 메시지 (D33).** `TextField`는 라벨이 입력과 연결된다. `error`가 주어지면 메시지를 입력 바로 아래에 그리고, 입력에 `aria-invalid="true"`와 그 메시지를 가리키는 `aria-describedby`를 둔다.
   - 확인: Vitest `TextField.test.tsx`. 준비: 라벨 없는 `<input>` 스텁. 레드: `getByLabelText`/`aria-describedby` 기대가 실패한다.
5. **표.** `DataTable`이 열 정의와 행을 받아 `th scope="col"` 머리글과 행을 그린다. 숫자 열(투입률·가용률 같은 %)은 끝 정렬이다. 행이 없으면 넘겨받은 상태 컴포넌트를 표 자리에 보여 준다. 좁은 화면(BRIEF Layout의 좁은 구간)에서는 BRIEF가 정한 좁은 표시로 바뀌고, 표 안에도 가로 스크롤이 없다.
   - 확인: Vitest `DataTable.test.tsx`(머리글 `scope`, 숫자 열의 정렬 표시, 빈 행일 때 상태 컴포넌트)와 기준 8의 e2e(좁은 표시와 가로 넘침 없음). 준비: 빈 `<table>` 스텁. 레드: `columnheader` 개수 기대가 실패한다.
6. **세 상태 (D35).** `StateMessage`가 `empty`(빈 목록), `no-results`(검색 결과 없음), `error`(오류) 세 종류를 BRIEF Components가 정한 서로 다른 제목·설명·표시로 그린다. `error`는 `role="alert"`이고, `onRetry`가 있으면 "다시 시도" 버튼이 그것을 부른다.
   - 확인: Vitest `StateMessage.test.tsx`. 준비: `null`을 그리는 스텁. 레드: 종류별 제목 텍스트를 찾지 못해 실패한다.
7. **참조 화면.** `/`가 `AppShell` 안에 기준 2–6의 컴포넌트를 모두 보여 준다. 버튼은 변형별로, 그리고 disabled와 loading 상태로 둔다(loading 버튼 옆에 같은 라벨의 보통 버튼). 오류가 있는 입력과 없는 입력을 둔다. 표에는 BRIEF Formats대로 쓴 날짜·% 값과, 공백 없이 긴 값(40자 이상)이 있는 행을 넣는다. 세 상태를 모두 보여 준다. 백엔드 상태 표시는 그대로다. 표본 값은 화면 파일 안의 상수이고, API나 시드에서 오지 않는다.
   - 확인: 회귀 `App.test.tsx`(T#3 기준 7, 고치지 않고 통과)와 기준 8–11의 e2e·스크린샷.
8. **참조 화면의 반응형 (D29, D34).** 1280px, 360px, 그리고 BRIEF Layout의 각 breakpoint 양쪽(breakpoint−1px와 breakpoint px)에서 참조 화면을 잰다. 애니메이션·전환이 끝난 뒤 `document.documentElement.scrollWidth <= window.innerWidth`이고, 어떤 요소의 오른쪽 끝도 뷰포트를 넘지 않는다. 내비게이션은 넓은 구간과 좁은 구간에서 각각 BRIEF Layout이 정한 형태다. 긴 값은 BRIEF Formats대로 줄바꿈하거나 말줄임한다(말줄임이면 전체 값이 `title`에 있다). 가로 넘침 측정은 이후 화면 태스크가 다시 쓸 수 있게 `frontend/e2e/support/layout.ts`의 함수(예: 페이지와 너비 목록을 받아 넘침을 단언)로 둔다.
   - 확인: Playwright `frontend/e2e/design-system.spec.ts`. 준비: `@playwright/test` 설치, `playwright.config.ts`(위 격리 표의 `webServer` 두 개), 스펙 작성. 레드: 셸이 없어 페이지 로드 후 `nav` 개수가 0이라 `expect(count).toBe(1)`가 실패한다. 레드 단언은 기다리는 locator 대신 개수나 측정값으로 즉시 판정한다.
9. **잰 값.** 같은 e2e 스펙에서 1280px와 360px 각각:
   - `:root`의 계산된 토큰 값이 BRIEF Tokens와 같다(기준 1과 같은 값 표).
   - 입력 오류 메시지의 위쪽 끝과 입력의 아래쪽 끝 사이가 BRIEF Checks가 정한 간격 이하이고, 왼쪽 끝이 입력과 같다.
   - loading 버튼의 너비가 같은 라벨의 보통 버튼 너비와 같다.
   - Tab으로 버튼에 포커스하면 BRIEF Components의 포커스 표시(outline 너비·색)가 계산된 스타일에 나타난다.
   - 숫자 열 셀들의 오른쪽 끝이 같다.
   - 확인: Playwright `design-system.spec.ts`. 레드: 기준 8과 같다.
10. **글꼴과 네트워크 (D40).** BRIEF가 정한 글꼴 파일은 앱 번들(npm 의존성이나 저장소 파일)에서 온다. 참조 화면을 불러오고 `document.fonts.ready`를 기다린 뒤 다음이 모두 성립한다.
    - (a) 글꼴 파일 로드: 페이지가 보낸 `font` 종류 요청 중 하나 이상이 `http://localhost:14173/`에서 200으로 끝나고, 실패한 글꼴 요청은 없다.
    - (b) FontFace 로드: `document.fonts`에 family가 BRIEF 글꼴 이름인 `FontFace`가 하나 이상 있고, 참조 화면이 쓰는 굵기의 것은 `status === 'loaded'`다. `document.fonts.check()`는 쓰지 않는다. 선언된 글꼴이 없어도 true를 낼 수 있기 때문이다.
    - (c) 한글 표시: Chromium DevTools Protocol `CSS.getPlatformFontsForNode`로 참조 화면의 한글 제목 노드를 조회하면, 결과의 글꼴이 BRIEF 글꼴 하나뿐이고 시스템 대체 글꼴 항목이 없다. 이 기계처럼 한글 시스템 글꼴이 없는 환경에서도 성립해야 한다.
    - (d) 네트워크: 페이지가 보낸 모든 요청이 `localhost`로만 간다.
    - 확인: Playwright `design-system.spec.ts`(요청·응답 기록, `document.fonts` 조회, CDP 세션).
    - 레드: 글꼴을 번들하기 전이라 (b)에서 BRIEF 글꼴 이름의 `FontFace` 개수가 0이어서 `expect(count).toBeGreaterThan(0)`가 실패한다.
11. **`make screenshots T=<N>`.**
    - `T`가 비었거나 `frontend/e2e/screens/T<N>.spec.ts`가 없으면, 아무 서버도 띄우지 않고 이유를 출력한 뒤 0이 아닌 코드로 끝난다.
    - `T=4`이면 빌드 순서대로 프런트엔드를 빌드하고, 격리 표대로 백엔드(18080, `backend/data/e2e.db`)와 preview(14173)를 띄운다. `/api/health`가 응답하면 각 화면에서 셸 랜드마크(header·nav·main 각 1개)를 단언한 다음 `docs/screens/T4/reference-1280.png`와 `docs/screens/T4/reference-360.png`(전체 페이지)를 저장하고, 이번 실행이 띄운 서버만 내린다.
    - 확인 (a) 성공: `make screenshots T=4; echo $?`가 0이고 `ls docs/screens/T4/`에 두 PNG가 있다. 그 뒤 `curl -s -o /dev/null http://localhost:18080/api/health`와 `curl -s -o /dev/null http://localhost:14173`이 둘 다 실패하고, `pgrep -f backend/data/e2e.db`가 빈 결과다.
    - 확인 (b) 인자: `make screenshots T=999`와 `make screenshots`가 0이 아닌 코드로 끝나고, 그 뒤 두 포트에 응답이 없다.
    - 확인 (c) 포트 사용 중: `python3 -m http.server 18080 &`로 포트를 먼저 잡고 PID를 적어 둔다. `make screenshots T=4`가 0이 아닌 코드로 끝나고, 14173에 응답이 없고, PNG가 새로 쓰이지 않는다(실행 전후 `cksum` 같음). 그 PID가 살아 있고(`kill -0`) `curl http://localhost:18080/`이 여전히 응답한다. 14173을 먼저 잡은 경우도 같은 방법으로 확인한다. 끝나면 검사가 띄운 `http.server`만 그 PID로 내린다.
    - 확인 (d) 중단: `setsid make screenshots T=4 &`로 띄우고 18080이 응답하기 시작하면 그 프로세스 그룹에 SIGINT를 보낸다. 끝난 뒤 두 포트에 응답이 없고 `pgrep -f backend/data/e2e.db`가 빈 결과다.
    - 준비: 지금의 `echo "not set up yet"` 자리표시자를 실제 명령으로 바꾸고 `T4.spec.ts`를 쓴다. 레드: 셸이 없어 랜드마크 개수 단언이 실패하고 PNG가 생기지 않는다. 자리표시자의 exit 1은 레드가 아니다.
12. **make 명령과 README.** `make test`가 백엔드 테스트, Vitest, `npm --prefix frontend run test:e2e`(빌드 뒤 preview로 `design-system.spec.ts` 실행)를 모두 실행해 통과한다. e2e도 기준 11의 서버 규칙을 지킨다. `make lint`는 새 파일(`e2e/` 포함)까지 검사해 통과하고, `make build`도 통과한다. README에는 다음을 더한다.
    - Playwright 버전과 브라우저 설치 명령(`npx --prefix frontend playwright install chromium`, Linux에서 시스템 라이브러리가 없을 때의 안내 포함)을 설치 순서 안에 둔다.
    - `make screenshots T=<N>` 사용법을 적는다.
    - 격리 표, 빌드 순서, 서버를 띄우고 내리는 규칙을 runner 옵션으로 옮긴다.
    - 확인: `frontend/package.json`의 `test:e2e`와 `Makefile`의 `screenshots`가 빌드 다음에 preview를 띄우는 순서임을 읽는다. `make test` 출력에서 `vite build` 출력이 Playwright 실행보다 앞에 있음을 증거에 남긴다.
    - 확인: 회귀 검사인 T#3 기준 8의 클린 카피 검사를 이 태스크 커밋으로 다시 실행한다. 새 clone에서 README 순서대로(브라우저 설치는 `--set PLAYWRIGHT_BROWSERS_PATH=<clone>/.nexi-home/ms-playwright`) 설치, `make build`, `make test`, `make lint`를 실행하면 모두 성공하고, 그 뒤 `git status --porcelain --untracked-files=all`이 빈 출력이다.

## 검증 명령

- 새 검사:
  - `npm --prefix frontend run test`: Vitest. 기준 1–6의 새 테스트 파일이다.
  - `npm --prefix frontend run test:e2e`: 빌드 뒤 preview로 Playwright `design-system.spec.ts`를 실행한다. 기준 8–10이다.
  - `make screenshots T=4`와 기준 11의 (a)–(d) 절차.
  - `grep` 검사(기준 1).
  - 각 검사의 준비와 레드 단언은 위 기준에 적었다.
- 회귀 검사:
  - `make build`, `make test`, `make lint`는 작업 전과 후에 모두 통과해야 한다. 작업 후의 `make test`에는 e2e가 들어간다.
  - `App.test.tsx`(T#3 기준 7)와 백엔드 `ApplicationStartupTest`, `HealthControllerTest`는 고치지 않고 통과해야 한다.
  - T#3 기준 8의 클린 카피 검사를 이 태스크 커밋에서 실행한다(기준 12).
