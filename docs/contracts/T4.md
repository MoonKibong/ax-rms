# T#4 Design system: BRIEF 기반 토큰·레이아웃·기본 컴포넌트와 make screenshots

## 산출물

승인된 `docs/design/BRIEF.md`를 옮긴 프런트엔드 디자인 시스템이 있다. 토큰, 반응형 레이아웃 셸, 기본 컴포넌트, 이것들을 모아 보여 주는 참조 화면 하나로 이루어지고, `make screenshots T=<N>`이 앱을 띄워 계약서가 정한 화면을 1280px·360px로 찍어 `docs/screens/T<N>/`에 저장한 뒤 이번 실행이 띄운 서버만 내린다.

## 작업량

PM 결정(이슈 #4, 2026-10-13)에 따라 나누지 않는다. 하루에 끝나도록 앞 초안에서 다음을 뺐다. 뺀 항목은 "하지 않을 일"에도 적었다.

- 글꼴 CDP 검사(`CSS.getPlatformFontsForNode`): 글꼴은 파일 로드와 `FontFace` 로드로 확인한다. 한글이 Pretendard로 보이는지는 리뷰어가 PNG로 대조한다(BRIEF Checks 2). 이 기계에는 한글 시스템 글꼴이 없어서, 글꼴이 빠지면 PNG에 네모(□)가 보인다.
- 중단(SIGINT) 시나리오와 14173 포트 사용 중 시나리오: 포트 검사는 "18080 사용 중" 하나로 줄였다. 중단 처리 코드(trap)는 리뷰어가 읽는다.
- e2e의 계산된 토큰 값 비교: 기준 1의 `tokens.test.ts`와 같은 내용이라 뺐다.
- breakpoint 일반화: 너비를 1280px, 1024px, 1023px, 360px 네 가지로 고정했다(BRIEF의 breakpoint는 1024px 하나다).
- 클린 카피 재실행: README 순서대로 새 clone에서 빌드·테스트하는 일은 `nexi-finish`가 마지막에 한다.

## 전제

- BRIEF는 `docs/design/BRIEF.md`(커밋 `699cb18`의 초안)이고, 이 계약서와 함께 PM이 승인한다. 아래에서 "BRIEF Tokens", "BRIEF Layout"처럼 부르는 값은 승인된 BRIEF의 해당 절에 있는 값이다. 테스트는 그 값을 기대값으로 옮겨 적고, 리뷰어는 BRIEF와 대조한다.
- BRIEF Checks의 "(e2e: …)" 표시 가운데 이 계약서가 재지 않는 것(2의 `CSS.getPlatformFontsForNode`, 11의 계산된 토큰 값)은 리뷰어가 PNG와 `tokens.test.ts`로 대조한다.
- 참조 화면은 T#3의 임시 첫 화면(`/`, 백엔드 상태 표시)을 대신한다. 백엔드 상태 표시는 그대로 남긴다(T#3 기준 7, 회귀 검사). 업무 화면이 생기면 그 태스크들이 `/`를 가져간다.
- 라우터는 넣지 않는다. 내비게이션 링크는 BRIEF Layout이 정한 경로를 가리키기만 하고, 라우팅·라우트 보호는 T#6이 맡는다.
- **반응형 회귀의 범위.** 이 태스크의 e2e는 참조 화면만 잰다. 다른 화면의 레이아웃 회귀는 이 검사로 잡히지 않는다. 화면을 만들거나 바꾸는 이후 태스크(T#6 로그인, T#12–T#18)는 각자 계약서에 자기 화면의 반응형 검사를 e2e로 더한다. 1280px, 1024px, 1023px, 360px에서 가로 넘침이 없는지 재고, 이 태스크의 측정 도우미(기준 8)를 쓴다. `make test`가 그 검사를 실행한다.

## 격리와 서버

e2e(`npm --prefix frontend run test:e2e`, `make test`)와 `make screenshots`는 같은 서버 스크립트 `scripts/e2e-servers.sh -- <명령>`으로 서버를 띄우고 내린다. Playwright `webServer`는 쓰지 않는다. README의 "검사 격리" 표에도 같은 내용을 runner 옵션으로 적는다.

| 대상 | 값 | 정하는 법 |
|---|---|---|
| 백엔드 포트 | `18080` | 백엔드를 `scripts/nexi-isolated.sh --root <저장소> --file DB_PATH=backend/data/e2e.db --set SERVER_PORT=18080 -- ./backend/mvnw -f backend/pom.xml spring-boot:run`으로 띄운다 |
| 백엔드 DB 파일 | `<저장소>/backend/data/e2e.db` (`*.db`라 git 제외) | 위 명령의 `--file DB_PATH=...` |
| 프런트엔드 포트 | `14173`. 방금 빌드한 `frontend/dist`를 `vite preview --port 14173 --strictPort`로 띄운다 | 서버 스크립트 |
| `/api` 프록시 대상 | e2e·스크린샷은 `http://localhost:18080`. 개발 서버 기본값은 `http://localhost:8080`(T#3과 같음) | `frontend/vite.config.ts`가 환경변수 `API_TARGET`을 읽고, 없으면 `http://localhost:8080`을 쓴다 |
| 띄운 서버 기록 | `<저장소>/.nexi-tmp/e2e-servers.pids` (`.nexi-tmp/`는 git 제외). 이번 실행이 띄운 두 프로세스 그룹 ID를 한 줄에 하나씩 쓴다 | 서버 스크립트. 다음 실행이 덮어쓴다 |
| Playwright 브라우저 | 기본 `~/.cache/ms-playwright`. 격리 실행에서는 `<root>/.nexi-home/ms-playwright` | `--set PLAYWRIGHT_BROWSERS_PATH=<root>/.nexi-home/ms-playwright` |
| 스크린샷 출력 | `docs/screens/T<N>/` | `make screenshots T=<N>` |
| 외부 네트워크 | 쓰지 않는다 (D40) | 기준 10이 확인한다 |

서버 스크립트는 이 순서로 동작한다. Linux와 macOS의 bash에서 같게 동작해야 하며, `setsid`처럼 한쪽 OS에만 있는 명령은 쓰지 않는다.

1. 18080과 14173이 비어 있는지 확인한다. 하나라도 쓰이고 있으면 아무것도 띄우지 않고, 그 포트를 쓰는 프로세스를 건드리지 않는다. `포트 18080 사용 중`처럼 포트 번호를 적은 메시지를 내고 0이 아닌 코드로 끝난다.
2. `npm --prefix frontend run build`(`tsc -b && vite build`)로 그 시점의 소스를 빌드한다. 실패하면 서버를 띄우지 않고 끝난다.
3. 백엔드와 preview를 각각 자기 프로세스 그룹으로 띄우고(예: bash `set -m`), 두 그룹 ID를 기록 파일에 쓴다.
4. `http://localhost:14173/api/health`가 응답할 때까지 기다린다(최대 120초). 응답이 없으면 실패로 끝난다.
5. 명령을 실행한다.
6. 성공·실패·중단(EXIT, INT, TERM trap) 어느 경우든 기록한 그룹에만 TERM을 보낸다. 10초 안에 끝나지 않으면 KILL을 보낸다.
7. 명령의 종료 코드로 끝난다.

포트나 이름으로 프로세스를 찾아 죽이지 않는다(`fuser -k`, `kill $(lsof -t -i:…)`, `pkill -f` 같은 방식은 쓰지 않는다).

## 수용 기준

1. **토큰.** `frontend/src/styles/tokens.css`가 BRIEF Tokens의 모든 토큰(색, 글자 크기·줄 높이·굵기, 간격, 반경, 그림자, 크기)을 CSS 사용자 정의 속성으로 정의하고, 값은 BRIEF와 같다. BRIEF 2.1절의 글자/배경 쌍마다 WCAG 대비가 4.5:1 이상이다. 컴포넌트 CSS는 색·그림자를 `var(--…)`로만 쓴다.
   - 확인: Vitest `frontend/src/styles/tokens.test.ts`. tokens.css 텍스트를 읽어 BRIEF 값 표와 비교하고 대비를 계산한다. 준비: 빈 `tokens.css`와 테스트. 레드: 첫 토큰이 없어 기대값 비교가 실패한다.
   - 확인: `grep -rnE "#[0-9a-fA-F]{3,8}\b|rgba?\(" frontend/src --include=*.css | grep -v tokens.css`가 빈 결과다.
2. **레이아웃 셸.** `AppShell`이 `header`(banner), `nav`(navigation), `main` 랜드마크를 그린다. BRIEF Layout의 내비게이션 항목(대시보드, 직원, 프로젝트)을 링크로 보여 주고, 현재 항목에는 `aria-current="page"`가 있다. 넓은 구간과 좁은 구간의 모양은 BRIEF Layout을 따른다.
   - 확인: Vitest `AppShell.test.tsx`. 준비: children만 그리는 스텁. 레드: `queryByRole('navigation')`가 null이라 `toBeInTheDocument()`가 실패한다.
3. **버튼.** `Button`이 `primary`, `secondary`, `danger` 변형과 `disabled`, `loading` 상태를 가진다. `loading` 중에는 `aria-busy="true"`이고 클릭해도 `onClick`이 불리지 않으며 라벨 글자가 DOM에 남는다.
   - 확인: Vitest `Button.test.tsx`. 준비: 평범한 `<button>`을 그리는 스텁. 레드: `aria-busy`가 없고 loading 중 클릭에서 `onClick`이 불려 실패한다.
4. **입력과 입력 오류 메시지 (D33).** `TextField`는 라벨이 입력과 연결된다. `error`가 주어지면 메시지를 입력 바로 아래에 그리고, 입력에 `aria-invalid="true"`와 그 메시지를 가리키는 `aria-describedby`를 둔다.
   - 확인: Vitest `TextField.test.tsx`. 준비: 라벨 없는 `<input>` 스텁. 레드: `getByLabelText`와 `aria-describedby` 기대가 실패한다.
5. **표.** `DataTable`이 열 정의와 행을 받아 `th scope="col"` 머리글과 행을 그린다. 숫자 열은 끝 정렬이다. 행이 없으면 넘겨받은 상태 컴포넌트를 표 자리에 보여 준다. 좁은 구간(<1024px)에서는 BRIEF 3.3절의 카드 표시로 바뀐다.
   - 확인: Vitest `DataTable.test.tsx`(머리글 `scope`, 숫자 열의 정렬 표시, 빈 행일 때 상태 컴포넌트)와 기준 8의 e2e(카드 표시와 가로 넘침 없음). 준비: 빈 `<table>` 스텁. 레드: `columnheader` 개수 기대가 실패한다.
6. **세 상태 (D35).** `StateMessage`가 `empty`, `no-results`, `error` 세 종류를 BRIEF 3.4절의 아이콘·기본 제목·설명으로 그린다. `error`는 `role="alert"`이고 `onRetry`가 있으면 "다시 시도" 버튼이 그것을 부른다. `no-results`는 `onReset`이 있으면 "필터 초기화" 버튼이 그것을 부른다.
   - 확인: Vitest `StateMessage.test.tsx`. 준비: `null`을 그리는 스텁. 레드: 종류별 기본 제목을 찾지 못해 실패한다.
7. **참조 화면.** `/`가 BRIEF 6.0절대로 `AppShell` 안에 기준 2–6의 컴포넌트를 모두 보여 준다. 여기에는 같은 라벨 "저장"의 보통 버튼과 loading 버튼, 오류 입력, 48자 영문 값이 있는 표, 세 상태가 들어간다. 백엔드 상태 표시는 그대로이고, 표본 값은 화면 파일 안의 상수다.
   - 확인: 회귀 `App.test.tsx`(T#3 기준 7, 고치지 않고 통과)와 기준 8–11의 e2e·스크린샷.
8. **참조 화면의 반응형 (D29, D34).** 1280px, 1024px, 1023px, 360px에서 참조 화면을 잰다.
   - 전환이 끝난 뒤 `document.documentElement.scrollWidth <= window.innerWidth`이고, 어떤 요소의 오른쪽 끝도 뷰포트를 넘지 않는다.
   - 1280px와 1024px에서는 nav가 세로 사이드바(너비 220px)이고, 1023px와 360px에서는 header 아래 가로 탭 막대다.
   - 48자 값은 칸 안에서 줄바꿈된다(그 칸의 `scrollWidth <= clientWidth`).
   - 가로 넘침 측정은 이후 화면 태스크가 다시 쓸 수 있게 `frontend/e2e/support/layout.ts`의 함수(페이지와 너비 목록을 받아 넘침을 단언)로 둔다.
   - 확인: Playwright `frontend/e2e/design-system.spec.ts`. 준비: `@playwright/test` 설치와 `playwright.config.ts`(baseURL `http://localhost:14173`), 스펙 작성. 레드: 셸이 없어 페이지 로드 후 `nav` 개수가 0이라 `expect(count).toBe(1)`가 실패한다. 레드 단언은 기다리는 locator 대신 개수나 측정값으로 즉시 판정한다.
9. **잰 값.** 같은 e2e 스펙에서 1280px와 360px 각각 다음을 잰다.
   - 입력 오류 메시지의 위쪽 끝과 입력의 아래쪽 끝 사이가 4px 이하이고, 왼쪽 끝이 입력과 같다(BRIEF Checks 6).
   - loading 버튼의 너비가 같은 라벨의 보통 버튼 너비와 같다(BRIEF Checks 5).
   - Tab으로 primary 버튼에 포커스하면 계산된 `outline-width`가 `2px`, `outline-color`가 `rgb(41, 82, 204)`이다(BRIEF Checks 10).
   - 1280px에서 숫자 열 셀들의 오른쪽 끝이 같다(BRIEF Checks 7).
   - 확인: Playwright `design-system.spec.ts`. 레드: 기준 8과 같다.
10. **글꼴과 네트워크 (D40).** Pretendard 글꼴 파일은 앱 번들(npm `pretendard`)에서 온다. 참조 화면을 불러오고 `document.fonts.ready`를 기다린 뒤 다음이 모두 성립한다.
    - (a) 파일 로드: 페이지가 보낸 `font` 종류 요청 중 하나 이상이 `http://localhost:14173/`에서 200으로 끝나고, 실패한 글꼴 요청은 없다.
    - (b) FontFace 로드: `document.fonts`에 family가 `Pretendard`인 `FontFace` 가운데 `status === 'loaded'`인 것이 하나 이상 있다. `document.fonts.check()`는 선언된 글꼴이 없어도 true를 낼 수 있으므로 쓰지 않는다.
    - (c) 네트워크: 페이지가 보낸 모든 요청이 `localhost`로만 간다.
    - 확인: Playwright `design-system.spec.ts`(요청·응답 기록, `document.fonts` 조회). 한글이 실제로 Pretendard로 그려지는지는 리뷰어가 PNG로 대조한다(BRIEF Checks 2).
    - 레드: 글꼴을 번들하기 전이라 loaded 상태인 `Pretendard` `FontFace` 개수가 0이어서 `expect(count).toBeGreaterThan(0)`가 실패한다.
11. **`make screenshots T=<N>`과 서버 정리.** `T=4`이면 서버 스크립트로 `frontend/e2e/screens/T4.spec.ts`를 실행한다. 이 스펙은 각 너비에서 셸 랜드마크(header·nav·main 각 1개)를 단언한 다음 `docs/screens/T4/reference-1280.png`와 `docs/screens/T4/reference-360.png`(전체 페이지)를 저장한다.
    - (a) 성공: `make screenshots T=4; echo $?`가 0이고 두 PNG가 있다. 이어서 다음을 확인한다.
      - `.nexi-tmp/e2e-servers.pids`의 각 그룹 ID에 대해 `kill -0 -- -<그룹 ID>`가 실패한다(살아 있는 프로세스 없음).
      - `curl -s -o /dev/null http://localhost:18080/api/health`와 `curl -s -o /dev/null http://localhost:14173/`이 둘 다 실패한다.
    - (b) 인자: `make screenshots T=999`와 `make screenshots`(T 없음)가 0이 아닌 코드로 끝난다. 출력에는 각각 `screenshots: frontend/e2e/screens/T999.spec.ts 없음`과 `screenshots: T가 필요합니다 (예: make screenshots T=4)`가 있다. 그 뒤 두 포트에 응답이 없다.
    - (c) 포트 사용 중: (a) 다음에 이 순서로 확인한다.
      - `node -e "require('http').createServer((q,s)=>s.end('busy')).listen(18080)" & busy=$!`로 18080을 먼저 잡는다.
      - 두 PNG의 `cksum`을 적어 둔다.
      - `make screenshots T=4`가 0이 아닌 코드로 끝나고, 출력에 `포트 18080 사용 중`이 있다.
      - `kill -0 $busy`가 성공하고, `curl -s http://localhost:18080/`이 `busy`를 돌려준다.
      - 14173에 응답이 없고, 두 PNG의 `cksum`이 그대로다.
      - 끝나면 `kill $busy`로 이 검사가 띄운 프로세스만 내린다.
    - 준비와 레드 (b)·(c): 명령을 그대로 실행하기만 하는 서버 스크립트 스텁과, 그것을 부르는 `Makefile` `screenshots` 타깃을 만든다. 레드는 출력에 위 메시지가 없어서 `grep -F` 단언이 실패하는 것이다. 지금 자리표시자의 `not set up yet`(exit 1)은 레드가 아니다.
    - 준비와 레드 (a): 서버 스크립트의 포트 확인·빌드·시작·기록·종료를 만든 뒤, 셸이 없는 상태에서 실행한다. 레드는 랜드마크 개수 단언이 실패하고 PNG가 생기지 않는 것이다.
12. **make 명령과 README.** `make test`가 백엔드 테스트, Vitest, `npm --prefix frontend run test:e2e`(서버 스크립트로 `design-system.spec.ts` 실행)를 모두 실행해 통과한다. `make lint`는 새 TypeScript 파일(`e2e/` 포함)까지 검사해 통과하고(셸 스크립트는 lint 대상이 아니다), `make build`도 통과한다. README에는 다음을 더한다.
    - Playwright 버전과 브라우저 설치 명령(`npx --prefix frontend playwright install chromium`, Linux에서 시스템 라이브러리가 없을 때의 안내 포함)을 설치 순서 안에 둔다.
    - `make screenshots T=<N>` 사용법을 적는다.
    - 위 "격리와 서버" 표와 서버 스크립트의 동작을 적는다.
    - 확인: README를 읽는다. `make test` 출력에서 `vite build` 출력이 Playwright 실행보다 앞에 있음을 증거에 남긴다.
