# T#53 변경: 배치 계산 순서와 후보 조회 기간 제한

변경 대상: T#10, T#17 (구현 변경, 배포된 대상 없음 — D40). T#10·T#17의 계약서·증거·판정은 고치지 않는다.

## 산출물

배치 생성·수정·후보 조회가 하루 단위 계산에 들어가기 전에 기간 길이를 검사해 366일(시작일·종료일 포함)을 넘는 요청을 `400 ASSIGNMENT_PERIOD_TOO_LONG`으로 거절하고, 후보 조회가 직원마다 배치를 따로 읽지 않고 배치를 한 번에 읽으며, 인력 배치 화면이 그 기간을 입력 아래에 알려 후보 요청을 보내지 않는다.

## 바뀌는 동작 (PM 승인 대상, 아래 `(제안)`은 값 선택)

| 항목 | 지금 | 바뀐 뒤 |
|---|---|---|
| 기간 길이 | 제한 없음. `0001-01-01~9999-12-31` 요청 하나가 날짜 수백만 건을 돈다 | 시작일~종료일(포함) **최대 366일** `(제안)`. 넘으면 400 `ASSIGNMENT_PERIOD_TOO_LONG`, 메시지 "배치 기간은 최대 366일입니다." |
| 적용 대상 | – | 배치 생성(`POST`), 수정 뒤의 기간(`PATCH`, 준 값과 기존 값을 합친 기간), 후보 조회(`GET .../candidates`) |
| 검사 순서 | 기간 형식 → 투입률(D14) → 존재 → … | 기간 형식(`ASSIGNMENT_REQUEST_INVALID`) → **기간 길이** → 투입률(D14) → 존재 → … 나머지는 T#10 그대로 |
| 오류 우선순위 | D8·D27 순서는 T#10 표대로 | **바뀌지 않는다** `(제안)`. 366일 상한이 날짜 반복을 366회로 묶으므로 투입 불가·가용률 0·초과·프로젝트 기간·중복의 순서를 그대로 둔다 |
| 후보 조회 쿼리 | 직원마다 `findByEmployeeId` (N+1) | 배치 `findAll` 한 번을 직원별로 묶어 계산. 응답 모양·값은 그대로 |
| 366일보다 긴 프로젝트 | 한 배치가 프로젝트 전체를 덮을 수 있다 | 한 배치는 366일까지. 더 긴 구간은 이어지는 배치 여러 개로 나눠 만든다(D27: 겹치지 않으면 허용). 배치 화면의 처음 기간은 프로젝트 시작일부터 366일로 줄인다 |
| 해제(`DELETE`) | – | 바뀌지 않는다(길이와 무관하게 항상 가능) |

## 수용 기준

모든 백엔드 테스트는 시드(`AbstractSeedTest`, "오늘" = 2026-06-15)를 쓰고 직원·프로젝트 ID는 이름으로 찾는다. 긴 프로젝트가 필요한 검사는 프로젝트 저장소로 `2026-01-01..2027-12-31` 프로젝트를 테스트 안에서 만든다(시드를 바꾸지 않는다).

1. **상한 경계 (생성).** 긴 프로젝트에 E3(이수민)을 `2026-01-01..2027-01-01`(366일) 20%로 `POST` → 201. `2026-01-01..2027-01-02`(367일) → 400 `ASSIGNMENT_PERIOD_TOO_LONG`, 저장된 배치 수가 늘지 않는다 — 확인: `AllocationPeriodLimitTest.createBoundary`.
2. **극단 기간 (생성).** `0001-01-01..9999-12-31`로 `POST` → 400 `ASSIGNMENT_PERIOD_TOO_LONG`, 2초 안에 응답, 저장된 배치 수가 늘지 않는다 — 확인: `AllocationPeriodLimitTest.extremePeriodIsRejectedFast`(`assertTimeoutPreemptively`).
3. **수정.** 366일짜리 배치를 만든 뒤 `endDate`만 하루 늘려 `PATCH` → 400 `ASSIGNMENT_PERIOD_TOO_LONG`, 배치 값이 그대로. 투입률만 `PATCH` → 200 — 확인: `AllocationPeriodLimitTest.modifyChecksResultingPeriod`.
4. **후보 조회.** 366일 기간 → 200. 367일 → 400 `ASSIGNMENT_PERIOD_TOO_LONG`. `0001-01-01..9999-12-31` → 400, 2초 안에 응답 — 확인: `AllocationPeriodLimitTest.candidatesBoundary`.
5. **우선순위.** 시작일이 종료일보다 늦으면(그리고 길이가 아무리 길어도) `ASSIGNMENT_REQUEST_INVALID`가 먼저. 기간이 너무 길고 투입률이 7이면 `ASSIGNMENT_PERIOD_TOO_LONG`이 `ASSIGNMENT_INVALID_PERCENT`보다 먼저. 존재하지 않는 직원 ID와 너무 긴 기간이 함께면 `ASSIGNMENT_PERIOD_TOO_LONG`(404가 아님) — 확인: `AllocationPeriodLimitTest.priority`.
6. **N+1 제거.** `AssignmentService.candidates`가 `AssignmentRepository.findByEmployeeId`를 부르지 않고 `findAll`을 한 번 부른다. 직원 20명 시드로 호출 수를 센다(세는 가짜 저장소를 서비스에 직접 주입하는 단위 검사) — 확인: `AssignmentServiceCandidatesQueryTest.readsAssignmentsOnce`.
7. **회귀 (T#10 기준 1–15).** 기존 `Allocation*Test`가 고치지 않고 그대로 통과한다. 특히 `AllocationCreateTest.noAvailability`(같은 프로젝트에서 `NO_AVAILABILITY`가 `OVERLAP`보다 먼저)와 `AllocationCandidatesTest.candidateList`(박소영 40, 최동훈 `UNAVAILABLE`)가 같은 값이다 — 확인: `./backend/mvnw -f backend/pom.xml test -Dtest='Allocation*Test'` (baseline: `origin/main` `ca3fad9`, 지금 통과).
8. **화면: 기간 길이 알림.** 인력 배치 화면에서 시작·종료 기간이 366일을 넘으면 종료일 입력 아래(`TextField` `error`)에 "배치 기간은 최대 366일입니다."가 보이고 `aria-invalid="true"`이며, 그 기간으로는 후보 요청이 나가지 않는다. 366일이면 요청이 나간다. 저장 버튼은 기존 `checkInput`처럼 요청 없이 막는다. 프로젝트 기간이 366일보다 길면 처음 기간의 종료일은 시작일부터 366일째다 — 확인: Vitest `ProjectAssignPage.test.tsx`(새 사례).
9. **화면: 서버 오류 연결.** 서버가 `ASSIGNMENT_PERIOD_TOO_LONG`을 돌려주면 `api/assignments.ts`가 기간 입력 오류로 분류해 같은 자리에 보인다 — 확인: Vitest `ProjectAssignPage.test.tsx`의 기존 표(`ASSIGNMENT_REQUEST_INVALID` 줄 옆)에 이 코드를 더한 사례.
10. **화면 모양 (e2e, 가로챈 값 없음).** 1280px·360px에서 시드의 알파 프로젝트 배치 화면의 종료일을 2027-12-31로 바꾸면 메시지가 종료일 입력 바로 아래(간격 ≤ 4px)에 위험 색(`rgb(191, 43, 27)`)으로 보이고 가로 넘침이 없다 — 확인: Playwright `frontend/e2e/projects-assign.spec.ts`의 새 사례(`expectNoHorizontalOverflow`).
11. **회귀 (전체).** `make build`, `make test`, `make lint`가 통과한다.

## 검증 명령

- 새 검사:
  - `./backend/mvnw -f backend/pom.xml test -Dtest='AllocationPeriodLimitTest,AssignmentServiceCandidatesQueryTest'` — 기준 1–6.
  - `npm --prefix frontend run test -- ProjectAssignPage` — 기준 8–9.
  - `bash scripts/e2e-servers.sh -- npm --prefix frontend run e2e:run -- projects-assign.spec.ts` — 기준 10 (읽기만, 공유 e2e DB).
- 시작 전 준비(구현 단계, 기능 코드 전): 새 테스트 클래스·사례를 만들고 `ASSIGNMENT_PERIOD_TOO_LONG` 상수와 호출 대상 메서드가 없어도 컴파일되도록 필요한 최소 틀만 둔다.
- 레드(기능 전에 실패해야 하는 단언):
  - 기준 1: 367일 `POST`가 지금은 201이라 `status == 400` 단언 실패.
  - 기준 2·4: 극단 기간 요청이 400 `ASSIGNMENT_PERIOD_TOO_LONG`이 아니라 시간 초과 또는 다른 응답이라 `assertTimeoutPreemptively`·`code` 단언 실패.
  - 기준 3: 367일로 늘린 `PATCH`가 지금은 200.
  - 기준 5: 코드가 `ASSIGNMENT_INVALID_PERCENT`·`..._EMPLOYEE_NOT_FOUND`라 `code` 단언 실패.
  - 기준 6: `findByEmployeeId` 호출이 직원 수만큼이라 `isZero()` 단언 실패.
  - 기준 8–10: 긴 기간에서도 후보 요청이 나가고 메시지가 없다.
- 회귀 검사: 기준 7·11. `make test`, `make lint`, `make build`는 작업 전후 모두 통과해야 한다.

## 하지 않을 일

- 배치 날짜별 계산을 "경계 날짜만 보는 방식"으로 바꾸기(`AvailabilityCalculator` 변경, T#7 대상) — 366일 상한으로 비용이 묶이므로 이번엔 하지 않는다. 필요하면 별도 변경 이슈.
- D8·D27의 오류 우선순위 바꾸기, 새 DB 인덱스·저장소 메서드 추가(`findAll`은 이미 있다).
- 프로젝트 등록·수정(T#9·T#34)의 기간 길이 제한 — 프로젝트 자체는 이전과 같이 긴 기간을 허용한다.
- 이미 저장된 366일 넘는 배치의 이전·정리(시드에는 없는 것으로 본다). 그런 배치는 기간을 줄이거나 해제할 수 있고, 투입률만 고치는 `PATCH`는 길이 검사에 걸린다.
- 세션 만료·폼 오류 연결·배치 저장 뒤 복구(#55, #58), 오류 처리기 통합(#56), 동시성(#54).
- 후보 조회의 무효 기간 표시, `ProjectAssignPage` 구조 정리.
