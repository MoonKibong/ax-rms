## 프로젝트 API

### 목록 — `GET /api/projects`

쿼리 매개변수 `status`(선택): `PLANNED`, `IN_PROGRESS`, `DONE`, `ON_HOLD` 중 하나. 주면 그 상태의 프로젝트만 돌려준다. 그 밖의 값은 400 `PROJECT_STATUS_INVALID`.

응답 200, 배열, `id` 오름차순. 항목:

```json
{
  "id": 1, "name": "알파 프로젝트", "startDate": "2026-05-16", "endDate": "2026-09-13", "status": "IN_PROGRESS",
  "requiredHeadcount": 2, "assignedHeadcount": 3
}
```

### 상세 — `GET /api/projects/{id}`

응답 200:

```json
{
  "id": 1, "name": "알파 프로젝트", "description": "사내 포털 리뉴얼",
  "startDate": "2026-05-16", "endDate": "2026-09-13", "status": "IN_PROGRESS",
  "requiredSkills": [
    {"jobTitle": "백엔드 개발자", "skillName": "Java", "proficiencyLevel": "INTERMEDIATE", "headcount": 2}
  ],
  "requiredHeadcount": 2, "assignedHeadcount": 3,
  "assignments": [
    {"assignmentId": 13, "employeeId": 14, "employeeName": "권지안",
     "startDate": "2026-05-18", "endDate": "2026-09-08", "allocationPercent": 45, "currentAvailability": 55}
  ]
}
```

- `requiredSkills`는 필요 역량 줄(D22) 전부를 줄 `id` 오름차순으로 담는다. 줄이 없으면 빈 배열이다.
- **인력 현황 (제안).** `requiredHeadcount`는 줄별 `headcount`의 합계(D22)이고, `assignedHeadcount`는 오늘(D19, 서버 시계) 이 프로젝트에 배치된 서로 다른 직원 수다. 배정 기간이 오늘을 포함하는 직원만 센다(D20의 "오늘 배치된 인원"과 같은 기준이다). 프로젝트 상태·종료 여부는 따지지 않는다.
- `assignments`는 그 프로젝트의 전체 배치(오늘이 기간 밖인 것 포함)를 `startDate` 오름차순, 같으면 `employeeName`, 그래도 같으면 `assignmentId` 오름차순으로 담는다. 직원이 가진 모든 프로젝트의 배치로 계산한 `currentAvailability`(종료된 프로젝트 제외, D7·D19)를 함께 보인다.
- 없는 id는 404 `{"code": "PROJECT_NOT_FOUND", "message": "프로젝트를 찾을 수 없습니다."}`.

### 등록 — `POST /api/projects`

요청 본문: `{"name", "description", "startDate", "endDate", "status", "requiredSkills": [{"jobTitle", "skillName", "proficiencyLevel", "headcount"}]}`. `description`은 선택(없으면 `null`), `requiredSkills`는 없으면 빈 배열이다(줄 0개를 허용한다. 제안). 상태는 요청의 값을 그대로 쓴다(제안).

성공: 201, `Location: /api/projects/{새 id}`, 본문은 상세와 같은 모양이다(`assignments`는 빈 배열, `assignedHeadcount` 0).

검증 실패는 모두 400이고, 아래 표의 위에서부터 처음 걸리는 하나만 돌려준다.

| 조건 | code | message |
|---|---|---|
| 본문이 JSON이 아니거나 읽을 수 없다 | `PROJECT_REQUEST_INVALID` | 요청 본문을 읽을 수 없습니다. |
| `name`이 없거나 공백뿐이다 | `PROJECT_NAME_REQUIRED` | 프로젝트명을 입력하세요. |
| `startDate`나 `endDate`가 없거나 `YYYY-MM-DD` 날짜가 아니다 | `PROJECT_PERIOD_REQUIRED` | 시작일과 종료일을 YYYY-MM-DD 형식으로 입력하세요. |
| `endDate`가 `startDate`보다 앞선다(같은 날은 허용) | `PROJECT_PERIOD_INVALID` | 종료일은 시작일보다 앞설 수 없습니다. |
| `status`가 없거나 네 값이 아니다 | `PROJECT_STATUS_INVALID` | 프로젝트 상태를 선택하세요. |
| 필요 역량 줄의 `jobTitle`·`skillName`이 비었거나, `proficiencyLevel`이 세 값이 아니거나, `headcount`가 없거나 1 미만이다 | `PROJECT_SKILL_LINE_INVALID` | 필요 역량의 직무, 기술, 숙련도, 인원(1 이상)을 모두 입력하세요. |

### 수정 — `PUT /api/projects/{id}`

요청 본문은 등록과 같다. `name`, `description`, `startDate`, `endDate`, `status`를 바꾸고, `requiredSkills`는 요청 배열로 완전히 바꾼다(없던 줄은 더하고, 요청에 없는 줄은 지운다). 한 요청의 변경은 전부 반영되거나 하나도 반영되지 않는다. 검증 실패는 등록과 같은 표다. 없는 id는 404 `PROJECT_NOT_FOUND`.

**D30 기간 검사.** 검증을 통과한 뒤, 그 프로젝트의 기존 배정 가운데 시작일이 새 `startDate`보다 앞서거나 종료일이 새 `endDate`보다 뒤인 것이 하나라도 있으면 저장을 막고 400 `PROJECT_PERIOD_EXCLUDES_ASSIGNMENTS`로 답한다. 기간의 양 끝 날짜는 그 안에 든다(배정 기간이 새 기간과 정확히 같아도 허용). 메시지는 "프로젝트 기간을 바꾸면 기간 밖으로 나가는 배정 N건이 있어 저장할 수 없습니다: <직원 이름> <시작일> ~ <종료일>, …"이고, 직원 이름과 기간은 `startDate`, `employeeName` 순으로 최대 3건까지 적는다. 이 검사는 기간을 줄일 때만이 아니라 모든 수정에서 같이 돈다. 막힌 요청은 프로젝트 정보도 필요 역량도 바꾸지 않는다.

성공: 200, 본문은 상세와 같은 모양이고 `assignments`는 바뀌지 않는다.

## 저장소 메서드 (T#5 저장소 계층에 더한다)

- `ProjectRepository.update(Project project)`: 그 id의 이름·설명·기간·상태를 바꾼다. 없는 id면 `false`(바꾼 행이 없다).
- `ProjectRequiredSkillLineRepository.deleteByProjectId(long projectId)`: 그 프로젝트의 필요 역량 줄을 모두 지운다.
- `AssignmentRepository.findByProjectId(long projectId)`: 그 프로젝트의 배정을 모두 돌려준다.

1. **목록 (D3).** `project.manager`로 로그인해 `GET /api/projects`를 부르면 200, 5건, `id` 오름차순이고 위 표의 이름·상태·기간·필요·오늘 배치와 같다.

   - 준비: 테스트 클래스와 로그인하는 도우미만 둔다(컨트롤러 없음).
   - 레드: 처리기가 없어 `GET /api/projects`가 404라 "200이어야 한다" 단언이 실패한다.
2. **상태 필터 (D3, D13).** `status=IN_PROGRESS`는 알파·베타 2건, `DONE`은 감마 1건, `PLANNED`는 델타 1건, `ON_HOLD`는 엡실론 1건이다. `status=ACTIVE`는 400 `PROJECT_STATUS_INVALID`이고 메시지가 한국어다.
   - 확인: `ProjectReadApiTest.statusFilter`. 준비·레드: 기준 1과 같다(404라 건수·상태 단언이 실패).
3. **상세 — 필요 역량·배치 인력·인력 현황 (D3, D22, D36).**
   - 프로젝트 1: `description` "사내 포털 리뉴얼", `requiredSkills`는 위 표의 한 줄, `requiredHeadcount` 2, `assignedHeadcount` 3. `assignments`는 3건이고 `startDate` 오름차순으로 권지안(2026-05-18 ~ 2026-09-08, 45%, `currentAvailability` 55), 강민재(2026-05-21 ~ 2026-09-03, 40%, 60), 박소영(2026-05-26 ~ 2026-07-25, 60%, 40)이다.

   - 확인: `ProjectReadApiTest.detail`. 준비·레드: 기준 1과 같다.
4. **상세 — 없는 id.** `GET /api/projects/99999`는 404 `PROJECT_NOT_FOUND`다.
   - 확인: `ProjectReadApiTest.detailNotFound`. 레드: 처리기가 없어 404이긴 하지만 본문이 `{"code","message"}`가 아니라 `code` 단언이 실패한다.
5. **등록 (D3, D22).** `project.manager`가 `{"name":"새 프로젝트","description":"설명","startDate":"2026-07-01","endDate":"2026-12-31","status":"PLANNED","requiredSkills":[{"jobTitle":"백엔드 개발자","skillName":"Java","proficiencyLevel":"ADVANCED","headcount":2},{"jobTitle":"디자이너","skillName":"Figma","proficiencyLevel":"BEGINNER","headcount":3}]}`를 POST하면 201, `Location: /api/projects/{id}`, 본문의 `requiredHeadcount`가 5, `assignedHeadcount`가 0, `assignments`가 빈 배열이다. 이어서 목록은 6건이고, 상세는 같은 줄 두 개를 보인다. 필요 역량 줄 없이 `description` 없이 만든 프로젝트도 201이고 `requiredHeadcount` 0, `description` `null`이다.
   - 확인: `ProjectWriteApiTest.create`. 준비: 테스트 클래스. 레드: POST가 404라 "201이어야 한다" 단언이 실패한다.
6. **등록 검증 (D33).** 위 표의 각 조건(이름 공백, 시작일 없음, 종료일 `2026-13-01`, 종료일이 시작일보다 하루 앞섬, 상태 `ACTIVE`, 줄의 `jobTitle` 공백, `skillName` 없음, `proficiencyLevel` `EXPERT`, `headcount` 0, 본문이 `not json`)마다 400과 그 `code`와 한국어 `message`를 확인한다. 시작일과 종료일이 같은 날은 201이다. 거절된 요청 뒤에도 프로젝트 수가 그대로다. 위반이 둘이면 표의 위쪽 조건의 `code`가 나온다(이름 공백과 상태 오류를 함께 보내면 `PROJECT_NAME_REQUIRED`).
   - 확인: `ProjectWriteApiTest.createValidation`. 레드: POST가 404라 400 단언이 실패한다.
7. **수정 (D3, D22).** 만든 프로젝트를 `PUT`으로 이름·설명·상태·기간을 바꾸고 줄을 둘에서 하나로 바꾸면 200, 본문과 이어지는 `GET` 상세가 바뀐 값이고 줄이 하나뿐이다(지운 줄이 남지 않는다). 줄을 모두 빼면 `requiredSkills`가 빈 배열이고 `requiredHeadcount` 0이다. 없는 id에 PUT은 404 `PROJECT_NOT_FOUND`다. 수정은 등록과 같은 검증 표를 따른다(이름 공백이면 400 `PROJECT_NAME_REQUIRED`이고 프로젝트는 바뀌지 않는다).
   - 확인: `ProjectWriteApiTest.update`. 레드: PUT이 404라 "200이어야 한다" 단언이 실패한다.
8. **D30 — 기간 밖으로 나가는 배정.** 프로젝트 하나를 만들고(기간 2026-05-01 ~ 2026-12-31) `AssignmentRepository`로 직원 두 명의 배정 `2026-05-20 ~ 2026-09-08`과 `2026-06-01 ~ 2026-08-31`을 넣는다. 그러고 `PUT`으로:
   - `endDate`를 `2026-09-07`로 줄이면(첫 배정만 밖으로 나감) 400 `PROJECT_PERIOD_EXCLUDES_ASSIGNMENTS`, 메시지에 "1건"과 그 직원 이름이 있다.
   - `startDate`를 `2026-05-21`로 늦추면(첫 배정이 밖으로 나감) 400 같은 코드, "1건"이다.
   - `startDate`를 `2026-06-02`로 늦추면(두 배정이 모두 밖으로 나감) "2건"이고 두 직원 이름이 모두 있다.
   - 막힌 요청이 이름·설명·상태·줄까지 바꾸려 했어도 그 뒤 `GET` 상세가 요청 전과 같다(기간, 이름, 필요 역량 줄 포함).
   - 새 기간이 정확히 `2026-05-20 ~ 2026-09-08`(배정들이 이루는 최소 구간)이면 200이다(경계 포함).
   - 기간을 넓히면 200이다.
   - 배정이 없는 프로젝트의 기간은 마음대로 줄일 수 있다(200).
   - 확인: `ProjectWriteApiTest.periodExcludesAssignments`. 레드: PUT이 404라 400·200 단언이 실패한다.
9. **저장소 메서드.** `update`는 이름·설명·기간·상태를 바꾸고 바뀐 행이 있으면 `true`, 없는 id면 `false`다. `deleteByProjectId`는 그 프로젝트의 줄만 지우고 다른 프로젝트의 줄은 남긴다. `findByProjectId`는 그 프로젝트의 배정만 돌려준다(시드 프로젝트 1은 3건, 프로젝트 2는 3건, 줄·배정이 없는 새 프로젝트는 0건).
   - 확인: `ProjectRepositoryTest`, `ProjectRequiredSkillLineRepositoryTest`, `AssignmentRepositoryTest`에 테스트를 더한다. 준비: 인터페이스에 메서드와, 아무것도 하지 않는(`false`, 빈 목록) 스텁 구현. 레드: `update`가 `true`를 돌려주지 않고 `findByProjectId`가 빈 목록이라 값 단언이 실패한다.
10. **회귀.** `make build`, `make test`, `make lint`가 통과한다. #6의 `AuthorizationPolicyTest`·`AuthApiTest`와 #5의 시드·저장소 테스트, #7의 `AvailabilityCalculatorTest`는 그대로 통과한다. `AuthorizationPolicyTest`는 이 태스크 전후 모두 `/api/projects` 행에서 401·403 여부만 보므로(허용 행은 "401도 403도 아님"), 처리기가 생겨도 통과한다.
    - 확인: `make build`, `make test`, `make lint`. baseline: 작업 전 `main`에서 통과.
