# T#11 대시보드 API: 집계 지표

## 산출물

`backend/`에 `GET /api/dashboard`이 D5의 아홉 항목(전체·투입 가능·투입 불가 직원 수, 가용 인원 수, 진행 프로젝트 수, 인력 부족 프로젝트, 직원별 투입률, 부서별 평균 투입률, 확인 필요 배치)을 돌려주고, 같은 직원의 현재 가용률이 직원 API·프로젝트 API·대시보드 API에서 같은지 확인하는 일관성 검사가 통과한다.

## 전제

- 근거: REQ-CONTEXT D5, D7, D13, D18, D19, D20, D21, D23, D33, D36.
- 이 태스크는 권한 검사를 따로 구현하지 않는다. `GET /api/dashboard`는 #6 계약서 "권한 정책" 표의
  `GET /api/employees/**, /api/projects/**, /api/assignments/**, /api/dashboard/**` 행(비로그인 401, 직원만 403,
  인력 관리자·프로젝트 관리자·겸임 허용)에 이미 포함되어 있어 표를 바꾸지 않는다. 쓰기 요청(`POST /api/dashboard` 등)은
  표의 "그 밖의 모든 요청" 행이 기본 거부한다. 역할별 401·403 검사는 #6의 `AuthorizationPolicyTest`가 맡는다.
- 가용률·투입률 계산은 T#7의 `AvailabilityCalculator`(`currentAvailability`, `needsReview`)를 그대로 쓴다.
  D36 "투입률과 가용률은 백엔드 한 곳에서만 계산" — 이 태스크는 새 계산 로직을 만들지 않고, 직원 API(T#8)·프로젝트
  API(T#9)와 같은 메서드에서 값을 낸다.
- "직원별 투입률"은 직원 API·프로젝트 API와 같은 값인 **현재 가용률**(D7, D18, D19 — `currentAvailability`)로
  돌려준다. 화면은 이 값을 그대로 보여 준다(D36).
- 인력 부족 판정(D20)은 서비스 메서드로 둔다. 이슈 #11 댓글(PM, 2026-10-13)의 후속 태스크 #32가 프로젝트
  목록 API에서 같은 판정을 재사용한다.
- T#5의 시드(부서 3·직원 20·프로젝트 5·배치 15, 고정 `Clock` 2026-06-15)를 그대로 쓴다. 아래 수용 기준의
  숫자는 그 시드로 미리 계산한 값이다. 이 태스크는 시드를 바꾸지 않는다.
- "오늘 배치"는 시작일 ≤ 오늘(2026-06-15) ≤ 종료일인 배정이다.

## 대시보드 API

### `GET /api/dashboard`

응답 200, 단일 객체:

```json
{
  "employeeCount": 20,
  "availableCount": 19,
  "unavailableCount": 1,
  "availableHeadcount": 19,
  "ongoingProjectCount": 2,
  "shortStaffedProjects": [],
  "employees": [
    {"id": 1, "name": "박소영", "currentAvailability": 40},
    {"id": 2, "name": "최동훈", "currentAvailability": 60}
  ],
  "departments": [
    {"id": 1, "name": "개발팀", "averageAvailability": 70.6},
    {"id": 2, "name": "기획팀", "averageAvailability": 93.6},
    {"id": 3, "name": "디자인팀", "averageAvailability": 72.0}
  ],
  "needsReview": [{"id": 2, "name": "최동훈"}]
}
```

- `employeeCount`: 직원 전체 수(D5).
- `availableCount` / `unavailableCount`: `availabilityStatus`가 `AVAILABLE` / `UNAVAILABLE`인 직원 수(D5).
- `availableHeadcount`: 상태 `AVAILABLE`이고 오늘 현재 가용률이 0보다 큰 직원 수(D23). 시드에서는 `UNAVAILABLE`인
  최동훈 1명만 제외되어 19다(임도윤 35, 신예은 30은 0이 아니다).
- `ongoingProjectCount`: 상태 `IN_PROGRESS`인 프로젝트 수(D5, D13 "진행 프로젝트 수는 진행 중 프로젝트 수").
- `shortStaffedProjects`: D20의 인력 부족 프로젝트. 각 항목은 `id`, `name`, `requiredHeadcount`(필요 역량 줄
  `requiredHeadcount`의 합), `assignedHeadcount`(오늘 배치된 인원 수), `missingSkills`(오늘 그 기술을 가진
  직원이 한 명도 배치되지 않은 줄의 `skill`과 `requiredHeadcount`). `id` 오름차순. 시드에서는 비어 있다(아래 기준 2).
- `employees`: 전체 직원의 `id`, `name`, 현재 가용률(`currentAvailability`). `id` 오름차순.
- `departments`: 전체 부서의 `id`, `name`, `averageAvailability`(그 부서에 속한 직원의 현재 가용률 산술 평균,
  소수점 둘째 자리에서 반올림 — HALF_UP). `id` 오름차순.
- `needsReview`: `needsReview`가 `true`인 직원(D21, T#8의 `AvailabilityCalculator.needsReview`)의 `id`, `name`.
  `id` 오름차순.

### 인력 부족 판정 (D20, 재사용 가능한 서비스 메서드)

`com.ax.rms.dashboard` 패키지의 서비스 메서드: `List<Long> shortStaffedProjectIds(List<Project> projects,
List<Assignment> assignments, List<EmployeeSkill> employeeSkills, LocalDate today)`.

- 대상은 `status == IN_PROGRESS`인 프로젝트만(D20 "진행 중이면서").
- 부족 조건(둘 중 하나):
  1. `today`가 `[startDate, endDate]` 안에 있는 그 프로젝트 배정이 붙은 **다른 직원 수**가 `requiredHeadcount`
     (필요 역량 줄 합)보다 적다.
  2. 필요 역량 줄 중 하나라도, 그 `skill`을 가진 직원(숙련도 무관)이 오늘 그 프로젝트에 한 명도 배치되지 않았다.
- 이 판정은 T#8·T#9·이 API가 쓰는 가용률 계산과는 별개의 집계다(가용률 계산은 `AvailabilityCalculator`가 그대로
  담당). #32가 이 메서드를 프로젝트 목록 API에서 재사용한다.

## 수용 기준

모든 새 검사는 `backend/src/test/java/com/ax/rms/dashboard/` 아래 JUnit이다. API 검사는 `AbstractApiTest`

1. **대시보드 전체 (D5).** `GET /api/dashboard`를 부르면 200이고, `employeeCount` 20, `availableCount` 19,
   `unavailableCount` 1, `availableHeadcount` 19(D23 — `UNAVAILABLE`인 최동훈 1명만 제외), `ongoingProjectCount` 2
   (D13 — 알파·베타), `needsReview`는 `[{id:2, name:"최동훈"}]` 1건(D21)이다.
   - 확인: `DashboardApiTest.dashboard`.
   - 준비: 테스트 클래스만 둔다(컨트롤러 없음).
   - 레드: 처리기가 없어 `GET /api/dashboard`가 404라 "200이어야 한다" 단언이 실패한다.
2. **인력 부족 프로젝트 (D20, 시드).** `shortStaffedProjects`는 `[]`(비어 있다).
   - 베타: 오늘 배치 3명(최동훈·임도윤·안유진) ≥ 필요 2이고, React 보유자 최동훈이 베타에 배치되어 있다(`SeedRunner.java:240`)
     → 부족 아님.
   - 알파: 오늘 배치 3명(박소영·강민재·권지안) ≥ 필요 2이고, Java 보유자(박소영·한지우)가 배치되어 있다 → 부족 아님.
   - 감마(`DONE`)·엡실론(`ON_HOLD`)·델타(`PLANNED`)는 `IN_PROGRESS`가 아니라 대상이 아니다.
   - 확인: `DashboardApiTest.shortStaffed`. 준비·레드: 기준 1과 같음.
3. **인력 부족 항목 모양 (D20, API).** 시드를 바꾸지 않고, 테스트 안에서 저장소로 배치를 더하거나 지워 부족 상황을
   만든 뒤, `shortStaffedProjects` 항목의 모양을 단언한다.
   - 방법: `IN_PROGRESS` 프로젝트(알파)의 오늘 배치를 전부 `AssignmentRepository.delete`로 지우고, 알파의 필요
     기술(Java)을 **가지지 않은** 직원(예: 임도윤) 하나를 알파에 오늘 포함 배정으로 `insert`한다.
   - 단언: `shortStaffedProjects`에 알파 항목이 1건이고, `id`·`name`("알파 프로젝트")·`requiredHeadcount`(2)·
     `assignedHeadcount`(1)·`missingSkills`(`[{skill:"Java", requiredHeadcount:2}]`)가 정확히 같다.
   - 확인: `DashboardApiTest.shortStaffedShape`. 준비·레드: 기준 1과 같음.
4. **직원별 현재 가용률 (D5, D36).** `employees`는 20건, `id` 오름차순이고, 위 표의 각 직원의
   `currentAvailability`와 정확히 같다(예: id 1 → 40, id 2 → 60, id 5 → 100, id 9 → 35, id 13 → 30,
   id 14 → 55, id 19 → 100, id 20 → 100).
   - 확인: `DashboardApiTest.perEmployee`. 준비·레드: 기준 1과 같음.
5. **부서별 평균 (D5).** `departments`는 3건, `id` 오름차순이고, `averageAvailability`는 개발팀 **70.6**
   (565/8 = 70.625, 반올림), 기획팀 **93.6** (655/7 = 93.571, 반올림), 디자인팀 **72.0** (360/5)이다.
   - 확인: `DashboardApiTest.departmentAverage`. 준비·레드: 기준 1과 같음.
6. **일관성 (D36).** 같은 직원의 현재 가용률이 세 API에서 같다. 직원 목록 API(`GET /api/employees`)의
   20건 전체에 대해, 대시보드의 `employees` 항목의 `currentAvailability`와 같고, 프로젝트 상세
   (`GET /api/projects/{id}`)의 `assignments`에 그 직원이 있으면 그 항목의 `currentAvailability`와도
   같음을 확인한다(특히 id 1·7·14는 알파 상세, id 2·9·16은 베타 상세의 `assignments`에 등장한다).
   - 확인: `DashboardApiTest.consistencyWithEmployeeAndProjectApis`. 준비·레드: 기준 1과 같음.
7. **인력 부족 판정 단위 검사 (D20, 서비스 메서드).** 손으로 만든 값으로(시드 없이):
   - `IN_PROGRESS` 프로젝트, 필요 2, 오늘 배치 1명 → 부족(조건 1).
   - `IN_PROGRESS` 프로젝트, 필요 1, 오늘 배치 1명인데 그 줄의 기술을 가진 직원이 배치되지 않음 → 부족(조건 2).
   - `IN_PROGRESS` 프로젝트, 필요 1, 오늘 배치 1명이고 그 직원이 그 기술을 가짐 → 부족 아님.
   - `DONE`·`PLANNED`·`ON_HOLD` 프로젝트는 배치가 부족해도 대상이 아님.
   - 확인: `ShortStaffedProjectsTest`.
   - 준비: 메서드가 `UnsupportedOperationException`을 던지는 스텁.
   - 레드: 네 테스트 모두 그 예외로 실패한다.
8. **회귀.** `make build`, `make test`, `make lint`가 통과한다. #6의 `AuthorizationPolicyTest`·`AuthApiTest`,
   #8의 `EmployeeApiTest`, #9의 프로젝트 API 검사, #7의 `AvailabilityCalculatorTest`, #10의 배치 API 검사는
   그대로 통과한다. `AuthorizationPolicyTest`는 `GET /api/dashboard` 행에서 401·403 여부만 보므로(허용 행은
   "401도 403도 아님"), 처리기가 생겨도 통과한다.
   - 확인: `make build`, `make test`, `make lint`. baseline: 작업 전 `main`에서 통과.

## 검증 명령

  들어간다.

## 격리

JUnit이 쓰는 임시 SQLite 파일(`@TempDir`)과 고정 시계만 건드린다. API 검사는 `RANDOM_PORT`로 임의 포트를 쓴다.
작업 폴더의 `backend/data/*.db`, `DB_PATH`, 18080·14173·8080 포트에는 의존하지 않는다. `make test`의 e2e는
T#4가 만든 `scripts/e2e-servers.sh`를 그대로 쓴다. 외부 네트워크를 쓰지 않는다(D40). 기계별 설치 경로나 PATH
설정을 쓰지 않는다.

## 하지 않을 일

- 배치 생성·수정·해제 API(D8, D14, D27, D28) — → T#10(이미 병합됨).
- 대시보드 화면(목록 항목, 상세 이동, 빈·오류 상태) — → T#18.
- 프로젝트 목록 API에 인력 부족 표시를 넣는 일 — → T#32(이 태스크의 서비스 메서드를 재사용).
- 대시보드의 필터·페이지네이션·기간 선택 — 이 태스크는 고정 "오늘"(주입된 `Clock`) 기준으로 한 번에 돌려준다.
- 직원 API·프로젝트 API의 응답 형식 변경 — 이 태스크는 그것들을 읽기만 한다.
- 시드 데이터 변경. 이 태스크는 시드를 바꾸지 않는다.
