# T#18 통합 대시보드 화면

## 산출물

로그인한 관리자가 `/`에서 D5의 아홉 항목(숫자 타일 다섯 개와 목록 네 개)을 `GET /api/dashboard` 값 그대로 보고, 각 항목에서 관련 직원·프로젝트 상세나 목록으로 이동하며, 목록마다 빈 목록과 오류 상태가 따로 보이는 화면. T#4 참조 화면은 `/design-reference`로 옮겨 그 검사들이 그대로 돈다.

## 작업량

이슈 #18 그대로 하나로 한다. 예상 약 7.5시간(하루, 빠듯함).

| 일 | 예상 |
|---|---|
| 라우트(`/` → 대시보드, 참조 화면 `/design-reference`), 기존 검사의 주소 고치기 | 0.5시간 |
| `api/dashboard.ts` 타입, `Badge`의 `인력 부족` 변형(아직 `main`에 없을 때) | 0.5시간 |
| 대시보드 화면: 타일 다섯 개, 목록 네 개, 형식, 상태, CSS | 2.5시간 |
| Vitest | 1.5시간 |
| e2e(실제 시드와 API 대조, 고정 응답, 네 너비, 이동, 다시 불러오기), 스크린샷 8장 | 2시간 |
| 베이스라인·레드·그린 기록, 증거 | 0.5시간 |

## 전제

- **선행 작업 #11은 `main`에 있다**(PR #45, `fab91f9`). 이 계약서는 `origin/main`(`fab91f9`)을 읽고 썼다. 응답 모양은
  `backend/src/main/java/com/ax/rms/dashboard/DashboardService.java`의 `DashboardResponse`에서 읽은 그대로다:
  `{employeeCount, availableCount, unavailableCount, availableHeadcount, ongoingProjectCount, shortStaffedProjects: [{id, name,
  requiredHeadcount, assignedHeadcount, missingSkills: [{skill, requiredHeadcount}]}], employees: [{id, name, currentAvailability}],
  departments: [{id, name, averageAvailability}], needsReview: [{id, name}]}`. 목록은 모두 `id` 오름차순으로 오고, 화면은 그 순서
  그대로 보인다. `averageAvailability`는 소수 첫째 자리까지 반올림된 수다(#11 계약서, JSON `70.6`, `72.0`).
- 근거: REQ-CONTEXT D5, D9, D13, D20, D21, D23, D25, D29, D34, D35, D36. 화면은 `docs/design/BRIEF.md` 6.2절(통합 대시보드),
  3.4절(StateMessage), 3.6절(Badge `확인 필요`·`인력 부족`, 숫자 타일), 4절(Layout), 5절(Formats), 6절 공통, 7절 Checks 7–10을
  따른다. BRIEF가 정하지 않은 값은 `(제안)`이다.
- **화면은 계산하지 않는다(D36).** 숫자, 가용률, 평균, 인력 부족 여부, 확인 필요 여부는 API 값을 그대로 보인다. 화면이 하는 일은
  형식(단위, `%`, 천 단위 쉼표, 소수 한 자리)뿐이다.
- **권한(D9, D25).** 대시보드는 읽기만 한다. 서버 규칙은 #6 그대로다: `GET /api/dashboard`는 인력 관리자·프로젝트 관리자·겸임
  200, 직원 역할만 403, 비로그인 401(#6 `AuthorizationPolicyTest`, 2026-10-14 임시 DB에서 네 데모 계정으로 확인). `/`는 이미
  `ManagerOnly` 아래에 있다. 이 태스크는 권한 규칙을 바꾸지 않는다.
- **`/`를 이 화면이 가져간다.** T#4 계약서("업무 화면이 생기면 그 태스크들이 `/`를 가져간다")와 T#6 계약서("`/` — T#4 참조 화면
  (T#18이 대시보드로 바꾼다)")대로다. 참조 화면(`App.tsx`)은 지우지 않고 새 주소 `/design-reference`(제안, `ManagerOnly`, 메뉴에
  없음)로 옮긴다. `App.tsx`는 바꾸지 않으므로 메뉴의 현재 항목은 그대로 "대시보드"다(T#4 기준과 BRIEF Checks 3이 재는 값). 그 화면을
  재는 기존 검사는 단언을 바꾸지 않고 여는 주소만 `/design-reference`로 바꾼다(기준 11).
- **`Badge`의 `인력 부족` 변형.** PM 메모(이슈 #18 댓글 2026-10-14): #32와 #18이 함께 쓰고, 먼저 병합된 태스크가
  `BadgeStatus`에 `UNDERSTAFFED`(글자 "인력 부족", `--color-warning`/`--color-warning-bg`)를 더하며 나중 태스크는 쓰기만 한다.
  2026-10-14 `origin/main`에는 아직 없다. 구현을 시작하기 전과 `origin/main`을 병합한 뒤 다시 확인한다(기준 1).
- 서버 시드(`SeedRunner`)는 날짜를 DB를 만든 날 기준으로 만들고, 공유 e2e DB(`backend/data/e2e.db`)는 한 번 만든 뒤 계속 쓴다. 그래서
  e2e는 시드 숫자를 하드코딩하지 않고, 같은 세션의 `GET /api/dashboard` 응답과 화면을 대조한다.
- `make`가 설치되어 있지 않은 환경에서는 Makefile의 각 줄을 같은 명령으로 실행해 증거에 적는다.

## 화면 동작

### 라우트

| 경로 | 비로그인 | 직원만 | 관리자(인력·프로젝트·겸임) |
|---|---|---|---|
| `/` | `/login` | `/me` | 대시보드(이 태스크) |
| `/design-reference` (제안) | `/login` | `/me` | T#4 참조 화면(`App.tsx` 그대로) |

다른 라우트와 `homePath`는 바꾸지 않는다. 관리자는 로그인하면 지금처럼 `/`로 오고, 이제 대시보드를 본다.

### 구성 (BRIEF 6.2)

1. 제목 "대시보드"(h1, xl/700) (제안).
2. 숫자 타일 다섯 개(아래 표). 타일은 링크 하나(`Link`)이고, 안에 라벨(sm, text-muted), 값(2xl/700, `tabular-nums`), 단위(sm,
   text-muted)가 있다. 타일 면은 surface, 테두리 1px border, 반경 `--radius-md`, `--shadow-sm`, 패딩 `--space-4`, hover 배경
   surface-subtle (제안). 값은 1,000 이상이면 천 단위 쉼표다(BRIEF 5절).

   | 라벨 | 값 | 단위 | 링크 |
   |---|---|---|---|
   | 전체 직원 | `employeeCount` | 명 | `/employees` |
   | 투입 가능 | `availableCount` | 명 | `/employees?status=AVAILABLE` |
   | 투입 불가 | `unavailableCount` | 명 | `/employees?status=UNAVAILABLE` |
   | 가용 인원 | `availableHeadcount` | 명 | `/employees?status=AVAILABLE` (제안: 직원 목록에 "가용률 0% 초과" 필터가 없어 가장 가까운 목록이다. 목록은 행마다 현재 가용률을 보인다) |
   | 진행 프로젝트 | `ongoingProjectCount` | 개 (제안) | `/projects?status=IN_PROGRESS` |

3. 목록 네 개, 이 순서다. 목록마다 카드(surface, 테두리 1px border, 반경 `--radius-md`, 패딩 `--space-4`) 안에 제목(h2, lg/600)과
   `ul`이 있다. 항목은 최소 높이 `--row-min-height`(44px)이고 항목 사이에 1px border 선이 있다. 항목의 이름은 링크(primary 색)이고
   값은 오른쪽 끝 정렬, sm, `tabular-nums`다 (제안).

   | 목록(제목) | 데이터 | 항목 | 링크 |
   |---|---|---|---|
   | 확인 필요 배치 | `needsReview` | 직원 이름, `Badge` "확인 필요"(warning) | `/employees/<id>` |
   | 인력 부족 프로젝트 | `shortStaffedProjects` | 첫 줄: 프로젝트명, `Badge` "인력 부족"(warning). 둘째 줄(sm, text-muted): `필요 2명 / 배치 1명`(BRIEF 5절 인원 형식). `missingSkills`가 있으면 셋째 줄: `부족한 역량: Java 2명, React 1명` (제안) | `/projects/<id>` |
   | 직원별 가용률 (질문 1) | `employees` | 직원 이름, `currentAvailability` → `40%` | `/employees/<id>` |
   | 부서별 평균 가용률 (질문 1) | `departments` | 부서 이름, `averageAvailability` → 소수 한 자리 `70.6%`, `72.0%` (제안) | `/employees?departmentId=<id>`(T#13 직원 목록의 부서 필터) |

- **질문 1 (PM 결정): 셋째·넷째 목록의 제목.** D5와 BRIEF 6.2는 "직원별 투입률", "부서별 평균 투입률"이라 부른다. 그러나 #11
  계약서(승인)는 이 두 항목을 현재 가용률(`currentAvailability`)과 부서 평균 가용률(`averageAvailability`)로 돌려주고 "화면은 이
  값을 그대로 보여 준다"고 정했다. 화면은 `100 − 값`을 계산하지 않는다(D36). 이 초안은 숫자가 가리키는 것을 제목에 쓴다(위 표).
  BRIEF 제목을 그대로 쓸지(값은 가용률), API에 투입률을 더할지(#11 변경 태스크, `nexi-backlog change`)는 PM이 정한다.
- 긴 값(공백 없는 48자 이름)은 칸 안에서 줄바꿈하고 말줄임을 쓰지 않는다(BRIEF 5절 "긴 값").

### 배치 (BRIEF 4절, 6.2절)

- **넓은 구간**(≥1024px): 타일은 한 줄 5열(`repeat(5, 1fr)`, 간격 `--space-4`), 목록은 2열 격자(간격 `--space-5`), 타일과 목록
  사이는 `--space-6`이다 (제안). 1행은 확인 필요 배치 · 인력 부족 프로젝트, 2행은 직원별 · 부서별이다.
  - 1280px 본문 996px: 타일 (996 − 4×16) ÷ 5 = 186.4px, 목록 (996 − 24) ÷ 2 = 486px.
  - 1024px 본문 740px: 타일 (740 − 64) ÷ 5 = 135.2px(안쪽 약 101px에 "진행 프로젝트" 약 88px가 들어간다), 목록 358px.
- **좁은 구간**(<1024px): 타일은 2열(간격 `--space-2`), 목록은 한 열(위 순서, 간격 `--space-4`)이다.
  - 360px 본문 328px: 타일 (328 − 8) ÷ 2 = **160px**(BRIEF 6.2 "각 160px"), 3줄(마지막 줄 1개). 목록 328px.
- 모든 너비에서 가로 스크롤이 없다(D34).

### 불러오는 동안과 상태 (D35, BRIEF 6.2·6절 공통)

- 요청은 화면을 열 때마다 `GET /api/dashboard` 한 번이다. 화면 안에 값을 쌓아 두지 않는다. 그래서 배치·수정·해제 뒤 대시보드로
  돌아오면 다시 불러온 값을 보인다(D36). 서버 응답은 `Cache-Control: no-cache, no-store`다(2026-10-14 확인). 화면을 떠나면 진행
  중인 요청은 버린다.
- **불러오는 중**: 제목 아래 내용 자리에 "불러오는 중…"(sm, text-muted)을 두고 그 영역에 `aria-busy="true"`를 둔다. 타일과 목록은
  그리지 않는다.
- **오류**(네트워크 오류, 2xx가 아닌 응답, 401 포함): 타일 다섯 개는 라벨과 링크를 그대로 두고 값 자리에 `—`(text-muted, 단위
  없음)를 쓴다(BRIEF 5절 빈 값). 네 목록은 각자 제목 아래에 `StateMessage` `error`("데이터를 불러오지 못했습니다", "잠시 후 다시
  시도하세요.", "다시 시도")를 둔다(BRIEF 6.2 "오류: 그 목록 자리에 error"). 어느 "다시 시도"든 `GET /api/dashboard`를 한 번 다시
  부르고, 그동안은 불러오는 중 상태다. 세션 만료 처리는 하지 않는다(T#15와 같다).
- **빈 목록**: 목록마다 따로 `StateMessage` `empty`를 둔다.
  - 확인 필요 배치: "확인이 필요한 배치가 없습니다"(BRIEF 6.2), 설명 "투입 불가 직원에게 남은 배치가 없습니다." (제안)
  - 인력 부족 프로젝트: "인력이 부족한 프로젝트가 없습니다"(BRIEF 6.2), 설명 "진행 중인 프로젝트의 인원과 필요 역량이 채워져
    있습니다." (제안)
  - 직원별: "등록된 직원이 없습니다"(T#13과 같은 글자). 부서별: "등록된 부서가 없습니다" (제안). 설명은 기본값이다.
- **검색 결과 없음**: 대시보드에는 검색·필터가 없어 생기지 않는다. BRIEF 6.2도 빈 목록과 오류만 정한다.

## 수용 기준

1. **`Badge`의 `인력 부족` 변형.** `BadgeStatus`에 `UNDERSTAFFED`가 있고 글자 "인력 부족", `data-status="UNDERSTAFFED"`로 그린다.
   색은 `--color-warning` 글자 / `--color-warning-bg` 배경이다(BRIEF 3.6, 대비 5.52).
   - 확인: Vitest `Badge.test.tsx`에 테스트를 더한다. 색은 기준 7(e2e).
   - 준비: 없음(테스트만 더한다). 레드: `UNDERSTAFFED`가 없어 `getByText('인력 부족')`이 실패한다.
   - **#32가 먼저 병합되어 `main`에 이미 있으면** 이 기준은 새 검사가 아니라 회귀 검사다. 그때는 `Badge.tsx`·`Badge.css`를 고치지
     않고 #32의 테스트가 통과함을 베이스라인과 함께 기록한다.
2. **라우트.** 관리자가 `/login`에서 `/`로 오면 제목 "대시보드"가 보이고 메뉴의 "대시보드"가 `aria-current="page"`다. 관리자가
   `/design-reference`를 열면 주소가 그대로이고 제목 "디자인 참조"가 보인다. 직원 역할만 가진 계정은 `/`와 `/design-reference`에서
   `/me`로 가고, 비로그인은 둘 다 `/login`으로 가며, 그동안 `/api/dashboard`를 부르지 않는다.
   - 확인: Vitest `AppRoutes.test.tsx`. 기존 테스트 "sends a manager from /login to /"의 단언 하나를 "디자인 참조" → "대시보드"로
     바꾸고(가짜 `fetch`에 `/api/dashboard` 응답을 더한다), 나머지는 새 테스트로 더한다.
   - 준비: 없음. 레드: `/`가 아직 참조 화면이라 제목 "대시보드"가 없고, `/design-reference`는 `*`가 `/`로 보내 주소 단언이
     실패한다.
3. **숫자 타일 (D5, D13, D23).** 고정 응답(`employeeCount` 1234, `availableCount` 19, `unavailableCount` 1, `availableHeadcount` 18,
   `ongoingProjectCount` 2)으로 열면 타일 다섯 개가 위 표 순서로 라벨·값·단위를 보인다: "전체 직원 1,234명", "투입 가능 19명",
   "투입 불가 1명", "가용 인원 18명", "진행 프로젝트 2개". 각 타일은 링크이고 `href`가 위 표 그대로다.
   - 확인: Vitest `pages/DashboardPage.test.tsx`(가짜 `fetch`, `MemoryRouter`).
   - 준비: `AppShell`만 그리는 `DashboardPage` 스텁. 레드: 링크 "전체 직원"이 없어 `getByRole('link', …)`가 실패한다.
4. **목록 네 개 (D5, D20, D21).** 고정 응답으로 목록 제목 네 개가 순서대로 있고(질문 1의 결정을 따른다), 항목이 응답 순서
   그대로다.
   - 확인 필요 배치: 항목마다 이름 링크(`/employees/<id>`)와 "확인 필요" 배지.
   - 인력 부족 프로젝트: `{id: 7, name: '알파 프로젝트', requiredHeadcount: 2, assignedHeadcount: 1, missingSkills: [{skill: 'Java',
     requiredHeadcount: 2}]}`이 이름 링크 `/projects/7`, "인력 부족" 배지, "필요 2명 / 배치 1명", "부족한 역량: Java 2명"이다.
     `missingSkills`가 빈 항목에는 "부족한 역량" 줄이 없다.
   - 직원별: `currentAvailability` 40, 0, 100이 `40%`, `0%`, `100%`이고 이름 링크가 `/employees/<id>`다.
   - 부서별: `averageAvailability` 70.6, 72(JSON `72.0`)가 `70.6%`, `72.0%`이고 이름 링크가 `/employees?departmentId=<id>`다.
   - 확인: `DashboardPage.test.tsx`. 준비·레드: 기준 3과 같다.
5. **상태 (D35, D36).** 응답 전에는 "불러오는 중…"과 `aria-busy="true"`이고 타일이 없다. 네트워크 거부, 500, 401은 오류이고 타일

   응답과 화면이 같다: 타일 값 다섯 개, 확인 필요 배치의 이름 목록, 인력 부족 프로젝트의 이름 목록(비어 있으면 그 빈 목록 제목),
   직원별 항목 수·이름·`<값>%`, 부서별 이름·`<값>%`(소수 한 자리), 각 링크의 `href`.
   - 이동: 직원별 첫 항목을 누르면 `/employees/<id>`이고 그 직원 이름이 제목이다. 부서별 첫 항목을 누르면
     `/employees?departmentId=<id>`이고 직원 목록의 부서 필터가 그 부서다. 타일 "진행 프로젝트"를 누르면 `/projects?status=IN_PROGRESS`

## 격리

새로 건드리는 DB·폴더·서비스·포트는 없다. e2e와 스크린샷은 T#4가 만든 `scripts/e2e-servers.sh`와 README "검사 격리" 표를 그대로
쓴다(백엔드 18080, 공유 DB 파일 `backend/data/e2e.db`, 프런트엔드 14173, 서버 기록 `.nexi-tmp/e2e-servers.pids`, 잠금
`.nexi-tmp/e2e-servers.lock`). 이 태스크의 e2e는 공유 DB를 읽기만 하고(`POST /api/auth/login`·`/api/auth/logout` 말고는 쓰기
요청을 보내지 않는다) `frontend/e2e/write/`에 스펙을 더하지 않는다. 응답 가로채기는 브라우저 안(`page.route`)에서만 일어난다.
외부 네트워크를 쓰지 않는다(D40). 기계별 설치 경로나 PATH 설정을 쓰지 않는다.
