# T#58 변경: 폼 오류 연결과 배치 저장 뒤 복구

변경 대상: T#4, T#17, T#34, T#39 (구현 변경, 배포된 대상 없음 — D40). T#4·T#17·T#34·T#39의 계약서·증거·판정은 고치지 않는다. 프런트엔드만 바꾼다(`backend/` 변경 없음).

## 산출물

`TextField`·`SelectField`가 호출부의 `aria-*`를 덮어쓰지 않고 합치며, 프로젝트·직원 폼의 기간·필요 역량·기술 오류가 해당 input에 `aria-invalid`·`aria-describedby`로 연결되고 저장 실패 때 첫 오류 input으로 포커스가 가며, 인력 배치 저장 뒤 프로젝트를 다시 불러오는 데 실패해도 화면과 입력 중인 폼이 남고 그 조회만 다시 시도할 수 있다.

## 바뀌는 동작

| 항목 | 지금 | 바뀐 뒤 |
|---|---|---|
| `TextField`·`SelectField`의 `aria-invalid`·`aria-describedby` | 호출부가 준 값을 내부 값이 덮어쓴다 | 호출부가 준 `aria-describedby` id는 내부 메시지 id와 공백으로 합쳐지고, 호출부의 `aria-invalid`는 내부 `error`와 OR로 합쳐진다. 오류도 도움말도 호출부 값도 없으면 속성은 없다 |
| 프로젝트 폼 기간 오류 | `fieldset`에만 `aria-invalid`·`aria-describedby` | 시작일·종료일 input 둘 다 `aria-invalid="true"`와 기간 메시지 id를 가리키는 `aria-describedby`. `fieldset`의 `aria-invalid`는 없애고 `aria-describedby`는 그대로 둔다(그룹 역할에 `aria-invalid`는 쓸 수 없고 설명은 쓸 수 있다). 메시지 자리·모양은 그대로 |
| 필요 역량·기술 오류 | `fieldset`에만 | 오류가 가리키는 첫 줄의 첫 input(직무 / 직원 폼은 기술 이름)에 연결. 인원이 정수가 아닌 오류(`HEADCOUNT_NOT_WHOLE`)는 그 줄의 인원 input에 연결. `fieldset`의 `aria-invalid`는 없애고 `aria-describedby`는 그대로 둔다. 메시지 자리·모양은 그대로 |
| 저장 실패 뒤 포커스 | 포커스가 저장 버튼에 남는다 | 입력에 연결된 오류(이름·기간·상태·필요 역량·기술·경력·부서·직무)이면 DOM 순서로 첫 `aria-invalid="true"` 입력이 포커스를 받는다. 폼 전체 오류(`role="alert"`)는 포커스를 옮기지 않는다. 클라이언트 검사 실패(인력 배치 화면의 투입률·기간 포함)에도 같다 |
| 배치 저장 뒤 프로젝트 재조회 실패 | 화면 전체가 오류 화면(`StateMessage`)이 되고 폼이 사라진다 | 이미 불러온 프로젝트가 있으면 마지막으로 불러온 값이 그대로 보이고, 요약 위에 "프로젝트를 다시 불러오지 못했습니다." 알림(`role="alert"`)과 "다시 불러오기" 버튼이 나온다. 버튼은 프로젝트 조회만 다시 보낸다. 처음부터 불러오지 못한 경우(아직 프로젝트가 없음)는 지금처럼 오류 화면이다. 재조회가 404면 지금처럼 "프로젝트를 찾을 수 없습니다" |

## 수용 기준

1. **필드 aria 합치기.** `TextField`에 `aria-describedby="x"`를 주고 오류가 있으면 `describedby`가 `"x <메시지 id>"`(둘 다 존재), 오류·도움말이 없으면 `"x"`, 호출부 값도 없으면 속성 없음. `aria-invalid`를 준 `TextField`는 오류가 없어도 `aria-invalid="true"`. `SelectField`도 같다 — 확인: Vitest `TextField.test.tsx`, `SelectField.test.tsx`(새 사례).
2. **프로젝트 폼 기간 오류.** 종료일이 시작일보다 앞서 저장하면 서버 400 `PROJECT_PERIOD_INVALID`(고정 응답)에서 시작일·종료일 input 둘 다 `aria-invalid="true"`이고 둘의 `aria-describedby`가 기간 메시지 요소를 가리키며, `fieldset`에는 `aria-invalid`가 없고 `aria-describedby`는 그대로 그 메시지를 가리킨다 — 확인: Vitest `ProjectFormPage.test.tsx`(새 사례).
3. **프로젝트 폼 필요 역량 오류.** 400 `PROJECT_SKILL_LINE_INVALID`이면 첫 줄의 직무 input이, 인원 `1.5`를 넣으면 그 줄의 인원 input이 `aria-invalid="true"`이고 해당 메시지를 가리킨다. `fieldset`에는 `aria-invalid`가 없고 `aria-describedby`는 그대로다 — 확인: Vitest `ProjectFormPage.test.tsx`.
4. **직원 폼 기술 오류.** 400 `EMPLOYEE_SKILL_DUPLICATE`이면 첫 줄의 기술 이름 input이 `aria-invalid="true"`이고 메시지를 가리킨다. `fieldset`에는 `aria-invalid`가 없고 `aria-describedby`는 그대로다 — 확인: Vitest `EmployeeFormPage.test.tsx`.
5. **포커스.** 위 기준 2~4와 이름 비어 있음(`PROJECT_NAME_REQUIRED`/`EMPLOYEE_NAME_REQUIRED`), 경력 `1.5`의 클라이언트 오류에서 저장 실패 직후 `document.activeElement`가 첫 오류 input이다.  "첫 번째"는 DOM 순서다(예: 기간 오류면 시작일). 폼 전체 오류(500 등 `role="alert"`)에서는 활성 요소가 저장 버튼에서 바뀌지 않는다. 인력 배치 화면의 투입률 7 입력(클라이언트 검사)에서 투입률 input이, 기간 오류에서 종료일 input이 포커스를 받는다 — 확인: Vitest `ProjectFormPage.test.tsx`, `EmployeeFormPage.test.tsx`, `ProjectAssignPage.test.tsx`(새 사례).
6. **저장 뒤 재조회 실패.** 인력 배치 화면에서 배치 저장(201) 뒤 `GET /api/projects/<id>`가 500이면: 프로젝트 이름 h1과 입력 폼이 그대로 있고(저장이 성공했으므로 투입률 입력만 비워진다), "프로젝트를 다시 불러오지 못했습니다." 알림이 보인다. "다시 불러오기"를 누르면 프로젝트 요청만 한 번 더 나가고(후보·일정 요청은 늘지 않는다) 성공하면 알림이 사라진다 — 확인: Vitest `ProjectAssignPage.test.tsx`(응답 보류·해제로 재조회를 가로챔, 새 사례).
7. **처음 조회 실패와 404는 그대로.** 처음 `GET /api/projects/<id>`가 500이면 오류 화면과 "다시 시도", 404면 "프로젝트를 찾을 수 없습니다" — 확인: 기존 `ProjectAssignPage.test.tsx` 사례(고치지 않는다, regression).
8. **실제 서버 e2e (읽기만, 서버가 400으로 거절).** `project.manager`로 `/projects/new`에서 이름 `포커스 확인`, 시작일 `2026-12-31`, 종료일 `2026-01-01`, 상태 `진행 중`으로 저장하면 서버가 400을 돌려주고(저장되지 않음) 시작일·종료일 input이 `aria-invalid="true"`, 시작일이 포커스를 갖고 메시지가 종료일 줄 아래에 위험 색 `rgb(191, 43, 27)`으로 보인다. 1280px와 1024px(프로젝트 폼이 보이는 두 폭; 1024px 미만에서는 폼이 숨겨지고 데스크톱 안내가 나온다, D29), 가로 넘침 없음 — 확인: Playwright `frontend/e2e/project-form.spec.ts`(새 사례).
9. **기존 폼 동작 회귀.** 기존 `TextField.test.tsx`, `SelectField.test.tsx`, `ProjectFormPage.test.tsx`, `EmployeeFormPage.test.tsx`, `LoginPage.test.tsx`, `ProjectAssignPage.test.tsx`, `project-form.spec.ts`, `employee-form.spec.ts`, `projects-assign.spec.ts`의 기존 사례가 고치지 않고 통과한다. 예외는 `fieldset`의 `aria-invalid`를 단언하던 아래 줄뿐이고, 새 기준(기준 2~4)에 맞게 고친다: `fieldset` `aria-invalid="true"` 단언(`ProjectFormPage.test.tsx:427,443,489,507`, `EmployeeFormPage.test.tsx:412`)은 해당 input의 `aria-invalid="true"` 단언으로, "다시 저장하면 지워짐"의 `fieldset` `not aria-invalid` 단언(`ProjectFormPage.test.tsx:493`, `EmployeeFormPage.test.tsx:416`)은 해당 input의 `not aria-invalid` 단언으로 바꾼다. `fieldset`의 `aria-describedby`·설명 단언(`toHaveAccessibleDescription`, `not aria-describedby`)은 고치지 않는다. 고친 줄과 이유를 증거에 적는다 — 확인: `npm --prefix frontend run test`, `test:e2e`.
10. **전체 회귀.** `make build`, `make test`, `make lint` — 작업 전후 통과.

## 검증 명령

- 새 검사:
  - `npm --prefix frontend run test -- TextField SelectField ProjectFormPage EmployeeFormPage ProjectAssignPage` — 기준 1~7.
  - `bash scripts/e2e-servers.sh -- npm --prefix frontend run e2e:run -- project-form.spec.ts` — 기준 8 (읽기만, 공유 e2e DB; 서버는 400으로 거절하므로 저장 없음).
- 시작 전 준비(구현 단계, 기능 코드 전): 새 사례를 기존 테스트 파일에 쓴다. 새 컴포넌트·파일이 없으므로 스텁은 필요 없다.
- 레드(기능 전에 실패해야 하는 단언):
  - 기준 1: `aria-describedby="x"`가 내부 값에 덮여 `"x <id>"`가 아니라 메시지 id 하나 / 오류 없을 때 `undefined`.
  - 기준 2~4: 입력의 `aria-invalid`가 null, `fieldset`에는 `aria-invalid="true"`가 있어 `not.toHaveAttribute` 단언 실패.
  - 기준 5: `document.activeElement`가 저장 버튼.
  - 기준 6: 재조회가 500이면 h1이 사라지고 오류 화면이라 `getByRole('heading', { level: 1 })` 단언 실패.
  - 기준 8: 시작일 input에 `aria-invalid`가 없다.
- 회귀 검사: 기준 7·9·10. `make test`, `make lint`, `make build`는 작업 전후 모두 통과해야 한다(이 환경에 `make`가 없으면 Makefile 레시피의 명령을 그대로 실행하고 증거에 적는다).

## 하지 않을 일

- 로그인 화면(`LoginPage`)의 포커스 이동 — 이미 `TextField`를 쓰고 있고 이 변경의 대상이 아니다(기준 9에서 회귀만 확인).
- 폼 라이브러리·`useForm` 훅 도입, 폼 구조 정리, `ProjectAssignPage` 상태 분리(회고 보류 항목 F#7–F#10).
- 모든 오류 메시지에 `role="alert"`를 붙이거나 live region을 새로 만들기 — 입력에 포커스가 가면 `aria-describedby`로 메시지가 읽히는 것으로 충족한다 `(제안)`.
- 서버 오류 코드·메시지, API, 백엔드 변경. #53(기간 길이)과 #55(401 처리, 같은 `ProjectAssignPage`)의 변경.
- 후보 표·간트의 자체 재조회 오류 표시 — 이미 각자 오류 상태가 있다(기준 6은 프로젝트 재조회만).
- 필요 역량·기술 오류의 위치를 줄별로 정밀하게 가리키는 일 — 서버 오류에 줄 번호가 없으므로 첫 줄에 연결한다 `(제안)`.
