# T#28 내 정보 API: GET /api/me/employee

## 산출물

로그인한 계정에 연결된 직원의 상세를 #8의 직원 상세와 같은 모양으로 돌려주는 읽기 API `GET /api/me/employee`가 있다.

## 작업량

이슈 #28 그대로 하나로 한다. 예상 약 2.5시간(컨트롤러와 서비스 연결 0.5시간, 새 검사 1시간, 레드·그린과 증거 1시간).

## 전제

- 근거: REQ-CONTEXT D17(계정 하나는 직원 한 명과 1:1), D24("내 정보"는 본인의 직원 상세, 읽기 전용), D25(직원 역할만
  가진 계정은 본인 상세만 본다), D33(오류 본문 `{code, message}`), D36.
- 로그인한 계정의 직원 ID는 #6의 세션 사용자 `AccountPrincipal.employeeId()`에서 읽는다. 요청의 경로·쿼리·본문에서 직원 ID를
  받지 않는다. 그래서 다른 사람의 상세를 고를 방법이 없다.
- 응답은 #8의 `EmployeeService.detail(id)`가 만드는 `EmployeeDetailResponse` 그대로다(`id, name, departmentId,
  departmentName, jobTitle, careerYears, availabilityStatus, unavailableReason, unavailableUntil, currentAvailability,
  needsReview, skills, assignments`). 계산을 새로 하지 않는다(D36).
- 권한은 #6의 보안 설정 그대로다: `GET /api/me/**`는 로그인한 모든 역할 허용, 비로그인은 401 `AUTH_REQUIRED`, `/api/me/**`의
  쓰기는 표에 없어 403 `AUTH_FORBIDDEN`(`ApiSecurityFilterChain.java:84`, `anyRequest().denyAll()`). 이 태스크는 보안 설정과
  #6의 권한 표를 바꾸지 않는다.
- 새 컨트롤러는 `com.ax.rms.employee` 패키지에 두어 #8의 `EmployeeApiExceptionHandler`가 `EmployeeApiException`을 그대로
  `{code, message}`로 바꾸게 한다. 새 예외 처리기를 두지 않는다.
- 시드 데모 계정과 연결된 직원(`SeedRunner.java` `insertDemoAccounts`): `hr.manager` → 이수민, `project.manager` → 정하늘,
  `employee.demo` → 한지우, `dual.manager` → 오승현.

## 수용 기준

1. **본인 상세 (D24, D25).** 각 데모 계정으로 로그인해 `GET /api/me/employee`를 부르면 200이고, 본문이 그 계정에 연결된
   직원의 상세다: `employee.demo` → `name` "한지우", `hr.manager` → "이수민", `project.manager` → "정하늘",
   `dual.manager` → "오승현". 각 응답의 `id`는 같은 세션의 `GET /api/auth/me`의 `employeeId`와 같다.
   - 확인: `MeEmployeeApiTest`(새 클래스, `AbstractApiTest`, 실제 포트, 임시 SQLite, 고정 `Clock`).
   - 준비: 테스트 클래스만 둔다(구현 스텁 없음). 레드: 컨트롤러가 없어 `GET /api/me/employee`가 404라 상태 `200` 단언이 실패한다.
2. **#8 상세와 같은 모양과 값.** 네 계정 각각에 대해 `GET /api/me/employee`의 JSON이 `hr.manager`로 부른
   `GET /api/employees/{그 id}`의 JSON과 같다(키 집합, 키 순서와 무관하게 값 전체, `skills`·`assignments` 배열 순서 포함).
   - 확인: `MeEmployeeApiTest`. 준비·레드: 기준 1과 같다(404라 본문 비교 전에 상태 단언이 실패한다).
3. **다른 사람을 고를 수 없음 (D25).** `employee.demo`로:
   - `GET /api/me/employee?id=1`과 `GET /api/me/employee?employeeId=1`은 쿼리를 무시하고 본인(한지우) 상세를 돌려준다.
   - `GET /api/me/employee/1`은 404이고 본문에 다른 직원의 이름이 없다.
   - `GET /api/employees/1`은 403 `AUTH_FORBIDDEN`이다(#6 규칙, 회귀).
   - 확인: `MeEmployeeApiTest`. 준비·레드: 기준 1과 같다(쿼리를 붙인 요청도 404라 상태 `200` 단언이 실패한다).
4. **비로그인과 쓰기 (#6 정책, 회귀).** 비로그인 `GET /api/me/employee`는 401 `AUTH_REQUIRED`. `employee.demo`와
   `dual.manager`의 `PUT`·`PATCH`·`POST`·`DELETE /api/me/employee`는 403 `AUTH_FORBIDDEN`이다.
   - 확인: `MeEmployeeApiTest`와 #6의 `AuthorizationPolicyTest`(`GET /api/me/employee`, `PUT /api/me/employee` 행). 이미
     지금도 통과하는 동작이라 회귀 검사다: 근거 `ApiSecurityFilterChain.java:84`(`GET /api/me/**` 인증 필요)와
     `anyRequest().denyAll()`, base에서의 통과 실행 기록.
5. **값이 바뀌면 따라온다.** `hr.manager`가 `PATCH /api/employees/{한지우 id}/status`로 한지우를 `UNAVAILABLE`(사유
   "교육", 복귀일 오늘+30일)로 바꾼 뒤, `employee.demo`의 `GET /api/me/employee`에서 `availabilityStatus`가
   `UNAVAILABLE`, `unavailableReason`이 "교육"이다(저장된 값을 매번 읽는다. 세션에 담아 두지 않는다).
   - 확인: `MeEmployeeApiTest`(이 테스트만 쓰기를 하므로 마지막 순서이고, 임시 DB라 다른 테스트에 남지 않는다). 준비·레드: 기준
     1과 같다.
6. **회귀.** `make build`, `make test`, `make lint`가 작업 전후에 통과한다. #8의 `EmployeeApiTest`·`EmployeeListSkillsTest`,
   #6의 `AuthApiTest`·`AuthorizationPolicyTest`, `AvailabilityCalculatorTest`는 고치지 않고 통과한다.
   - 확인: 작업 전 base 실행과 작업 후 실행을 각각 기록한다.

## 검증 명령

- 새 검사: `./backend/mvnw -f backend/pom.xml -Dtest=MeEmployeeApiTest test` — 기준 1, 2, 3, 5. 작업 전에는 `/api/me/employee`가
  404라 첫 상태 `200` 단언이 실패하고, 작업 뒤 통과한다.
- 회귀 검사: `make build`, `make test`, `make lint`는 작업 전후에 통과한다(기준 4, 6). 작업 후의 `make test`에는 새 검사가
  들어간다.

## 격리

새로 건드리는 DB·폴더·서비스·포트는 없다. 백엔드 검사는 T#5 규칙대로 JUnit `@TempDir` 임시 SQLite와 고정 `Clock`, 임의 포트를
쓴다. 기준 5의 상태 변경도 그 임시 DB에서만 일어난다. 외부 네트워크를 쓰지 않는다(D40).

## 하지 않을 일

- "내 정보" 화면(→ #14). 이 태스크는 API만 만든다.
- 본인 정보 수정, 비밀번호 변경, 계정 정보(`/api/auth/me`) 변경.
- `ApiSecurityFilterChain`·#6 권한 표 변경, 새 역할, 새 예외 처리기.
- #8 상세 응답의 필드 추가·변경, 가용률·확인 필요 계산 변경.
- 연결된 직원이 없는 계정 처리: D17로 계정은 직원과 1:1이고 직원 삭제 기능이 없다. 그래도 직원을 찾지 못하면 #8과 같은 404
  `EMPLOYEE_NOT_FOUND`가 나가며, 이 태스크는 그 경우를 따로 만들지 않는다.
