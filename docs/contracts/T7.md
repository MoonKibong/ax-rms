# T#7 가용률 계산 엔진

## 산출물

`backend/`에 날짜별 투입률 합계·기간 가용률(최저일)·현재 가용률을 계산하는 순수 도메인 클래스(`AvailabilityCalculator`, 패키지 `com.ax.rms.availability`)가 있고, 겹침·비겹침·부분 겹침·종료된 프로젝트(현재 가용률에서만 제외)·주말 포함·§7 정상 배치 단위 테스트가 통과한다.

## 설계 (계약서 수준)

`AvailabilityCalculator`는 DB나 Spring 컨텍스트에 의존하지 않는 순수 클래스다 — `List<Assignment>`만 받아 계산하고, 단위 테스트는 손으로 만든 값만으로(DB·시드 없이) 돈다.

- `int dailyTotal(List<Assignment> assignments, LocalDate day)` — `day`가 `[assignment.startDate, assignment.endDate]` 안에 있는 배정들의 `allocationPercent` 합(D7 "기간이 겹치는 배정만 합산"). **프로젝트 상태·종료 여부와 무관하게 전부 더한다** — 과거에 끝난 프로젝트의 배정도 그날이 자기 기간 안이면 포함된다(간트 등 "그날 실제 겹친 투입률"을 보여줄 다른 화면이 이 값을 그대로 쓸 수 있어야 한다). 주말·공휴일도 똑같이 계산한다(D18) — 달력상 특별 취급 없음.
- `int periodAvailability(List<Assignment> assignments, LocalDate rangeStart, LocalDate rangeEnd)` — `[rangeStart, rangeEnd]`의 각 날짜에서 `100 - dailyTotal(...)`을 구해 그 중 최저값을 돌려준다(D18 "기간의 가용률은 그 기간 중 가장 낮은 날의 값이다"). `dailyTotal`과 마찬가지로 종료 여부를 따지지 않는다.
- `boolean isEnded(Project project, LocalDate today)` — D19: `project.status() == DONE` 이거나 `project.endDate()`가 `today`보다 이전이면 종료된 프로젝트다.
- `int currentAvailability(List<Assignment> assignments, Map<Long, Project> projectsById, LocalDate today)` — **종료된 프로젝트(`isEnded`)의 배정을 뺀 나머지**로 "오늘"(`today`) 하루치 가용률을 구한다(D7 "종료된 프로젝트는 현재 가용률에서 뺀다", D19 "현재 가용률은 오늘 하루의 가용률이다"). 즉 `assignments`를 `isEnded`가 아닌 것만 걸러 `100 - dailyTotal(걸러진 목록, today)`. **`dailyTotal`·`periodAvailability`는 이 거름을 하지 않는다** — 오직 `currentAvailability`만 한다.
- "오늘"은 호출하는 쪽이 넘긴다(이 태스크는 자체 `Clock` 빈을 추가하지 않는다).

이 태스크는 이 계산을 실제 요청(API)에 연결하지 않는다 — D8 전체(신규 배치 저장 조건), 가용률 조회 API, 대시보드 집계, 간트 컴포넌트는 다른 태스크의 일이다.

## 수용 기준

각 테스트는 아래 입력 그대로 손으로 만든 `Assignment`/`Project` 값을 쓰고, 적힌 숫자와 정확히 같은지(`isEqualTo`) 확인한다 — 스텁이 `0`이나 `100`을 그대로 돌려주면 아래 숫자와 달라 반드시 실패한다.

1. **겹침(D7)**: 배정 A(기간 `2026-06-01~2026-06-30`, 투입률 `40`)와 배정 B(기간 `2026-06-10~2026-06-20`, 투입률 `35`)가 있을 때 `dailyTotal([A,B], 2026-06-15)` = **`75`**.
2. **비겹침(D7)**: 배정 A(`2026-01-01~2026-01-31`, `50`)와 배정 C(`2026-03-01~2026-03-31`, `20`)가 있을 때 `dailyTotal([A,C], 2026-01-15)` = **`50`**(C는 그 날을 덮지 않아 더하지 않음).
3. **부분 겹침**: 배정 A(`2026-02-01~2026-02-20`, `30`)와 배정 D(`2026-02-15~2026-02-28`, `40`)가 있을 때 `dailyTotal([A,D], 2026-02-10)` = **`30`**, `dailyTotal([A,D], 2026-02-18)` = **`70`**, `dailyTotal([A,D], 2026-02-25)` = **`40`**.
4. **`dailyTotal`은 종료된 프로젝트도 빼지 않음(D7) — 과거 날짜로 확인**: `today = 2026-06-15`. 프로젝트 P1(`status=DONE`, `endDate=2026-01-31`)의 배정 E1(`2026-01-01~2026-01-31` — 오늘보다 전인 과거 기간, `40`)이 있을 때 `dailyTotal([E1], 2026-01-15)` = **`40`**(P1이 이미 끝난 프로젝트여도, 그 날짜가 E1의 기간 안이면 그대로 더한다 — T#5 시드의 과거 `DONE` 프로젝트 배정과 같은 모양).
5. **`currentAvailability`만 종료된 프로젝트를 뺌(D7, D19)**: 같은 `today = 2026-06-15`. 프로젝트 P1(기준 4와 같음, `status=DONE`)의 배정 E1b(`2026-06-01~2026-06-30` — 이번엔 오늘을 포함, `40`), 프로젝트 P3(`status=IN_PROGRESS`, `endDate=2026-05-01` — 상태는 완료가 아니지만 종료일이 오늘 이전이라 역시 종료됨, D19)의 배정 E3(`2026-06-01~2026-06-30`, `15`), 프로젝트 P4(`status=IN_PROGRESS`, `endDate=2026-12-31` — 종료 안 됨)의 배정 E4(`2026-06-01~2026-06-30`, `25`)가 있을 때:
   - `dailyTotal([E1b,E3,E4], 2026-06-15)` = **`80`**(종료 여부와 무관하게 셋 다 더함 — 기준 4와 같은 메서드, 이번엔 오늘 날짜로).
   - `currentAvailability([E1b,E3,E4], {P1,P3,P4}, 2026-06-15)` = **`75`**(E1b·E3는 `isEnded`라 빠지고 E4의 `25`만 남아 `100-25`).
6. **기간 가용률은 최저일(D18)**: 배정 H(`2026-07-01~2026-07-10`, `20`)와 배정 I(`2026-07-05~2026-07-08`, `50`)가 있을 때 `periodAvailability([H,I], 2026-07-01, 2026-07-10)` = **`30`**(겹치는 `2026-07-05~08`의 그날 투입률 합 `70` → 가용률 `30`이 가장 낮음).
7. **주말도 똑같이 계산(D18)**: 배정 K(`2026-07-18~2026-07-18`, `45` — 2026-07-18은 토요일)가 있을 때 `dailyTotal([K], 2026-07-18)` = **`45`**(평일과 똑같이 포함).
8. **현재 가용률(D19)**: `today = 2026-08-10`. 종료되지 않은 프로젝트 P5(`status=IN_PROGRESS`, `endDate=2026-12-31`)의 배정 L(`2026-08-01~2026-08-20`, `40`)이 있을 때 `currentAvailability([L], {P5}, 2026-08-10)` = **`60`**.
9. **§7 "정상 배치" 시나리오**: 배정 M(`2026-09-01~2026-09-30`, `60`)과 배정 N(`2026-09-10~2026-09-20`, `30`)이 있을 때 `periodAvailability([M,N], 2026-09-10, 2026-09-20)` = **`10`**(그 구간 모든 날의 합이 `90` → 가용률 `10`).
10. **회귀**: `make build`, `make test`, `make lint`가 그대로 통과한다(T#3·T#5의 기존 코드는 바뀌지 않음) — 확인: `make build`/`make test`/`make lint`(baseline: T#5 머지 커밋, 이미 통과 상태 유지).

## 검증 명령

- 새 검사(전부 `backend/src/test/java/com/ax/rms/availability/AvailabilityCalculatorTest.java`, DB·Spring 컨텍스트 없는 순수 단위 테스트):
  - `./backend/mvnw -f backend/pom.xml -Dtest=AvailabilityCalculatorTest test` — 기준 1~9
  - 레드(기준 1~9 전부 같은 방식): `AvailabilityCalculator`의 각 메서드를 `dailyTotal`→`0`, `periodAvailability`→`0`, `currentAvailability`→`100`을 그대로 돌려주는 스텁으로 먼저 둔다. 위 수용 기준의 기대값(`75`, `50`, `30`/`70`/`40`, `40`, `80`/`75`, `30`, `45`, `60`, `10`)은 모두 스텁 값(`0` 또는 `100`)과 달라, 스텁 상태에서 전부 실패한다.
- 회귀 검사: `make build`, `make test`, `make lint` — 작업 전후 모두 통과해야 한다.

## 하지 않을 일

- 신규 배치 저장 조건(D8) 전체 검증(투입 가능 여부, 가용률>0, 중복 배정, 프로젝트 기간 안 등) — → T#10(배치 API). 이 태스크는 계산 결과(숫자)만 돌려주고, 그 결과로 저장을 막을지는 T#10이 정한다.
- 가용률·배치를 보여주는 REST API, 저장소 조회 연결 — → T#8·T#9·T#10·T#11. 이 태스크는 `AssignmentRepository`/`ProjectRepository`를 직접 호출하지 않는다(순수 계산만).
- 대시보드 집계(가용 인원 수, 인력 부족 프로젝트 등, D20·D23) — → T#11.
- 간트 차트가 `dailyTotal`을 쓰는 연결 — → T#12(간트 차트 컴포넌트), 디자인 브리프 3.6절.
- 프런트엔드 변경 — 이 태스크는 `backend/`만 건드린다.
