# T#14 직원 상세·등록·수정 화면 (내 정보 포함)

## 산출물

로그인한 관리자가 `/employees/<id>`에서 한 직원의 정보·기술·배치 현황(간트와 표)·현재 가용률을 API 값 그대로 보고, 인력
관리자는 넓은 구간에서 직원을 등록·수정하고 투입 상태를 바꾸며(규칙 위반 원인은 그 입력 아래), 직원은 `/me`에서 같은 상세를
읽기 전용으로 보는 화면이 있다.

  정수 여부, 주소의 id 형식)만 보내기 전에 검사하고, 나머지 규칙은 서버 하나가 판단한다.

### 경로와 역할 (D9, D24, D25, D29)

| 경로 | 비로그인 | 직원만 | 프로젝트 관리자 | 인력 관리자·겸임 |
|---|---|---|---|---|
| `/employees` | `/login` | `/me` | 목록(버튼 없음) | 목록, 넓은 구간에서 "직원 등록" |
| `/employees/:id` | `/login` | `/me` | 상세(버튼 없음) | 상세, 넓은 구간에서 "수정"·"상태 변경" |
| `/employees/new` | `/login` | `/me` | `/employees`로 | 넓은 구간: 등록 폼, 좁은 구간: 데스크톱 이용 안내 |
| `/employees/:id/edit` | `/login` | `/me` | `/employees/:id`로 | 넓은 구간: 수정 폼, 좁은 구간: 데스크톱 이용 안내 |

- "인력 관리자"는 `roles`에 `HR_MANAGER`가 있는 계정(`hr.manager`, `dual.manager`)이다. 서버는 #6 표대로 다른 역할의 직원
  쓰기를 403으로 막는다. 화면은 버튼을 숨기고 폼 주소를 돌려보낼 뿐, 권한을 정하지 않는다.
- `:id`는 `^[1-9][0-9]*$`여야 한다. 아니면(예: `/employees/abc`, `/employees/abc/edit`) 요청을 보내지 않고 StateMessage
  `error`, 설명 "직원을 찾을 수 없습니다."를 보인다 (제안). `/employees/new`는 id가 `new`인 상세가 아니다.
- 셸의 현재 항목은 `/employees/…`에서 "직원", `/me`에서 "내 정보"다.
- **좁은 구간 (D29, BRIEF 6절)**: 관리 버튼("직원 등록", "수정", "상태 변경")은 1023px 이하에서 `display: none`이다. 등록·수정
  주소는 아래 "데스크톱 이용 안내"를 보인다. 상태 변경 대화상자는 주소가 없고 그 버튼으로만 열린다.

### 상세 `/employees/:id` (BRIEF 6.4)

구역 제목은 h2 lg/600, 구역 사이는 `--space-6`(32px)이다(BRIEF 6.0의 구역 규칙을 따름, 제안).

1. **머리**: 이름(h1, xl/700). 그 아래 한 줄(`flex-wrap`, 간격 `--space-2`): 상태 `Badge`(`투입 가능`/`투입 불가`),
   `needsReview`가 참이면 `확인 필요` `Badge`(제안), "현재 가용률"(sm, text-muted)과 값 `40%`(sm/600, `tabular-nums`).
2. **기본 정보**: `dl` 줄마다 라벨(`dt`, sm/600 text-muted, 너비 120px)과 값(`dd`, md/400 text) (제안). 순서: 부서, 직무,
   경력(`5년`), 투입 불가 사유, 종료 예정일(`YYYY-MM-DD`). 값이 `null`이면 `—`(text-muted).
3. **기술**: `ul`, 줄마다 `Java · 고급`(API 순서, 숙련도 `초급`·`중급`·`고급`). 없으면 `—`.
4. **배치 현황**: `Gantt`, 그 아래 `DataTable` 프로젝트 · 기간 · 투입률(API 순서 = `startDate` 오름차순).
   - 간트 입력: 배정마다 `{id: "<projectId>-<startDate>", projectName, projectStatus, start: startDate, end: endDate,
     rate: allocationPercent}`. `projectStatus`는 `PLANNED`→`계획`, `IN_PROGRESS`→`진행 중`, `DONE`→`완료`,
     `ON_HOLD`→`보류`. `today`는 응답의 `today`다. 종료된 프로젝트의 배정도 그대로 넘긴다(#8, D15).
   - 표: 프로젝트명은 일반 글자(프로젝트 상세 링크는 #16), 기간 `2026-09-23 ~ 2026-11-22`, 투입률 `60%`(끝 정렬,
     `tabular-nums`).
   - 배치가 없으면 간트의 `empty` "배치된 프로젝트가 없습니다" 하나만 보이고 표는 그리지 않는다.
5. **버튼 줄**(인력 관리자, 넓은 구간): primary "수정"(→ `/employees/:id/edit`), secondary "상태 변경"(대화상자), 간격
   `--space-2`.

### 등록 `/employees/new`, 수정 `/employees/:id/edit` (BRIEF 6.4 폼)

- 제목(h1): "직원 등록", "직원 수정".
- 불러오기: 등록은 `GET /api/departments`, 수정은 그것과 `GET /api/employees/{id}`를 함께 부른다. 하나라도 실패하면 StateMessage
  `error`(API `message`가 있으면 그 글자)와 "다시 시도"이고, 다시 시도는 실패한 요청을 다시 보낸다.
- `form`은 `noValidate`다(브라우저 기본 검사 말풍선 대신 BRIEF의 오류 표시를 쓴다). 한 열, 최대 너비 560px, 필드 사이
  `--space-4`(16px) (제안). 필드 순서(D2):
  1. 이름 `*` — `TextField`.
  2. 부서 `*` — `SelectField`: "선택하세요"(빈 값), 그 뒤 부서 응답 순서대로(글자 `name`, 값 `id`). 수정은 그 직원의 부서가
     골라져 있다.
  3. 직무 `*` — `TextField`.
  4. 기술 — `fieldset`(legend "기술", sm/600). 기술 줄마다 `TextField` "기술 이름", `SelectField` "숙련도"("선택하세요",
     `초급`, `중급`, `고급`), secondary "삭제"(접근 이름 "기술 N 삭제"). 줄 아래 secondary "기술 추가"는 빈 줄을 끝에 더하고 그
     줄의 기술 이름에 포커스를 둔다. 수정은 API 순서대로 줄이 차 있다. 한 줄은 `1fr 140px auto`다 (제안).
  5. 경력(년) `*` — `TextField` `type="number"`, `min=0`, `step=1`, `inputMode="numeric"`.
- 버튼 줄: secondary "취소", primary "저장"(BRIEF 3.6 대화상자와 같은 순서, 제안).
- **요청**: 등록 `POST /api/employees`, 수정 `PUT /api/employees/{id}`, `Content-Type: application/json`, 본문은 정확히
  `{"name", "departmentId", "jobTitle", "careerYears", "skills": [{"skillName", "proficiencyLevel"}]}`.
  - `name`, `jobTitle`, `skillName`은 앞뒤 공백을 지운다 (제안). `departmentId`는 고른 id 숫자, 안 골랐으면 `null`.
    `proficiencyLevel`은 고른 값, 안 골랐으면 `""`. 기술 줄은 화면 순서대로 모두 보낸다(빈 줄도 보내 서버가 판단한다).
  - `careerYears`: 빈 칸이면 `null`. `^-?[0-9]+$`이고 −2147483648–2147483647이면 그 정수. 그 밖(`1.5`, `1e2`,
    `99999999999`)이면 요청을 보내지 않고 경력 아래에 "경력은 정수로 입력하세요."를 보인다 (제안. 서버가 잘라 저장하거나 기본
    400을 주는 값이다). 음수는 서버가 판단한다.
- **서버 오류의 자리 (D33)**: 메시지는 API `message` 그대로, TextField 오류 규칙(BRIEF 3.2)으로 보인다.

### 상태 변경 대화상자 (D6, BRIEF 6.4)

- "상태 변경"을 누르면 열린다. 제목 "상태 변경"(h2, lg/600).
- 필드: 상태 `*` `SelectField`("투입 가능", "투입 불가", 처음 값은 지금 상태). "투입 불가"일 때만 사유 `*` `TextField`(처음 값은
  지금 사유 또는 빈 칸)와 종료 예정일 `TextField` `type="date"`(지금 값 또는 빈 칸)를 보인다. "투입 가능"이면 둘을 그리지 않는다(#8이
  `null`로 지운다).
- 버튼: secondary "취소", primary "저장".
- 요청 `PATCH /api/employees/{id}/status`, 본문은 정확히: 투입 불가면 `{"availabilityStatus": "UNAVAILABLE", "unavailableReason":
  <앞뒤 공백을 지운 사유>, "unavailableUntil": <"YYYY-MM-DD" 또는 빈 칸이면 null>}`, 투입 가능이면 `{"availabilityStatus":
  "AVAILABLE", "unavailableReason": null, "unavailableUntil": null}`.
- 오류: 400 `EMPLOYEE_REASON_REQUIRED`는 사유 아래, 400 `EMPLOYEE_STATUS_INVALID`는 상태 아래, 그 밖은 대화상자 버튼 줄 위
  메시지(폼과 같은 규칙).
- 저장 중: "저장" loading, "취소" 비활성, Esc로 닫히지 않는다 (제안).
- 성공(200): 대화상자가 닫히고, 상세는 응답 본문(서버가 다시 읽은 상세)으로 바뀐다: 배지, 사유, 종료 예정일, 확인 필요, 가용률.
  배치는 그대로다(D6). 포커스는 "상태 변경"으로 돌아간다.
- 취소·Esc: 요청 없이 닫고 입력을 버린다. 포커스는 "상태 변경"으로 돌아간다. 바탕을 눌러도 닫히지 않는다 (제안).

### 불러오는 동안과 상태 (BRIEF 6절, 3.3)

- 불러오는 중: 내용 자리에 `Spinner` 24px와 "불러오는 중…"(sm, text-muted), 그 영역에 `aria-busy="true"`.

### 컴포넌트 값

- **`SelectField` 오류·필수** (BRIEF 3.2 "선택 상자는 TextField와 같은 … 오류 규칙"): `error`가 있으면 테두리 danger, 메시지는
  `select` 바로 아래 4px, 왼쪽 끝 맞춤, sm/400 danger와 16px 경고 아이콘, `aria-invalid="true"`와 메시지를 가리키는
  `aria-describedby`. `required`면 라벨 뒤 `*`(danger, `aria-hidden`)와 `select`의 `required`. #13의 동작은 그대로다.
- **`Dialog`** (BRIEF 3.6 "화면 안 대화상자", #17의 배치 해제도 쓴다): `role="dialog"`, `aria-modal="true"`, 제목을 가리키는
  `aria-labelledby`. 열리면 첫 입력(여기서는 상태)에 포커스, Tab·Shift+Tab은 대화상자 안을 돈다, 바깥 본문은 포커스를 받지
  않는다, Esc는 `onClose`. 너비 `min(480px, 100vw − 32px)`, 화면 가운데, surface, `--radius-md`, `--shadow-md`, 패딩
  `--space-6`. 바탕은 화면 전체를 `var(--color-text)` 불투명도 0.4로 덮는다(새 토큰 없음) (제안). `<dialog>`의
  `showModal()`로 만들어도 된다.

## 실행별 임시 DB (e2e 저장 검사)

- `scripts/e2e-servers.sh`에 선택 `--fresh-db`를 더한다: `scripts/e2e-servers.sh [--fresh-db] -- <명령>`.
  - 선택이 없으면 지금과 같다(DB `backend/data/e2e.db`, 명령 환경에 `E2E_DB`를 두지 않는다).
  - `--fresh-db`면 백엔드 DB가 `<저장소>/.nexi-tmp/e2e-write.db`다. 순서: 출력 경로 확인(이 DB 파일과 `-journal`·`-wal`·`-shm`도
    심볼릭 링크이거나 일반 파일이 아니거나 저장소 밖이면 아무것도 쓰거나 지우지 않고 2로 끝난다) → 포트 확인(쓰이고 있으면 아무
    파일도 지우지 않고 끝난다) → 그 파일들을 지운다 → 빌드 → 백엔드를 `--file DB_PATH=.nexi-tmp/e2e-write.db`로 띄운다(빈 DB라
    시더가 D31 시드를 넣는다, D38) → 명령을 `E2E_DB=fresh` 환경으로 실행 → 서버를 내린다 → 그 파일들을 지운다(성공·실패·중단 모두).
  - 포트(18080, 14173), 프런트엔드 빌드, 서버 기록 파일은 지금과 같다. 두 실행이 동시에 돌 수 없다(포트 확인).
- Playwright: 새 프로젝트 `e2e-write`(`testMatch: 'write/*.spec.ts'`). 기존 `e2e` 프로젝트는 `write/**`도 제외한다. `screens`는
  그대로 `screens/*.spec.ts`만이다.
- `frontend/package.json`: `e2e:write`는 `playwright test --project=e2e-write`. `test:e2e`는 지금의 공유 DB 단계 다음에
  `bash ../scripts/e2e-servers.sh --fresh-db -- npm run e2e:write`를 잇는다(`&&`). 그래서 `make test`가 두 단계를 모두 돈다.
- `write/` 스펙은 첫 단계에서 `process.env.E2E_DB`가 `fresh`인지 확인하고, 아니면 요청을 하나도 보내지 않고 실패한다. 그래서 공유
  DB 서버로 잘못 돌려도 공유 DB에 쓰지 않는다.
- README "검사 격리" 표에 줄을 더한다: "e2e 저장 검사 DB 파일 | `<root>/.nexi-tmp/e2e-write.db`, 실행마다 새로 만들고 끝나면
  지운다 | `scripts/e2e-servers.sh --fresh-db`가 `--file DB_PATH=.nexi-tmp/e2e-write.db`로 띄운다".
