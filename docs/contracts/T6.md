## 인증 API

- `POST /api/auth/login`. 요청은 `Content-Type: application/json`, 본문 `{"username": "...", "password": "..."}`.
  - 성공: 200, `{"username", "employeeId", "employeeName", "roles"}`. `roles`는 `HR_MANAGER`, `PROJECT_MANAGER`, `EMPLOYEE` 이름의 목록이고 순서는 뜻이 없다.
  - 성공하면 세션을 만들고, 이미 세션이 있었으면 세션 ID를 새로 발급한다(세션 고정 방지).
  - 틀린 비밀번호와 없는 계정: 둘 다 401, `{"code": "AUTH_INVALID_CREDENTIALS", "message": "계정 또는 비밀번호가 올바르지 않습니다."}`. 두 경우의 응답은 같다.
  - `username`이나 `password`가 없거나 비었다: 400, `AUTH_INVALID_REQUEST`, "계정과 비밀번호를 입력하세요."
  - JSON이 아닌 요청(예: `application/x-www-form-urlencoded`): 415.
- `GET /api/auth/me`: 로그인 중이면 200과 로그인 성공과 같은 본문, 아니면 401 `AUTH_REQUIRED` "로그인이 필요합니다."
- `POST /api/auth/logout`: 204. 세션을 없앤다. 그 뒤 같은 쿠키로 보낸 `me`는 401이다.
- 권한이 없으면 403 `AUTH_FORBIDDEN` "이 작업을 할 권한이 없습니다."
- 오류 본문은 모두 `{"code", "message"}`이다(D33). 이후 API 태스크도 이 형식을 쓴다.
- 비밀번호와 해시는 어떤 응답에도 나오지 않는다.
- 세션 쿠키 `JSESSIONID`는 `HttpOnly`, `SameSite=Strict`, `Path=/`이다. 로컬 http 시연(D40)이라 `Secure`는 두지 않는다.
- CSRF 토큰은 쓰지 않는다. 세션 쿠키가 `SameSite=Strict`라 다른 사이트에서 온 요청에는 붙지 않고, 로그인은 JSON만 받는다(D40 로컬 한 대 시연).

## 권한 정책 (서버, 한 곳)

권한은 백엔드 보안 설정 한 곳에서 경로와 HTTP 메서드로 정한다. "허용"은 인증·권한 단계가 막지 않는다는 뜻이다. 처리기가 아직 없는 경로는 404처럼 401·403이 아닌 응답을 준다.

| 요청 | 비로그인 | 직원만 | 인력 관리자 | 프로젝트 관리자 | 겸임 |
|---|---|---|---|---|---|
| `GET /api/health`, `POST /api/auth/login` | 허용 | 허용 | 허용 | 허용 | 허용 |
| `GET /api/auth/me`, `POST /api/auth/logout` | 401 | 허용 | 허용 | 허용 | 허용 |
| `GET /api/me/**` (본인 데이터) | 401 | 허용 | 허용 | 허용 | 허용 |
| `GET /api/employees/**`, `/api/projects/**`, `/api/assignments/**`, `/api/dashboard/**` | 401 | 403 | 허용 | 허용 | 허용 |
| `POST`·`PUT`·`PATCH`·`DELETE /api/employees/**` | 401 | 403 | 허용 | 403 | 허용 |
| `POST`·`PUT`·`PATCH`·`DELETE /api/projects/**`, `/api/assignments/**` | 401 | 403 | 403 | 허용 | 허용 |
| 그 밖의 모든 요청 (예: `PUT /api/me/**`, `POST /api/dashboard`, `/api/unknown`) | 401 | 403 | 403 | 403 | 403 |

- "직원만"은 `EMPLOYEE` 말고 다른 역할이 없는 계정이다. 인력 관리자나 프로젝트 관리자 역할이 하나라도 있으면 모든 조회가 열리고, 쓰기는 D9를 따른다(D25).
- 직원만 가진 계정은 자기 직원 ID로도 `/api/employees/{id}`에 접근하지 못한다. 본인 데이터는 경로에 ID가 없는 `/api/me/**`로만 읽으므로, 다른 사람의 ID를 넣을 자리가 없다. 본인 상세 API(`GET /api/me/...`)의 내용은 T#8이 만든다.
- 내 정보는 읽기 전용이라(D24) `/api/me/**`의 쓰기는 기본 거부다.
- 이후 API 태스크(T#8–T#11)는 위 경로 아래에 API를 둔다. 새 경로가 필요하면 그 태스크의 계약서가 이 표를 바꾼다고 적는다. 표에 없는 요청은 기본 거부다.
- Spring의 오류 전달(`/error`)이 403으로 바뀌지 않아야 한다. 그래야 허용된 요청의 404·405·400이 그대로 나간다.

## 화면과 라우팅

| 경로 | 비로그인 | 직원만 | 관리자(인력·프로젝트·겸임) |
|---|---|---|---|
| `/login` | 로그인 화면 | `/me`로 | `/`로 |
| `/` | `/login`으로 | `/me`로 | T#4 참조 화면(T#18이 대시보드로 바꾼다) |
| `/employees`, `/projects` | `/login`으로 | `/me`로 | 제목만 있는 자리 화면(T#13·T#15가 바꾼다) |
| `/me` | `/login`으로 | 내 정보 자리 화면 | 내 정보 자리 화면(메뉴에는 없다) |
| 그 밖의 경로 | `/login`으로 | `/me`로 | `/`로 |

- **인증 확인**: 앱을 열면 `GET /api/auth/me`로 로그인 상태를 확인한다.
  - 응답 전에는 보호된 화면도 로그인 폼도 그리지 않고 "불러오는 중…"(sm, text-muted)을 보인다.
  - 401이면 로그인하지 않은 상태다.
  - 네트워크 오류나 5xx면 StateMessage `error`("데이터를 불러오지 못했습니다", "잠시 후 다시 시도하세요.")와 "다시 시도"를 보인다. 다시 시도는 `me`를 다시 부른다.
- **로그인 화면** (BRIEF §6.1): 셸 없이 가운데 카드 하나다.
  - 카드는 너비 최대 400px, 좁은 구간에서는 화면 너비 − 32px다. surface, 패딩 `--space-6`, 반경 `--radius-md`, `--shadow-sm`.
  - 순서: 앱 이름 "Workforce Planner" → TextField "계정"(`autocomplete="username"`) → TextField "비밀번호"(`type="password"`, `autocomplete="current-password"`) → primary "로그인"(카드 안쪽 전체 너비).
  - 빈 칸으로 제출하면 요청을 보내지 않는다. 빈 칸마다 그 입력 아래에 "계정을 입력하세요." 또는 "비밀번호를 입력하세요."를 TextField 오류 규칙으로 보인다.
  - 401이면 API의 `message`를 비밀번호 입력 아래에 TextField 오류 규칙으로 보인다.
  - 네트워크 오류나 5xx면 비밀번호 입력 아래에 "로그인하지 못했습니다. 잠시 후 다시 시도하세요."를 보인다.
  - 로그인 요청 중에는 버튼이 loading이고, 다시 누르거나 Enter를 눌러도 요청을 더 보내지 않는다. 다시 제출하면 앞의 오류 메시지를 지운다.
  - 성공하면 역할의 첫 화면(위 표)으로 간다. 원래 가려던 주소로 돌려보내지는 않는다.
- **셸의 사용자 영역** (BRIEF §4 "오른쪽은 사용자 영역(T#6)"):
  - header 오른쪽 끝에 둔다.
  - 넓은 구간(≥1024px)에서는 직원 이름(sm/400, text-muted)과 secondary 버튼 "로그아웃"을 `--space-3` 간격으로 둔다.
  - 좁은 구간(<1024px)에서는 "로그아웃" 버튼만 둔다. 이름은 내 정보 화면에서 본다.
  - 로그아웃은 `POST /api/auth/logout`이 끝나면 `/login`으로 간다.
- **역할별 메뉴** (BRIEF §4 표, D25):
  - 관리자 역할이 있는 계정: 대시보드 `/`, 직원 `/employees`, 프로젝트 `/projects`.
  - 직원만 가진 계정: 내 정보 `/me` 하나.
  - 현재 경로의 항목에 `aria-current="page"`를 둔다.
  - 로그인 뒤 `/`의 참조 화면도 이 셸(사용자 영역, 역할별 메뉴)로 그린다.
  - 사용자 정보 없이 `AppShell`을 그리면 T#4와 같다(세 항목, 사용자 영역 없음).
- **자리 화면**: `/employees`, `/projects`는 셸 안에 제목(xl/700) "직원", "프로젝트"만 둔다. `/me`는 제목 "내 정보"와 그 아래 직원 이름(md)을 둔다. 업무 화면 태스크가 이 자리를 바꾼다.

- **데이터**: e2e는 로그인과 로그아웃만 하고 데이터를 바꾸지 않는다.

## 수용 기준

1. **로그인 API (D16, D17, D32).** 데모 계정 4개가 각각 로그인된다. 200 본문의 `username`, `employeeName`(위 표), `roles`(집합으로 비교)가 맞고, `employeeId`는 저장소에서 찾은 그 계정의 직원 ID다. 본문에 `password`나 `passwordHash` 키가 없다.
   - 확인: `AuthApiTest`(실제 포트, 쿠키를 들고 다니는 HTTP 클라이언트).
   - 준비: 테스트 클래스와 HTTP 클라이언트만 둔다.
   - 레드: 로그인 처리기가 없어 `POST /api/auth/login`이 404라 "200이어야 한다" 단언이 실패한다.
2. **로그인 실패와 잘못된 요청.**
   - 틀린 비밀번호와 없는 계정은 둘 다 401이고, 같은 `code`와 `message`를 준다.
   - 빈 값이나 빠진 값은 400 `AUTH_INVALID_REQUEST`다.
   - form 요청은 415다.
   - 확인: `AuthApiTest`. 레드: 404라서 401·400·415 단언이 실패한다.
3. **me, 로그아웃, 세션 유지.**
   - 로그인하지 않은 `me`는 401 `AUTH_REQUIRED`다.
   - 로그인한 쿠키로 보낸 `me`는 200이고, 로그인 응답과 같은 본문이다.
   - `logout`은 204이고, 그 뒤 같은 쿠키로 보낸 `me`는 401이다.
   - 확인: `AuthApiTest`. 레드: `me`가 404라서 401 단언이 실패한다.
4. **세션 쿠키와 세션 고정 방지.**
   - 로그인 응답의 `Set-Cookie: JSESSIONID=…`에 `HttpOnly`와 `SameSite=Strict`가 있다.
   - A 계정으로 받은 세션 쿠키 S1을 들고 B 계정으로 다시 로그인하면, 새 쿠키 S2의 값이 S1과 다르다. 그 뒤 S1로 보낸 `me`는 401이다.
   - 확인: `AuthApiTest`. 레드: 로그인이 404라 `Set-Cookie`가 없어 실패한다.
5. **서버 권한 정책 (D9, D25).** 위 "권한 정책" 표를 그대로 검사한다. 비로그인과 계정 4개 각각에 대해 아래 요청의 응답을 단언한다.
   - 요청 목록:
     - `GET /api/employees`, `GET /api/employees?departmentId=1`(필터를 바꾼 요청)
     - `GET /api/employees/{다른 직원 ID}`, `GET /api/employees/{자기 직원 ID}`
     - `POST /api/employees`, `PATCH /api/employees/{ID}/status`
     - `GET /api/projects`, `POST /api/projects`, `PUT /api/projects/1`
     - `GET /api/assignments`, `POST /api/assignments`, `DELETE /api/assignments/1`
     - `GET /api/dashboard`, `POST /api/dashboard`
     - `GET /api/me/employee`, `PUT /api/me/employee`, `GET /api/unknown`
   - 기대값: 401·403은 그 값과 `code`를 단언한다. "허용"은 상태가 401도 403도 아님을 단언한다.
   - 직원만 계정은 주소를 바꾼 변형 `GET /API/employees`와 `GET /api//employees`에서도 2xx를 받지 못한다.
   - 확인: `AuthorizationPolicyTest`(실제 포트라 `/error` 전달까지 실제와 같다).
   - 레드는 두 번 받는다.
     - 레드 1 (비로그인 행): 보안 설정을 넣기 전에 실행한다. 비로그인 행이 401 대신 404로 실패한다.
     - 레드 2 (계정 행): 먼저 기준 1–4의 로그인 API를 구현한다. 이 단계의 보안 설정은 공개 경로 말고는 로그인만 요구하고, 역할 규칙은 없다. 역할 규칙을 넣기 전에 계정 행을 실행한다. 계정 4개 각각의 403 기대 요청이 403이 아닌 응답(처리기가 없어 404 또는 405)을 받아 실패한다.
     - 레드 2에는 계정마다 적어도 다음 요청이 들어간다:
       - `employee.demo`: `GET /api/employees`
       - `hr.manager`: `POST /api/projects`
       - `project.manager`: `POST /api/employees`
       - `dual.manager`: `PUT /api/me/employee`
     - 그 뒤 역할 규칙을 넣어 그린을 받는다. 증거에는 레드 2의 명령과 계정별로 실패한 단언(기대 403, 받은 상태)을 남긴다.
6. **기존 공개 API (T#3).** 비로그인 `GET /api/health`가 200 `{"status":"UP"}`이다.
   - 확인: `AuthorizationPolicyTest`의 비로그인 행.
   - 확인: 회귀 `HealthControllerTest`(`@WebMvcTest`)를 고치지 않고 통과한다.
   - 주의: `@WebMvcTest`는 `SecurityFilterChain`·`WebSecurityCustomizer` 타입의 컴포넌트만 가져온다. `@Configuration` 클래스의 `@Bean`은 가져오지 않는다(3.5.16 `WebMvcTypeExcludeFilter`). 그래서 이 슬라이스에서도 `/api/health`가 열리게 설정을 둔다.
7. **인증 확인과 라우트 보호 (D16, D25).** 위 "화면과 라우팅" 표대로 보낸다.
   - Vitest `frontend/src/AppRoutes.test.tsx`: `fetch`를 모킹하고 메모리 라우터로 그린다.
     - 비로그인이면 `/employees`에서 로그인 폼(라벨 "계정")이 보인다.
     - 직원만 계정은 `/employees`에서 "내 정보"로 간다.
     - 관리자는 `/login`에서 `/`로 간다.
     - `me`가 응답 전이면 "불러오는 중…"만 보인다.
     - `me`가 500이면 "다시 시도"가 보이고, 그것을 누르면 `me`를 다시 부른다.
   - Playwright `frontend/e2e/auth.spec.ts`:
     - 비로그인으로 `/`, `/employees`, `/projects`, `/me`, `/no-such`를 열면 경로가 `/login`이다.
     - `employee.demo`로 `/`, `/employees`, `/projects`, `/no-such`를 열면 `/me`다.
     - 관리자 계정 3개로 `/login`, `/no-such`를 열면 `/`다.
     - 로그인한 뒤 `page.reload()`해도 로그인이 남는다.
   - 레드(Vitest): 라우터 스텁이 모든 경로에 참조 화면을 그려서, 라벨 "계정"을 찾는 단언이 실패한다.
   - 레드(e2e): 백엔드 인증 API를 구현한 뒤, 프런트엔드 구현 전에 받는다. `/employees`의 경로가 `/login`이 아니라서 즉시 판정하는 단언이 실패한다.
8. **로그인 화면 (BRIEF §6.1, D33).**
   - Vitest `LoginPage.test.tsx`:
     - 라벨 "계정"·"비밀번호"가 입력과 연결되고, 비밀번호는 `type="password"`다.
     - 빈 제출은 `fetch`를 부르지 않고 두 메시지를 보인다.
     - 401이면 API 메시지를 비밀번호 입력의 `aria-describedby`가 가리키고, 입력은 `aria-invalid="true"`다.
     - 네트워크 오류면 "로그인하지 못했습니다. 잠시 후 다시 시도하세요."다.
   - e2e: 틀린 비밀번호를 넣으면 메시지가 비밀번호 입력 아래 4px 이내에 왼쪽 끝을 맞춰 보이고, 경로는 `/login` 그대로다. 이어서 맞는 비밀번호로 다시 제출하면 `/`로 간다(실패 뒤 재시도).
   - 레드: `null`을 그리는 스텁이라 `getByLabelText('계정')`가 실패한다.
9. **지연 응답과 겹친 동작.** e2e에서 `page.route`로 요청을 붙잡았다가 놓는다.
   - `/api/auth/login`:
     - 붙잡은 요청이 1개임을 기록한다.
     - 그동안 버튼은 `aria-busy="true"`이고, 너비가 붙잡기 전 너비와 같다(±0.5px).
     - 버튼을 다시 누르고 Enter를 눌러도 붙잡힌 요청은 1개 그대로다.
     - 놓으면 `/`로 간다.
   - 앱을 열 때 `/api/auth/me`:
     - 붙잡은 동안 "불러오는 중…"이 보이고, 로그인 폼과 `nav`는 0개다.
     - 놓으면(401) 로그인 폼이 나온다.
   - 레드: 기준 7의 e2e와 같다.
10. **셸 사용자 영역과 역할별 메뉴 (BRIEF §4, D25).**
    - Vitest `AppShell.user.test.tsx`(T#4의 `AppShell.test.tsx`는 그대로 둔다):
      - 관리자 사용자면 메뉴가 `['대시보드', '직원', '프로젝트']`다.
      - 직원만 사용자면 `['내 정보']`이고 href는 `/me`다.
      - 이름과 "로그아웃" 버튼이 있고, 로그아웃을 누르면 넘겨받은 처리기를 부른다.

      - header에 그 계정의 직원 이름이 있다.
      - 현재 항목이 `aria-current="page"`다.
    - 레드: 사용자 정보를 무시하는 셸이라 직원만 사용자의 메뉴가 세 항목이어서 실패한다.
11. **로그아웃.** e2e: "로그아웃"을 누르면 경로가 `/login`이 된다. 이어서 `/`를 열면 `/login`이고, `page.request.get('/api/auth/me')`가 401이다. 화면만 비운 것이 아니라 서버 세션이 끝났다는 뜻이다. 레드: 로그아웃 버튼이 없어 실패한다.

## 하지 않을 일

- 업무 API(직원·프로젝트·배치·대시보드)와 `/api/me/...`의 실제 내용 (→ T#8–T#11). 이 태스크는 그 경로의 권한만 정한다.
- 업무 화면 (→ T#13–T#18). `/`는 T#4 참조 화면이고, `/employees`, `/projects`, `/me`는 제목만 있는 자리 화면이다.
- 화면 안의 역할별 버튼 숨김(예: 프로젝트 관리자에게 직원 수정 버튼 숨김) (→ 각 화면 태스크).
- 계정 관리(등록·비밀번호 변경·잠금), 비밀번호 재설정, 로그인 시도 횟수 제한, "로그인 유지".
- 로그인 뒤 원래 가려던 주소로 돌려보내기. 역할의 첫 화면으로 간다.
- CSRF 토큰, HTTPS와 `Secure` 쿠키, 운영 배포 설정 (D40 로컬 시연).
- 세션 만료 시간 변경. 서블릿 기본값(30분)을 쓴다.
- 시드와 데모 계정 변경 (T#5).
- `scripts/e2e-servers.sh`, `scripts/nexi-isolated.sh` 수정.
