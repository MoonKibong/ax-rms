# T#3 Skeleton: Spring Boot·React·SQLite 구조와 make 명령

## 산출물

`backend/`(Java 21, Spring Boot 3.5.16, Maven Wrapper 3.10.0)와 `frontend/`(Node 24 LTS, React 19.3.0, TypeScript 5.9.3, Vite 8.3.4)의 뼈대 구조, 검사를 실제 DB 파일·포트에서 격리해 돌리는 `scripts/nexi-isolated.sh`가 있고, README 순서대로 하면 `make build`·`make test`·`make lint`가 통과하며 빈 SQLite 파일과 백엔드 상태 API, 프런트엔드 첫 화면이 뜬다.

## 버전과 호환성 확인

- Java 21 (OpenJDK, 로컬 확인 21.0.12) — D39가 이미 고정.
- Maven 3.10.0 (최신 안정 3.x; 4.x는 아직 RC) — Maven Wrapper(`./backend/mvnw`)로만 쓴다. 전역 `mvn` 설치나 PATH 설정에 의존하지 않는다.
- Spring Boot 3.5.16 (Maven Central에 실존, `spring-boot-starter-parent:3.5.16` 확인함; D39 "3.x 이상" 충족). 최신 4.x 라인(4.1.1)도 존재하지만 생태계·툴링 성숙도가 검증된 3.x 최신판을 쓴다.
- Node 24 LTS(로컬 확인 24.21.0) — D39가 이미 고정. npm 11.19.0.
- Vite 8.3.4, React 19.3.0, `@vitejs/plugin-react` 6.1.2 — npm 레지스트리에서 서로의 `peerDependencies`로 호환 확인(`@vitejs/plugin-react`가 `vite: ^8.0.0` 요구).
- **TypeScript는 5.9.3으로 정한다 (7.0.2 아님).** 이유: `typescript-eslint`(8.71.2, ESLint용 타입 인식 린트 도구)가 선언한 `peerDependencies.typescript`가 `>=4.8.4 <6.1.0`이라 TypeScript 7.x(네이티브/Go 컴파일러)를 지원하지 않는다(실제 npm 레지스트리 조회로 확인). 5.9.3은 이 범위의 최신 안정판이다.
- SQLite 드라이버: `org.xerial:sqlite-jdbc:3.53.4.0` (Maven Central에 실존, 플랫폼별 네이티브 바이너리를 포함해 배포되므로 별도 OS 패키지 설치가 필요 없다).
- Lint 기준은 **Checkstyle 하나로 정한다**: `maven-checkstyle-plugin:3.6.0` + `checkstyle:14.3.0`, 규칙은 `google_checks.xml`(Checkstyle에 내장). "Maven 컴파일 경고 0건" 방식은 쓰지 않는다. 프런트는 `typescript-eslint`의 recommended 설정을 쓴 `eslint`.

## 격리

검사(테스트·빌드·실행)가 건드릴 수 있는 대상과, 각각을 고르는 변수/파일:

| 대상 | 기본값 | 고르는 방법 |
|---|---|---|
| SQLite DB 파일 | `<저장소 또는 클론 루트>/backend/data/app.db` | 환경변수 `DATABASE_URL` (예: `jdbc:sqlite:/path/to.db`); `backend/src/main/resources/application.yml`에 `spring.datasource.url: ${DATABASE_URL:jdbc:sqlite:./data/app.db}`로 선언해, 설정이 없으면 기본값을 쓴다 |
| 백엔드 서버 포트 | `0`(OS가 빈 포트 자동 할당) | 환경변수 `SERVER_PORT` (Spring Boot 표준 환경변수, 코드 변경 없이 적용됨) |
| 빌드 산출물 폴더 | `backend/target/`, `frontend/node_modules/`, `frontend/dist/` | 전부 `--root`(저장소/클론) 안에만 생성되고 `.gitignore`로 제외됨; 별도 변수 없음 |
| 외부 서비스 | 없음 | D40: 이 프로젝트는 외부 시스템을 쓰지 않는다 |

`scripts/nexi-isolated.sh --root <dir> [--file <sqlite 경로>] [--port <포트>] -- <명령...>`:

- `<dir>`로 이동한 뒤 `DATABASE_URL=jdbc:sqlite:<file>`(`--file` 생략 시 기본값 `<dir>/backend/data/app.db`)과 `SERVER_PORT=<port>`(`--port` 생략 시 `0`)만 설정하고 주어진 명령을 실행한다.
- `--file`이 `--root` 밖을 가리키면(경로를 정규화해 비교) 실행을 거부하고 종료코드 2를 낸다 — 검사가 저장소/클론 밖의 실제 DB를 건드리는 사고를 막는다.
- README의 설치·설정·실행 각 단계도 이 스크립트를 "runner 옵션"으로 거쳐 실행하도록 적는다(아래 수용 기준 9).

## 수용 기준

1. `backend/`에 Maven Wrapper(`./backend/mvnw`, Maven 3.10.0)로 빌드되는 Spring Boot 3.5.16 프로젝트가 있고 `java.version`이 21로 고정돼 있다 — 확인: `./backend/mvnw -v` 출력에 Maven 3.10.0·Java 21이 보임.
2. `frontend/`에 Vite 8.3.4 + React 19.3.0 + TypeScript 5.9.3 프로젝트가 있고 Node 24 LTS·npm 전제가 `.nvmrc`(`24.21.0`)와 `frontend/package.json`(`engines.node`)에 적혀 있다 — 확인: 두 파일을 읽어 버전이 위와 일치.
3. 기계별 경로 금지: 저장소의 어떤 스크립트·설정·README·Makefile에도 특정 기계의 절대 경로(`/home/...`, `/Users/...` 등)나 전역 PATH·셸 프로파일(`.bashrc` 등) 변경이 없다 — 모든 실행은 `./backend/mvnw`, `npm`처럼 저장소 상대 경로의 wrapper로만 한다 — 확인: `grep -rnE "^|[^.]/home/|/Users/" backend frontend scripts Makefile README.md .nvmrc`가 빈 결과이고, 어떤 파일도 `~/.bashrc`/`~/.profile`/`~/.zshrc`를 쓰지 않는다.
4. `scripts/nexi-isolated.sh`가 위 "격리" 표의 기본값과 `--file`/`--port` 재정의를 그대로 따르고, `--root` 밖의 `--file`은 거부한다 — 확인: 새 셸 스크립트 테스트 `scripts/nexi-isolated-test.sh`(준비: 이 테스트 스텁을 먼저 작성; 레드: 스크립트가 아직 없어 "command not found"로 실패) — 작업 후: ①기본값 케이스 ②`--file`/`--port` 재정의 케이스 ③root 밖 `--file` 거부 케이스가 모두 통과.
5. 호출 셸의 `DATABASE_URL` 격리: 호출 셸에서 `DATABASE_URL`을 클론 밖의 sentinel 파일(예: `$(mktemp)`)로 가리키게 `export`한 채 `scripts/nexi-isolated.sh --root <clone> --file <clone>/backend/data/app.db -- <백엔드 테스트 명령>`을 실행해도, sentinel 파일의 크기·수정시각이 실행 전후로 바뀌지 않는다 — 확인: `scripts/nexi-isolated-test.sh`의 한 케이스로 포함(준비/레드는 4와 같음).
6. 빈 SQLite 파일 생성: `DATABASE_URL`(또는 기본값)이 가리키는 경로에 백엔드를 처음 실행하면 SQLite 파일이 새로 생기고, 이 파일은 git에 포함되지 않는다 — 확인: `ApplicationStartupTest`(준비: `spring-boot-starter-test`·`sqlite-jdbc` 의존성 추가, 테스트가 임시 디렉터리를 `DATABASE_URL`로 주고 `@SpringBootTest`로 컨텍스트를 올리는 스텁 작성; 레드: DataSource 설정이 없어 컨텍스트 로드가 실패) — 작업 후: 컨텍스트가 뜨고 지정한 경로에 파일이 생성됨을 확인. `.gitignore`의 `*.db`/`*.sqlite*` 규칙으로 git 추적 제외도 함께 확인.
7. 백엔드 상태 API `GET /api/health`가 200과 `{"status":"UP"}` 형태 응답을 돌려준다 — 확인: `HealthControllerTest`(MockMvc)(준비: `spring-boot-starter-web` 추가, 빈 `HealthController`와 테스트 스텁 작성; 레드: 컨트롤러가 라우트를 안 갖고 있어 404로 실패) — 작업 후: 200·`{"status":"UP"}` 통과.
8. 프런트엔드 첫 화면이 백엔드 상태 API를 호출해 그 결과를 보여 준다 — 확인: Vitest + React Testing Library `App.test.tsx`(준비: `vitest`·`@testing-library/react`·`jsdom` 설치, `fetch`를 모킹하는 최소 스텁 작성; 레드: `App`이 아직 상태 텍스트를 렌더링하지 않아 `getByText` 실패) — 작업 후: 모킹된 응답 텍스트가 화면에 보임이 통과.
9. 클린 카피 검사(명령으로): 이 태스크 커밋을 새 폴더 `<clone>`에 clone한 뒤, `scripts/nexi-isolated.sh --root <clone>`을 통해 README의 설치(의존성 전체 — `org.xerial:sqlite-jdbc` 네이티브 드라이버 포함 — 설치)·DB 준비·`make build`·`make test`·`make lint`를 README가 적은 순서대로 실행하면 전부 성공하고, 그 뒤 `<clone>`에서 `git status --porcelain --untracked-files=all`이 빈 출력이다 — 확인: 아래 "검증 명령"의 클린 카피 검사 명령을 그대로 실행.
10. `make build`가 backend(`./backend/mvnw -f backend/pom.xml package`)와 frontend(`npm --prefix frontend run build`)를 순서대로 실행해 성공한다 — 확인: `make build`(준비: Makefile의 `build` 타깃을 echo 자리표시자에서 실제 명령으로 바꾸고, 최소 컴파일 가능한 골격을 추가하기 **전**에 한 번 실행해 "pom.xml/package.json 없음"으로 실제로 실패하는지 확인; 레드는 이 자리표시자 교체 직후의 자연스러운 실패다, 지금의 echo 실패가 아니다) — 작업 후: 성공.
11. `make test`가 Checkstyle을 제외한 백엔드 테스트(6·7·4·5) 전체와 프런트 테스트(8)를 실행해 모두 통과한다 — 확인: `make test`(준비/레드는 각 테스트 항목과 동일) — 작업 후: 성공.
12. `make lint`가 backend(`./backend/mvnw -f backend/pom.xml checkstyle:check`, `google_checks.xml`)와 frontend(`npm --prefix frontend run lint` → `eslint .`, typescript-eslint recommended)를 실행해 통과한다 — 확인: `make lint`(준비: Checkstyle/ESLint 설정 추가 후, 의도적으로 하나의 규칙 위반을 넣어 실패를 확인한 뒤 제거; 레드는 이 더미 위반이다) — 작업 후: 위반 없이 성공.
13. `README.md`에 Java 21(OpenJDK 21.0.12)·Node 24 LTS(24.21.0)·npm(11.19.0) 버전, 설치·설정·실행 순서(백엔드·프런트엔드 각각), SQLite 파일 위치, 그리고 위 "격리" 표와 `scripts/nexi-isolated.sh` 사용법(runner 옵션으로 설명)이 적혀 있다 — 확인: 기준 9의 클린 카피 검사가 이 README를 그대로 따라 실행하므로 같은 명령으로 함께 확인됨.

## 검증 명령

- 새 검사: `make build`, `make test`, `make lint`, `scripts/nexi-isolated-test.sh`(기준 4·5), 클린 카피 검사(기준 9, 아래 명령). 각 검사의 준비와 레드 상태는 위 수용 기준에 적었다.
  - 클린 카피 검사 명령(예시):
    ```
    tmp=$(mktemp -d)
    git clone . "$tmp"              # 또는 origin, 이 태스크 커밋으로 checkout
    git -C "$tmp" checkout <이 태스크 커밋>
    scripts/nexi-isolated.sh --root "$tmp" -- bash -c '
      cd "'"$tmp"'" &&
      <README의 설치·DB 준비 명령> &&
      make build && make test && make lint
    '
    git -C "$tmp" status --porcelain --untracked-files=all   # 빈 출력이어야 함
    ```
- 회귀 검사: 없음. skeleton 태스크라 이전에 통과하던 검사가 없다.

## 하지 않을 일

- 직원·프로젝트·배치 데이터 모델, 저장소 계층 구현, 시드 데이터 (→ T#5).
- 로그인·권한 검사 (→ T#6).
- 디자인 토큰·레이아웃 셸·기본 컴포넌트, `make screenshots` (→ T#4, 디자인 시스템 태스크).
- 실제 업무 화면(목록·상세·배치) 구현.
- `scripts/nexi-isolated.sh`를 이 태스크 이후의 모든 태스크 검사에 강제하는 일(이 태스크는 스크립트를 만들고 스스로의 검사에 쓰는 것까지만 한다; 다른 태스크가 쓰는 것은 각 태스크 계약서가 정한다).
