# T#54 변경: 직원·시드 트랜잭션과 SQLite 동시성

## 산출물

SQLite WAL 모드 및 busy_timeout 설정이 적용되고, 핵심 직원 관리 및 시드 주입 로직에 트랜잭션 경계가 설정된 백엔드 시스템.

## 수용 기준

1. **SQLite 동시성 설정**. 격리된 테스트 DB에서 `PRAGMA journal_mode`가 `wal`이고 `PRAGMA busy_timeout`이 `5000`이다 — 확인: `SqliteConfigTest`가 해당 PRAGMA 값을 쿼리하여 검증함.
2. **시드 원자성 보장**. `SeedRunner.run()` 실행 중 예외 발생 시 모든 시드 데이터가 롤백되어 `employee`, `department` 등 모든 테이블이 비어있다 — 확인: `SeedAtomicityTest`가 시드 도중 강제 예외를 발생시키고 테이블 행 수를 검사함.
3. **시드 재시작 가능성**. 시드 실패 후 다시 실행했을 때, 이전의 불완전한 데이터 없이 처음부터 정상적으로 시드가 완료된다 — 확인: `SeedRetryTest`가 [실패 $\rightarrow$ 재실행 $\rightarrow$ 성공] 과정을 거쳐 최종 시드 건수를 검사함.
4. **직원 관리 원자성 보장**. 다음 세 작업 중 어느 단계에서든 예외 발생 시 이전 상태로 완전히 롤백된다 — 확인: `EmployeeTransactionTest`가 각 단계에서 예외를 발생시키고 DB 상태를 검사함.
   - (i) `register()`: 직원 정보 삽입 후 `employee_skill` 삽입 중 실패 시 `employee` 테이블에 레코드가 남지 않아야 함.
   - (ii) `update()`: 기존 기술 삭제 후 새 기술 삽입 중 실패 시, 기존 기술 목록이 그대로 유지되어야 함.
   - (iii) `changeStatus()`: 상태 변경 및 관련 기록 처리 중 실패 시 상태가 변경되지 않아야 함.
5. **동시 쓰기 정합성**. 여러 스레드가同一 직원에게 동시에 배치를 요청해도 날짜별 투입 합계 100% 규칙(D8)이 엄격히 지켜진다 — 확인: `ConcurrentAssignmentTest`가 멀티스레드로 배치를 요청하고 최종 합계를 검사함.
6. **잠금 실패 재현**. SQLite 잠금 충돌 상황을 의도적으로 발생시켜 `SQLITE_BUSY` (또는 이에 대응하는 Exception)가 발생하는 것을 관찰할 수 있다 — 확인: `LockObservationTest`가 강제로 잠금을 유발하고 예외 발생 여부를 확인함.

## 검증 명령

- 새 검사:
  - `./backend/mvnw -f backend/pom.xml test -Dtest=com.ax.rms.concurrency.SqliteConfigTest` — 기준 1 (레드: WAL/Timeout 미설정으로 인해 기본값 반환)
  - `./backend/mvnw -f backend/pom.xml test -Dtest=com.ax.rms.seed.SeedAtomicityTest,com.ax.rms.seed.SeedRetryTest` — 기준 2, 3 (레드: `@Transactional` 부재로 일부 데이터 잔존)
  - `./backend/mvnw -f backend/pom.xml test -Dtest=com.ax.rms.employee.EmployeeTransactionTest` — 기준 4 (레드: 기술 수정 중 실패 시 기존 기술 유실)
  - `./backend/mvnw -f backend/pom.xml test -Dtest=com.ax.rms.concurrency.ConcurrentAssignmentTest,com.ax.rms.concurrency.LockObservationTest` — 기준 5, 6 (레드: Race Condition으로 인한 100% 초과 또는 즉시 에러 발생)
- 회귀 검사: `make test`, `make lint`, `make build` — T#5, T#8, T#10의 기존 기능(CRUD 및 기본 시드 주입)이 그대로 작동함을 확인.

## 하지 않을 일

- `SQLITE_BUSY` 에러의 클라이언트 응답 코드 변경(409 등으로 변환) — 이는 T#56에서 담당함.
- DB 스키마(`schema.sql`)의 구조 변경.
