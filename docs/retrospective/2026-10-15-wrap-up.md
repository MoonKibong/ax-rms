### 1.3 항목별 검토

#### 의견 1. AI 결과에 대한 높은 의존도

**사실 확인**
- 3·4번 문제는 각 태스크 리뷰에서 APPROVE를 받고 병합되었다. 맞다.
- NEXI의 리뷰(`nexi-review`)는 그 태스크 계약서의 수용 기준, 증거, 스크린샷을 판정하고, 테스트가 놓친 업무 오류와 유지보수 문제도 보도록 되어 있다(`nexi-review` SKILL 7단계). 다만 대상은 그 태스크의 변경(`git diff origin/main...HEAD`)이고, `main` 전체를 다시 보는 단계는 없다.
- 같은 날 따로 돌린 전체 코드 리뷰는 이런 문제를 쉽게 찾아냈다. 예: B#1 기간 무제한 반복, B#3 트랜잭션 누락, F#1 세션 만료 처리 없음.
- 사람이 확인하는 장치는 이미 있다.
  - 계약서 승인: PM이 수용 기준을 읽고 승인한다.
  - 화면 태스크의 스크린샷: 리뷰어가 BRIEF와 대조한다.
  - `nexi-finish`: 사람이 앱을 띄워 둘러보기 16행을 확인한다.

**의견: 타당함.** 원인은 두 가지로 본다. `main` 전체를 정기적으로 보는 독립 단계가 없었고, 태스크 리뷰의 유지보수 검토는 있었지만 충분히 작동하지 않았다. 사람이 시간을 내서 보라는 다짐만으로는 부족하고, 검토를 단계로 두는 편이 효과가 있다.

스크린샷 대조는 정적인 화면만 확인한다. 세션 만료 뒤 재시도(F#1) 같은 상호작용은 스크린샷만으로는 확인하기 어렵고, 상호작용 테스트나 사람의 직접 사용 점검이 필요하다. 병합마다 실행하는 비용은 크므로, "몇 개 태스크마다"와 "최종 보고 전"에 사람이 핵심 흐름을 직접 실행하는 점검을 권한다(실행이 쉬워지려면 의견 8의 `make run`이 먼저 있어야 한다).

**이 프로젝트**
- 2절의 코드 리뷰 결과(백엔드 21건, 프런트엔드 20건)를 3절의 변경 이슈로 만든다.

**NEXI 키트 제안**
- 새 단계 "구조 점검(architecture checkpoint)": 병합된 태스크가 N개(예: 5)가 될 때마다, 그리고 `nexi-finish` 직전에 `main` 전체를 읽기 전용으로 리뷰한다.
  - 다른 agent가 리뷰하고 결과는 이슈로 남긴다.
  - 확인 기준은 7번의 백엔드 기준 문서와 BRIEF다.
- `nexi-review` 판정에 "계약 밖 관찰" 칸을 둔다. 판정에는 영향이 없지만, 일관성 문제를 기록하게 한다.

#### 의견 3. 접근 제어자와 캡슐화 기준 부재

**사실 확인**
- `backend/src/main/java`의 최상위 타입 66개가 모두 `public`이다(class 36개, 나머지는 record·enum·interface). package-private은 0개다.
- `project/ProjectService.java:4,81`이 `dashboard.DashboardService`의 static 메서드 `shortStaffedProjectIds`를 직접 부른다.

**의견: 타당함.** 전부 public이라는 사실만으로 모든 타입이 잘못된 것은 아니다. 다른 기능이 써야 하는 타입(엔티티, 저장소, 공용 계산)은 public이어야 한다. 문제는 공개 경계를 정한 기준이 없었다는 점이다. Spring은 package-private 컴포넌트와 컨트롤러도 등록하므로, 기능 안에서만 쓰는 타입을 숨기는 데 기술적 장애는 없다. 어느 타입을 package-private으로 바꿀지는 일괄 전환이 아니라 기준 문서(의견 7)에서 정하는 설계 판단이다.

참고로 #32의 "#11 판정 재사용"은 PM 결정(이슈 #11 댓글)이었다. 의존 자체는 의도한 것이다. 문제는 재사용 대상이 dashboard 패키지의 서비스 안에 있었다는 점이다. package-private 기준이 있었다면 컴파일 에러가 났을 것이다. 그러면 판정이 공용 도메인 계산(예: `availability` 옆)으로 빠져나왔을 것이다(B#12와 같은 결론).

**이 프로젝트**
- 리팩터링 태스크를 둔다.
  - 기준 문서가 정한 공개 경계에 따라 기능 내부 타입(컨트롤러, 서비스, 요청·응답 record 등)을 package-private으로 바꾼다.
  - D20 판정을 공용 컴포넌트로 옮긴다.
- 테스트는 같은 패키지에 있으므로 대부분 그대로 컴파일된다.

**NEXI 키트 제안**
- 7번의 백엔드 기준 문서에 접근 제어 원칙을 넣는다.
- 그 원칙을 기계로 확인하는 검사를 둔다(예: ArchUnit 규칙 "다른 기능 패키지의 서비스를 import하지 않는다").
- `make lint`에 포함해 리뷰 이전에 걸리게 한다.

#### 의견 4. 예외 처리 기준의 일관성

**사실 확인**

- `@RestControllerAdvice` 4개:
  - `web/ApiErrorHandler`(범위 없음),
  - `employee/EmployeeApiExceptionHandler`(범위 없음),
  - `project/ProjectApiErrorHandler`(`basePackages` 지정),

- 실행 중인 앱에서 깨진 JSON(`{bad`)을 보낸 결과:

  - `POST /api/assignments` → `{"code":"ASSIGNMENT_REQUEST_INVALID","message":"요청 형식이 올바르지 않습니다."}`
- T#9 계약서 33행: "세 처리기를 하나로 합치는 일은 이 태스크가 하지 않는다." 정리는 끝까지 이루어지지 않았다.

**의견: 타당함.** "도구 차이가 아니라 공통 기준이 없었던 탓"이라는 진단에 동의한다. 키트 쪽 원인을 하나 더 들면, T#8 계약서는 "#6과 이 태스크 중 나중에 `main`에 들어가는 쪽이 정리한다"고 **책임을 조건부로 정했지만, 별도 이슈나 완료 확인이 없어 이행되지 않았다.** T#9 계약서 33행은 새 약속이 아니라 "이 태스크에서는 합치지 않는다"는 범위 제한이다. 이것은 1번의 구조 점검이 잡았어야 할 종류의 문제다.

**이 프로젝트**
- 공통 `ApiException(status, code, message)`과 전역 처리기 하나로 합친다.
- 형식 오류(400)와 최후 처리기(500, 로그 포함)도 D33 형식으로 맞춘다(B#6, B#21과 함께).

**NEXI 키트 제안**
- 계약서에 "다른 태스크가 나중에 정리"를 쓰면, `nexi-contract`가 그 정리를 위한 이슈 번호를 요구한다.
- `nexi-finish` 2단계에 "열린 정리 약속" 점검을 더한다: 계약서에 "나중에", "합치지 않는다" 같은 문장이 있고 대응 이슈가 없으면 표시한다.

#### 의견 5. 주석과 문서만으로 코드를 파악하기 어려움

**사실 확인**
- `rg -o '\bD[0-9]{1,2}\b|T#[0-9]+' backend/src frontend/src | wc -l` → 506회(289줄, 157파일, 테스트 포함). `rg -o '<같은 패턴>' backend/src/main frontend/src -g '!*.test.*' | wc -l` → 363회(테스트 제외). 주석만이 아니라 문자열·테스트 이름의 참조도 포함한 수이고, 패턴과 도구에 따라 수가 달라진다(단어 경계 없이 세면 523회). 의견의 "400곳 이상"은 테스트를 포함한 발생 횟수로 보면 맞다.
- README는 실행, 권한, 검사, 격리 위주다. 패키지·디렉터리 역할을 정리한 문서는 없다.

**의견: 타당함.** 의견은 번호를 없애자는 것이 아니라, 번호에 내용을 붙이고 구조 안내 문서를 두자는 것이다. 그 제안에 동의한다.
- **D번호**는 코드 → 요구사항 결정을 추적하게 해 주고, 리뷰가 근거를 대는 데 실제로 쓰였다. 그래서 남기고 한 줄 요약을 붙인다.
- **T#번호**는 다르다. 그 코드가 어느 태스크에서 왔는지는 git 기록(`git blame`, 병합 commit)이 이미 알려 준다. 코드 주석에 오래 남길 가치가 작다.
- "번호만으로는 뜻을 알 수 없다"는 지적은 맞다. 번호 옆에 한 줄 요약을 붙이는 것은 비용이 작고 효과가 크다.

**이 프로젝트**
- `docs/ARCHITECTURE.md`를 둔다: 패키지·디렉터리별 역할, 요청 흐름, 공용 코드 위치.
- 주석은 손댈 때마다 `D20`을 `D20(인력 부족 판정)` 식으로 바꾼다.

**NEXI 키트 제안**
- 주석 규칙을 정한다: "결정 번호에는 한 줄 요약을 붙인다. 태스크 번호는 코드 주석에 쓰지 않는다(커밋 메시지에만 쓴다)."
- 백엔드 기준 문서 승인 때 `ARCHITECTURE.md`의 뼈대도 함께 만든다(7번).

#### 의견 6. 인력 리스크와 PM 병목

**사실 확인**
- 규칙상 병합은 PM만 한다(AGENTS.md 팀 규칙 3). 계약 승인도 `nexi-contract approve`의 PM 검사로 PM만 한다. 리뷰 기록은 PM 전용이 아니다.
- 참여자는 PM 승인·병합 대기가 진행을 막았다고 느꼈다(참여자 경험). 대기 시간은 따로 재지 않았다.
- PM이 #28·#10·#50을 직접 개발했고, 그래서 "기록자 ≠ PR 작성자"(D41) 규칙을 PM 확인으로 예외 처리한 일이 세 번 있었다(`docs/FINAL.md:121`). 그 목적이 인력 부족을 메우는 것이었다는 설명은 PM 진술이다.
- 확인한 이슈(#19, #34) 댓글은 "선행 작업 수용"·"누구 차례" 알림이 대부분이다. PM 결정과 그 이유가 댓글로 남은 경우도 있지만(#19, #34의 "PM 결정" 댓글), 담당자가 바뀔 때 현재 상태·남은 일을 적는 인계 형식은 없다(#34·#19는 작업 시작 전에 넘겨 인계할 내용이 적었지만, 이슈에는 배정 변경만 남았다).

**의견: 타당함.** PM 한 사람이 승인하는 것은 책임 소재를 분명히 하려는 의도된 통제다. 그러니 "누구나 병합"으로 푸는 것은 맞지 않는다. 의견대로 **미리 지정한 대리자**와 **인계 메모**가 맞는 처방이다.

**이 프로젝트**
- 해당 없음(종료). 다음 프로젝트부터 적용한다.

**NEXI 키트 제안**
- AGENTS.md에 `PM 대리: <login>` 줄을 둔다. PM 검사는 `PM:` 또는 `PM 대리:` 중 하나와 맞으면 통과하고, 대리자가 한 승인·병합은 댓글에 표시한다.
- 대리자와 개발자가 같은 사람이면 D41처럼 막는다.
- 태스크마다 인계 메모를 남긴다. 형식: `인계: 현재 상태 / 남은 일 / 결정 이유(링크)`. `nexi-implement`가 멈출 때, 그리고 담당자를 바꾸는 `nexi-backlog assign` 때 이슈에 남기도록 한다.

#### 의견 8. 로컬 실행 절차가 번거로움

**사실 확인**
- `.nvmrc`(24.21.0)는 있고 README는 `nvm use`를 안내한다.
- 하지만 `Makefile`에는 `build`, `test`, `lint`, `screenshots`만 있고 실행 목표가 없다.
- 백엔드 실행 명령은 runner 옵션을 포함해 두 줄이고, 터미널이 두 개 필요하다.
- 최종 보고 때 실제로 이 번거로움을 겪었다.
  - 포트 8080(다른 앱 open-webui, 자동 재시작 서비스)과 5173(다른 세션의 개발 서버)이 막혀 앱을 두 번 띄우지 못했다.
  - 백엔드는 주소를 정하지 않아 모든 네트워크에 열리므로, `SERVER_ADDRESS=127.0.0.1`을 더해 띄웠다(B#15).

**의견: 타당함.** Node 버전 맞추기와 두 터미널 실행은 모두 자동화할 수 있는 비용이다. `make run`이 버전을 확인하고 두 서버를 함께 띄우면 둘 다 줄어든다.

**이 프로젝트**
- `make run`을 둔다: 버전 확인 → 포트 확인 → 백엔드(127.0.0.1)와 프런트엔드를 함께 띄우고, Ctrl-C로 함께 내린다.
- 포트는 환경 변수로 바꿀 수 있게 한다.
- `make reset-db`(데모 DB 다시 만들기)도 둔다. B#5: 시드 날짜가 DB를 만든 날 기준이라 시간이 지나면 시나리오가 깨진다.

**NEXI 키트 제안**
- 뼈대 태스크 계약서 필수 항목에 "한 줄 실행 명령과 그 검사"를 더한다.
- `nexi-finish`는 README의 실행 명령 대신 그 명령을 쓴다.


각 의견의 "이 프로젝트" 조치는 3절의 변경 이슈로 합쳤고, "NEXI 키트 제안"은 4절에 모았다.

## 3. 후속 조치 (중복 제거)

### 3.1 원칙과 규모

- 끝난 태스크의 계약서·증거·판정은 고치지 않는다. 바꿀 것은 `nexi-backlog change`로 만든 변경 이슈가 맡고, 각각 계약 → 구현 → Codex 리뷰 → PM 병합을 거친다.
- 모두 구현 변경이다. 지금의 결정(D1–D41)과 BRIEF 안에서 동작을 고친다. 배포된 대상은 없다(D40, 로컬 시연).
- **규모.** 처음에는 발견 사항을 모두 덮는 22개안(예상 약 105시간)을 세웠다. 원래 프로젝트(태스크 23개)만큼 크고, NEXI 태스크마다 계약·증거·리뷰·병합의 고정 비용(대략 1–2시간)이 든다. PM은 팀원이 납득하기 어려운 규모라고 판단했다. 그래서 **실제 결함(데이터 손실·장애·사용자가 겪는 오동작)과 팀이 제기한 오류 처리·실행 문제만** 지금 이슈로 만들고, 나머지는 3.3절에 보류로 남긴다. 축소안은 astra(Codex `gpt-6-astra`)의 읽기 전용 검토를 거쳐 6개로 정했다.
- **변경 대상.** 공통 부분 변경은 원래 태스크별로 나누면 따로 진행할 수 없어, 변경 하나를 이슈 하나로 만들고 `변경 대상:` 줄에 관련 태스크를 모두 적었다(키트의 "대상당 이슈 하나"와 다른 점, PM 확인). T#14는 나뉘어 수용되지 않았으므로 대상이 아니다.
- **크기.** 예상에는 계약·증거·리뷰·병합 시간을 포함했다. 계약서를 쓸 때 다시 산정하고, 하루(약 6시간)를 넘으면 범위부터 줄인다.
